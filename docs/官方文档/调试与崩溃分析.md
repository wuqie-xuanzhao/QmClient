## 使用 AddressSanitizer + UndefinedBehaviourSanitizer 或 Valgrind 的 Memcheck

ASan+UBSan 和 Memcheck 能更容易地发现代码问题。条件允许时，请用它们测试你的改动。

ASan+UBSan 的编译方式：

```sh
CC=clang CXX=clang++ CXXFLAGS="-fsanitize=address,undefined -fsanitize-recover=all -fno-omit-frame-pointer" CFLAGS="-fsanitize=address,undefined -fsanitize-recover=all -fno-omit-frame-pointer" cmake -DCMAKE_BUILD_TYPE=Debug -Bbuild -GNinja
cmake --build build
```

运行方式：

```sh
UBSAN_OPTIONS=log_path=./SAN:print_stacktrace=1:halt_on_errors=0 ASAN_OPTIONS=log_path=./SAN:print_stacktrace=1:check_initialization_order=1:detect_leaks=1:halt_on_errors=0:handle_abort=1 ./DDNet
```

之后检查 `SAN.*` 文件。它比 memcheck 能发现更多问题、运行更快，但需要较新的 GCC/Clang 编译器。

在 macOS 上使用 Homebrew 的 `sdl2-compat` 包时，需要设置 `DYLD_LIBRARY_PATH`：

```sh
DYLD_LIBRARY_PATH=$(brew --prefix sdl3)/lib ./DDNet
```

Valgrind 的 memcheck：编译一个普通的 Debug 构建，然后运行 `valgrind --tool=memcheck ./DDNet`。预期会有明显的性能下降。

## 为官方 Windows 发行版符号化崩溃转储（`.RTP`）

符号化是把原始崩溃数据转换成人类可读的调用栈。以下流程假定该崩溃转储来自官方 DDNet 发行版、候选版或 nightly 版本——这些版本才提供调试符号。

如果你在 Windows 上以 debug 模式、带 `-DEXCEPTION_HANDLING=ON` 构建客户端，崩溃转储会直接包含可读的调用栈。

1. **前置条件**
   - 用系统包管理器（Windows 上用 MSYS2）安装 `binutils`，特别是其中的 `addr2line` 和 `objdump` 工具：
     - MSYS2：`pacman -S mingw-w64-x86_64-binutils`
     - Ubuntu/Debian：`sudo apt install binutils`
   - 安装 [Python](https://www.python.org/downloads/)。
   - 下载/克隆 [ddnet](https://github.com/ddnet/ddnet) 仓库。

2. **下载崩溃转储（`.RTP` 文件）**
   - 务必保留原始文件名，因为文件名中包含用于匹配调试符号的重要信息。

3. **运行脚本完成符号化**
   - 在 `ddnet` 项目目录下打开终端并运行：
   ```sh
   python scripts/parse_crashlog_drmingw.py "<崩溃转储路径>"
   ```
   - 脚本会自动为较新的崩溃转储下载正确的调试符号。若不成功，见步骤 4。

4. **（可选）手动下载并指定调试符号**
   - 从 https://ddnet.org/downloads/symbols/ 下载与 git 提交版本和平台（win32/win64/win-arm64，steam/非 steam）匹配的调试符号压缩包并解压。
   - git 提交版本和平台可以从崩溃转储的文件名中读出。
   - 若文件名不含 `steam`，则为独立版本。
   - 在 `ddnet` 项目目录下打开终端并运行：
   ```sh
   python scripts/parse_crashlog_drmingw.py "<服务端/客户端崩溃转储路径>" --executable "<服务端/客户端符号 exe 路径>"
   ```

5. **检查输出**
   - 检查调用栈在理论上是否成立。如果函数调用顺序不合逻辑，或大量行显示 `?? ??:0`，很可能崩溃转储与调试符号配错了。
