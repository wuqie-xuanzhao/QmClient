# 向 DDNet 贡献代码

> 对应上游：`docs/CONTRIBUTING.md`

## 总则

开始写代码前，请先开一个 issue 讨论你的想法。
如果花时间做的贡献与 DDNet 项目的理念不符，那就太遗憾了。

以下是一份（非穷举的）通常会被拒绝的清单：

- 给 dummy 添加影响玩法的功能。
  https://github.com/ddnet/ddnet/pull/8275
  https://github.com/ddnet/ddnet/pull/5443#issuecomment-1158437505
- 破坏网络协议或皮肤、demo 等文件格式的向后兼容性。
- 破坏玩法的向后兼容性：
	- 不应让已有的 rank 变得无法达成。
	- 不应让已有的地图失效。
	- 新玩法不应让已完成过的地图变得更容易通关。

查看 [issue 列表](https://github.com/ddnet/ddnet/issues) 寻找可以着手的 issue。
未打标签的 issue 尚未分类，通常不是好的候选。
此外，标签 https://github.com/ddnet/ddnet/labels/needs-discussion 表示实现前仍需讨论的 issue，而标签 https://github.com/ddnet/ddnet/labels/fix-changes-physics 的 issue 对新贡献者来说过于复杂。
推荐从带 https://github.com/ddnet/ddnet/labels/good%20first%20issue、https://github.com/ddnet/ddnet/labels/bug 和 https://github.com/ddnet/ddnet/labels/feature-accepted 标签的 issue 入手。
请确认该 issue 尚未被他人处理——检查它的负责人指派，以及是否有与之关联的未关闭 pull request。
如果你想处理某个 issue，请在下面评论以便被指派，或提出你的疑问。

添加新功能通常需要至少两位维护者的支持，以避免功能蔓延。

## 编程语言

我们目前使用以下语言开发 DDNet。

- C++
- 极少量 Rust
- Python 用于代码生成和辅助工具
- CMake 用于构建

无法用其他编程语言添加代码。

在平台支持方面，我们也会用到 Java（Android）或 Objective-C++（macOS）等其他语言，但仅限于平台特定代码。

## 代码风格

有一些风格规则。其中一部分由 CI 强制执行，另一部分由审查者人工检查。
如果 GitHub pipeline 报错，请查看日志并尝试修复。

这类修复提交最好用 `git commit --amend` 或 `git rebase -i` 合并成一个大提交。

很多风格问题可以通过运行修复脚本 `./scripts/fix_style.py` 自动解决。

我们使用 clang-format 20 格式化 C++ 代码。

### 变量、方法、类名使用大驼峰

`src/base` 文件夹中的文件除外。

单个词：

- `int length = 0;` ❌
- `int Length = 0;` ✅

多个词：

- `int maxLength = 0;` ❌
- `int MaxLength = 0;` ✅

### 变量名应具有描述性

❌ 避免：

```cpp
for(int i = 0; i < MAX_CLIENTS; i++)
{
	for(int k = 0; k < NUM_DUMMIES; k++)
	{
		if(k == 0)
			continue;

		m_aClients[i].Foo();
	}
}
```

✅ 应改为：

```cpp
for(int ClientId = 0; ClientId < MAX_CLIENTS; ClientId++)
{
	for(int Dummy = 0; Dummy < NUM_DUMMIES; Dummy++)
	{
		if(Dummy == 0)
			continue;

		m_aClients[ClientId].Foo();
	}
}
```

更多示例见 [这里](https://github.com/ddnet/ddnet/pull/8288#issuecomment-2094097306)。

### 我们对匈牙利命名法的理解

DDNet 从 [Teeworlds](https://www.teeworlds.com/?page=docs&wiki=nomenclature) 继承了匈牙利式的前缀命名法。

只使用下面列出的前缀。DDNet 代码库**并不**严格遵循完整的匈牙利命名法。

**不要**用 `c` 表示常量、用 `b` 表示布尔值、用 `i` 表示整数。

C 风格函数指针是指针，但 `std::function` 不是。

#### 变量

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `m_` | 类成员 | `int m_Mode`, `CLine m_aLines[]` |
| `g_` | 全局成员 | `CConfig g_Config` |
| `s_` | 静态变量 | `static EHistoryType s_HistoryType`, `static char *ms_apSkinNameVariables[NUM_DUMMIES]` |
| `p` | 裸指针和智能指针 | `char *pName`, `void **ppUserData`, `std::unique_ptr<IStorage> pStorage` |
| `a` | 定长数组和 `std::array` | `float aWeaponInitialOffset[NUM_WEAPONS]`, `std::array<char, 12> aOriginalData` |
| `v` | 向量（`std::vector`） | `std::vector<CLanguage> m_vLanguages` |
| `pfn` | 函数指针（**不是** `std::function`） | `m_pfnUnknownCommandCallback = pfnCallback` |
| `F` | 函数类型定义 | `typedef void (*FCommandCallback)(IResult *pResult, void *pUserData)`, `typedef std::function<int()> FButtonColorCallback` |

按需合理组合使用。

#### 类

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `C` | 类 | `class CTextCursor` |
| `I` | 接口 | `class IFavorites` |
| `S` | ~~结构体（请改用类）~~ | ~~`struct STextContainerUsages`~~ |

### 枚举

无作用域枚举（`enum`）和有作用域枚举（`enum class`）都应以 `E` 开头并使用大驼峰。枚举值应使用大写下划线风格（SCREAMING_SNAKE_CASE）。

所有新代码都应使用有作用域枚举，且枚举值名称中不应包含枚举名。

❌ 避免：

```cpp
enum STATUS
{
	STATUS_PENDING,
	STATUS_OKAY,
	STATUS_ERROR,
};
```

✅ 应改为：

```cpp
enum class EStatus
{
	PENDING,
	OKAY,
	ERROR,
};
```

同样**不要**用 `enum` 或 `enum class` 表示标志位，改用下一节的做法。
`enum class` 只应用于枚举。带类型值的常量应改用 `constexpr`。

### 位标志

现有代码大量使用 `enum` 表示标志位。新代码应使用 `inline constexpr`。

❌ 避免：

```cpp
enum
{
	CFGFLAG_SAVE = 1,
	CFGFLAG_CLIENT = 2,
	CFGFLAG_SERVER = 4,
	CFGFLAG_STORE = 8,
	CFGFLAG_ECON = 16,
};
```

✅ 应改为：

```cpp
namespace ConfigFlag
{
	inline constexpr uint32_t SAVE = 1 << 0;
	inline constexpr uint32_t CLIENT = 1 << 1;
	inline constexpr uint32_t SERVER = 1 << 2;
	inline constexpr uint32_t STORE = 1 << 3;
	inline constexpr uint32_t ECON = 1 << 4;
}
```

### 应避免使用 C 预处理器

- 避免用 `#define` 定义常量，改用 `enum class` 或 `inline constexpr`。
  只有在别无选择时才使用 `#define`（例如条件编译）。
- 避免函数式 `#define`。如有可能，把代码提取为函数或 lambda 表达式，而不是宏。
  只有在没有其他更可读的方案时才使用函数式 `#define`。

### 不鼓励使用 `goto`

新代码中不要使用 `goto` 关键字，C++ 有更好的控制流结构。

### 应避免在 if 语句中赋值

不要在 if 语句中给变量赋值。

❌

```cpp
int Foo;
if((Foo = 2)) { .. }
```

✅

```cpp
int Foo = 2;
if(Foo) { .. }
```

除非替代写法更复杂、更难读。

### 应避免在布尔上下文中使用整数

❌

```cpp
int Foo = 0;
if(!Foo) { .. }
```

✅

```cpp
int Foo = 0;
if(Foo != 0) { .. }
```

### 应避免使用带默认参数的方法

默认参数很容易失效；如果有多个默认参数，即使只想改最后一个，也必须逐个指定。

### 应避免方法重载

试着取更有描述性的名字。

### 应避免全局/静态变量

使用成员变量或通过参数传递状态，而不要用全局或静态变量，因为静态变量会在类的各个实例间共享同一个值。

避免静态变量 ❌：

```cpp
int CMyClass::Foo()
{
	static int s_Count = 0;
	s_Count++;
	return s_Count;
}
```

改用成员变量 ✅：

```cpp
class CMyClass
{
	int m_Count = 0;
};
int CMyClass::Foo()
{
	m_Count++;
	return m_Count;
}
```

常量可以是静态的 ✅：

```cpp
static constexpr int ANSWER = 42;
```

### Getter 不应带 `Get` 前缀

虽然现有代码库中已有大量以 `Get` 开头的方法，但新增 getter 不应带该前缀。

❌

```cpp
int GetMyVariable() { return m_MyVariable; }
```

✅

```cpp
int MyVariable() { return m_MyVariable; }
```

### 类成员变量应在声明处初始化

不要这样 ❌：

```cpp
class CFoo
{
	int m_Foo;
};
```

如有可能，这样 ✅：

```cpp
class CFoo
{
	int m_Foo = 0;
};
```

### 应优先使用 `class` 而非 `struct`

虽然代码中仍有许多 `struct` 在使用，但所有新代码都应只使用 `class`。

### 应使用现代 C++ 而非旧式 C 风格代码

DDNet 在可移植性（易于在所有常见发行版上编译）与使用现代特性之间取得平衡。
因此，只要所用 C++ 版本支持，鼓励你使用全部现代 C++ 特性。
但要留意：在游戏主循环代码中应避免内存分配，因此栈上的静态缓冲区可能更可取。

示例：

- 用 `nullptr` 取代 `0` 或 `NULL`。
- 如有可能，用 `std::fill` 初始化数组，而不是 `mem_zero` 或循环。

### 用 `true` 表示成功

对于可能成功或失败的方法，不要用 `int` 作返回类型。
改用 `bool`。`true` 表示成功，`false` 表示失败。

参见 https://github.com/ddnet/ddnet/issues/6436

### 文件名

文件和文件夹名称应全部小写，单词之间用下划线分隔。

❌

```cpp
src/game/FooBar.cpp
```

✅

```cpp
src/game/foo_bar.cpp
```

## 代码文档

`base` 文件夹中所有函数的公开声明、类等都必须编写代码文档。
对于其他代码，面向复用或有助于提升清晰度的函数、类等，建议编写文档。

我们使用 [doxygen](https://www.doxygen.nl/) 生成代码文档。
文档会定期更新，可在 https://codedoc.ddnet.org/ 查阅。

我们使用 [Javadoc 风格块注释](https://www.doxygen.nl/manual/docblocks.html)，且 [doxygen 命令](https://www.doxygen.nl/manual/commands.html) 前缀用 `@` 而非 `\`。

## 本地化

我们使用 [Weblate](https://hosted.weblate.org/engage/ddnet/) 翻译 DDNet 客户端中面向用户的字符串。
在 Weblate 上注册即可参与翻译项目。
使用 Weblate 进行翻译的入门说明见 [Weblate 文档](https://docs.weblate.org/en/latest/index.html)。
要建议添加其他语言的翻译：[在 GitHub 上开 issue](https://github.com/ddnet/ddnet/issues/new)。

`data/languages` 文件夹中的翻译文件不应由译者手动修改。
维护者会根据 Weblate 上的翻译，在发布时更新翻译文件。

## 提交信息

描述你的贡献为玩家/用户带来的变化，而不是从技术角度讲你做了什么。你的 PR 信息最好能直接用于 [变更日志](https://ddnet.org/downloads/)。
