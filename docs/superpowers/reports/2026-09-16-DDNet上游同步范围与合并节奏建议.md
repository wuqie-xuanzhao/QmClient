## 一、同步基线如何确定

本仓库对上游是**重放式吸收**而非直接 merge：同一个上游提交在两边 SHA 不同
（例：上游 `d7266581d` = 本地 `56be9b0f0`，同为 teehistorian #12788），
所以 `git merge-base dyl_dev ddnet-upstream/master` 停在 `de609e845`（2025-11-27），
**不能用它判断同步进度**。

可靠的基线来自上一轮同步记录：

- [2026-09-08-DDNet分批同步与旧台账复核](../reports/archive/2026-09-08-upstream-sync-history/2026-09-08-DDNet分批同步与旧台账复核.md)
  末节「上游新增提交复核（2026-09-08）」明确：以 `59968143f` 为已同步基线复核至
  `ddnet-upstream/master`，新增 3 个非合并提交，对应包装 `1a703fa06`、`d7266581d`、`3290b4b35`。
- 因此**上一轮同步终点 = `3290b4b35`（2026-09-08）**，即 20.0 发布后的 master。

本轮以 `3290b4b35` 为排他基线，上游取 `a853d333a`（2026-09-15，实际 fetch 所得）。

> 注：沙箱内 `refs/remotes/ddnet-upstream/master` 无法被 `git fetch` 更新（对象已入库、
> 引用不落盘），因此全程用完整 SHA 操作。这是环境限制，不是仓库问题。

## 五、合并频率建议

### 上游产出速率（实测）

| 区间 | 非合并提交 | 折合每周 |
| --- | --- | --- |
| 2026 全年至今（约 37 周） | 1078 | ~29 |
| 20.0 发布后（2026-08-21 起约 3.7 周） | 124 | ~33 |
| 近 8 周（W31–W38，含 20.0 冲刺） | 329 | ~41 |
| 近 4 周（W35–W38） | 101 | ~25 |
| 峰值（W33） | 81 | 81 |

上游版本节奏（`src/game/version.h` 变更史）：19.5 → 2025-09-02、19.6 → 2025-10-07、
19.7 → 2025-12-07、19.8 → 2026-01-15、19.9 → 2026-03-15、20.0 beta 2026-04-19 / release 2026-08-21、
20.1 dev 2026-08-12。**大致 1–2 个月一版**，发版前后 2 周是提交高峰（W31=58、W33=81、W34=46）。

### 建议：双周完整同步 + 每周轻量巡视

| 层级 | 频率 | 内容 | 单批规模 |
| --- | --- | --- | --- |
| 轻量巡视 | 每周 | fetch、生成台账、筛出崩溃/DoS/权限类，不实施 | 0 |
| 完整同步 | **每 2 周** | 按功能域分批适配 + 构建 + gate + 台账回填 | ~50–60 条 |
| 强制上限 | **不超过 4 周** | 超过即拆成 2–3 个批次，不允许单批 >100 条 | — |
| 即时通道 | 触发式 | 服务端崩溃、DoS 限速、权限绕过，不等窗口 | 1–5 条 |
| 版本对齐 | 上游 bump dev version 后 1 周内 | 完整同步一轮 | — |

**理由：**

1. 上游稳定输出 25–40 条/周。双周即 50–80 条，与 9/8 那轮的实际吞吐（49 条非合并提交、
   多批次 + 2M token 预算）同量级，是单轮可消化的上限附近。
2. 适配成本与条数近似线性（73% 需人工适配），批次越大冲突越难拆；同时每轮有固定开销
   （fetch、台账、全量构建、gate），频率过高会浪费在固定开销上。**双周是两者交点。**
3. 4 周会出现 ~120–160 条，明显超过单轮可处理量，且会跨过一次上游发版高峰。
4. 发版高峰（可达 81 条/周）必须避开或提前：**在上游发版前把上一批清完**，
   不要让自己在高峰里追进度。
