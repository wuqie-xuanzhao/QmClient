## 三、三条关键机制（本轮所有结论的依据，务必先读）

1. **图集边长 = 显存成本**。页是 RGBA8、无 mipmap，`LoadProfile()` 里逐页 `LoadTexture()`
   整页上传：**4096² = 64 MiB、2048² = 16 MiB、1024² = 4 MiB**。
2. **官方 `msdf-atlas-gen` 装不下时不会静默截断**：打印 `Could not fit N out of M glyphs`
   并以非 0 退出（只有「无轮廓字形」如空格被静默跳过）。
   → **「先整批试一页、失败再拆」是可靠的**，也是唯一能同时压住页数与显存的做法。
3. **两个生成工具都需要 DLL 在 PATH**（否则 `0xC0000135`）：
   - 自建 `qm-nameplate-msdf-atlas.exe` → `libfreetype.dll`
   - 官方 `msdf-atlas-gen.exe` → `libfreetype.dll` + `libpng16-16.dll` + `zlib1.dll`
   - 都在 `ddnet-libs/*/windows/lib64/`

### morph 残留散点的成因分析（2026-09-18）

离线在图标实际尺寸（23px）下复现并量化，散点有两个独立来源：

1. **几何无抗锯齿**：morph 走原始三角形路径（无 SDF、无 MSAA 时无任何 AA），1~2px 细笔画在该尺寸下
   边缘碎裂（`tmp/morph_restore/aliasing_compare.png`：直出 vs 6× 超采样降采样对比）。客户端配置无
   `gfx_fsaa_samples`（默认关），实机即此状态。
2. **条带局部交叉**：目标外轮廓是「斜线∪上左眼睑」的**合并外边界**，与内轮廓（眼睑内缘）长度不匹配，
   索引配对会扫掠并局部压扁成亚像素。量化：p=1.0 时 6/64 条、p=0.79 时 2/64 条（`flipped_quads` 指标）。

可选修法（待拍板）：A. 在合并外轮廓的两个凹角处切分、斜线独立成带（端点精确、消除交叉，但细笔画 AA 仍依赖 FSAA）；
B. 保留几何 morph 并按进度叠加 MSDF 图标（笔画始终抗锯齿）；C. 按尺寸分工（小尺寸走交叉淡化，大尺寸走 morph）。

### 已知残留

p=1 的眼窝内部多填约 13% 面积（形状无缺失）。原因是目标的外轮廓是「斜线∪上左眼睑」的**合并外边界**，而其内轮廓只是眼睑内缘，两者长度不匹配，索引配对的条带在斜线段会扫过眼窝内部。反向处理（对内轮廓改用最近点对应）会让**斜线本身缺失**，比内部多填一块更显眼，故取当前方案。若要像素级精确，需在合并外轮廓的两个凹角（斜线与眼睑交界）处切分、把斜线单独作为一条带——成本较高，且输入框图标约 18px，实际不可察。

## 十五、中间帧白色边框：贴图前清空帧格（2026-09-18）

用户实机反馈：动画**中间态**图标外围有一圈白色方框（首末帧正常）。

### 根因（数据，不是渲染）

帧的显示框 `box` 按进度在 eye / eye-slash 两个图标的 box 之间插值，并取 `max(插值, 位图尺寸)`——所以中间帧的 box 比该帧**位图**大 1~3px。这几像素落在贴图之外，采到的是**未清理的图集背景 `(0,0,0,255)`**；而 MTSDF 的 alpha 是真 SDF，`alpha=1` 表示「远在形状内部」→ 着色器 `SignedDistance = Sample.a - 0.5` 解出覆盖率 1 → 沿框边渲染成一圈实色（即白框）。

实测（`tmp/morph_restore/probe_frame_bg.py`，统计框内等于背景色的像素）：

| 对象 | 框内背景像素 | 说明 |
| --- | --- | --- |
| 全部 1533 个静态图标 | **0** | 静态图标的 box 恒等于位图，采不到框外 |
| frame 0 / 7 | **0** | 端点帧 box 等于位图（所以首末帧一直正常） |
| frame 1~6 | **260 / 449 / 622 / 557 / 615 / 444** | box 比位图大 1~3px ← 白框来源 |

### 修复

`qm_build_icon_msdf_font.py::bake_morph_frames()`：贴位图前把整个帧格清成 `(0,0,0,0)`（「远在形状之外」，两种编码下都是透明），框内位图以外的部分因此恒为透明。改动只有一行 + 注释，不影响静态图标（它们的 box 等于位图）。

> 副作用为零：与烘焙前备份逐像素对比，变化仅 **12403 像素**，包围盒正好是 `x 2160..2736, y 2736..2808` 的 8 个帧格；其余单元格逐像素一致。
