## Quick Answer

这些卡顿不是同一个根因，但形态一致：平时工作被推迟到“事件发生的第一帧”同步完成。皮肤切换容易卡，是因为图片解码后的皮肤 sprite 纹理上传和 `RefreshSkin()` / `UpdateRenderInfo()` 合并会落到主线程帧里；文本突然出现容易卡，是因为首次中文 glyph 栅格化、text atlas 更新和 text container 上传都在渲染路径同步发生；切歌或提示音容易卡，是因为未预加载音频走 `LoadOpus()` / `LoadWV()` 时会同步读文件、解码和重采样；UI 偶发卡顿则多来自 section 测量、未缓存 label 和资源/皮肤后台上传同帧叠加。

当前最可疑的共性不是 GPU 算力不足，而是 CPU 侧解码/布局/容器构建 + 主线程提交 GPU 资源的尖峰。声音问题需要拆成两层看：DDNet 官方也有的公共层，是 SDL 音频回调、播放/停止/进度查询共用 `m_SoundLock`，在特定 Windows 音频设备/驱动/系统提示音组合下可能被放大；QmClient 额外叠加层，是 Windows SMTC 切歌时封面纹理释放/上传、媒体岛标题文本和歌词状态机同帧更新。下一步不要只盯 `sound_update`，需要同时给 SMTC 封面上传和歌词 Tick/Render 加耗时证据，才能区分“音频设备/锁等待”还是“切歌带来的 UI/封面/歌词尖峰”。

官方 DDNet issue 没找到一个完全匹配“系统提示音/外部播放器切歌导致客户端卡顿”的报告，但有多条相邻证据支持这个方向不是 QmClient 独有：Discord 语音通话会导致 FPS drops，维护者要求先测量外部回调耗时；`snd_buffer_size` 官方已确认大值会导致声音延迟；Windows 上曾因 SDL2/WASAPI 变化出现声音坏掉；音频设备不可用/热插拔长期有开放 issue；Android 音频问题曾通过按设备播放率重采样方向处理。这些都指向“外部音频/第三方组件/设备后端能影响客户端体验”，但不能单独证明用户当前卡顿就是同一根因。

## Details

### 皮肤切换

用户判断“CPU 上传问题，GPU 倒没啥大问题”基本符合代码形态。图片读取/解码、sprite 切片、CPU atlas/纹理数据准备和 render info 合并都在 CPU 侧或主线程提交侧体现；真正的 GPU 侧绘制不一定重，但 `LoadSpriteTexture()` / `UpdateTextTexture()` 这类提交会把 CPU 和图形后端同步起来。

设置页的皮肤列表已经比普通切换更预算化：有 visible / background 请求、upload limiter、`settings-skin-source` perf 日志和 list drain summary。但如果是实际玩家 skin 切换或新玩家加入时走 `RefreshSkin()`，它可能和文本通知、玩家数据更新同帧发生，表现就是“明明单项不重，但那一帧很卡”。

### 文本突然出现

全屏通知、HUD 通知、好友进服广播、聊天高亮等共同风险是首次出现的中文字符和新文本容器。文字路径不是简单画字符串：要测宽、查字体 fallback、FreeType 栅格化、更新 text texture、生成 quads、上传 text buffer。已有的 settings text cache 只覆盖设置页一部分稳定 label；游戏内突发通知还需要专门的预热或首帧延迟策略。

### 切换音乐和提示音

如果切歌使用的是已加载 sample，`Play()` 本身很轻；如果切歌时才 `LoadOpus()` / `LoadWV()`，那就是同步文件读取、完整解码、重采样，足够造成明显卡顿。DDNet 菜单背景音乐当前更接近前者：`SOUND_MENU` 是启动时加载的普通 soundset，切换背景音乐开关/离线状态主要是 `Enqueue()` / `Stop()`，不是每次重读文件。

用户补充“官方客户端也有”后，公共根因优先级上升：`CSound::Mix()` 是 SDL 音频回调线程，会持有 `m_SoundLock` 遍历 voice；主线程同时在 `Stop()`、`Play()`、`IsPlaying()`、`SetChannel()` 等路径上拿同一把锁。正常机器上这把锁很短，但如果 Windows 音频设备、驱动、省电策略、蓝牙/虚拟声卡、独占模式、系统提示音或其他播放器导致 SDL 回调调度抖动，就可能表现成“别人没反馈、自己很明显”的本机问题。这解释了为什么 Proma 完成提示音或外部播放器切歌会和客户端卡顿相关，即使 QmClient 本身没有同步加载那个系统提示音。

QmClient 额外有一个只在本机开启对应功能时出现的放大器：Windows SMTC / 媒体岛 / 歌词。切外部音乐时，SMTC 后台线程会拿到新标题和封面，但封面真正变成 GPU 纹理是在主线程 `OnUpdate()` 的 `ApplySharedAlbumArt()`；同时 HUD 会展开媒体岛、渲染新标题，歌词状态机会清旧状态、读缓存/映射并发起查询。这条路径不是官方客户端的问题，但会让“官方已有的音频抖动”在 QmClient 上更容易被感知为一帧卡顿。

### 官方 DDNet issue 对照

本轮查了 DDNet 官方 GitHub issues/PR，没有找到完全同款的“系统提示音或外部播放器切歌时客户端卡顿”。最接近的是 #11472：Discord 语音通话导致 FPS drops。它不是音频播放代码本身的 issue，但结构很像：外部程序状态变化或第三方 SDK 回调影响客户端帧时间，维护者也要求先测量具体耗时而不是猜测修复。

音频配置和设备层也有相邻证据。#7229 / #7389 说明官方已经把 `snd_buffer_size` 和可感知延迟关联起来；#1371 是 Windows + SDL2/WASAPI 变更导致声音坏掉的历史案例；#4603 表明 DDNet 当前音频设备初始化/热插拔不是动态完整处理；#8820 表明设备播放率和重采样路径曾真实影响声音表现。这些不能证明用户当前的 Proma 提示音卡顿就是同一 bug，但它们支持把排查重点放在 Windows 音频后端、设备调度、buffer size、外部程序干扰和主线程第三方/媒体状态更新上。

## Next Steps

先做一次带 perf log 的复现矩阵：皮肤切换、纯 ASCII 通知、中文通知、已加载提示音、首次加载提示音、DDNet 背景音乐开关、外部播放器切歌、设置页首进/切 tab/滚动。

声音专项先走无代码 A/B，避免把官方 issue 的相邻线索误当成根因：

1. `snd_buffer_size 1024`，再试 `snd_buffer_size 2048`。如果卡顿减少但声音延迟变大，优先怀疑音频 callback / 设备调度；如果完全无变化，buffer 不是主因。
2. `snd_nonactive_mute 0`。如果后台/切焦点时卡顿变化，说明 focus mute 和音频播放状态切换可能参与。
3. `qm_smtc_enable 0`。如果外部播放器切歌卡顿消失，优先查 QmClient SMTC 主线程更新。
4. `qm_smtc_show_hud 0`。如果 SMTC 开着但关 HUD 后缓解，优先查媒体岛文本/封面渲染，而不是音频后端。
5. 如果启用了歌词，再试 `qm_lyrics 0` 和 `qm_lyrics_auto_fetch 0`。如果只在切歌首帧缓解，优先查歌词 identity 切换、缓存读取和首帧文本测量。
6. Windows 本机可额外开独立进程对比 SDL audio driver：默认 WASAPI vs `SDL_AUDIODRIVER=directsound`。这只作为诊断，不作为默认用户配置建议。

如果 A/B 仍不能归因，再加三类临时诊断：`CSound::Mix()` / `Play()` / `Stop()` / `IsPlaying()` / `SetChannel()` 的锁等待和持锁耗时，`CSystemMediaControls::ApplySharedAlbumArt()` 的封面主线程处理和 texture upload 耗时，`CQmLyrics::TickStateMachine()` / `RenderHud()` 的切歌首帧耗时。确认尖峰归属后，可能的修复路径才分开：音频锁路径要缩短持锁或调整设备/backend 兼容策略；SMTC 封面路径要延迟/预算化上传、限制封面尺寸或复用旧纹理；歌词路径要拆分曲目切换首帧工作、预热文本或限制同步缓存读取；设备热插拔路径则参考 #4603 的 `SDL_AUDIODEVICEADDED` 方向处理。
