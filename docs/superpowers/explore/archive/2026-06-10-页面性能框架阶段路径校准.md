## 速答

当前“页面性能优化 + 量化系统”的大路径已经明确，但需要做一次阶段口径校准：**量化系统已完成，FBO 只应保留为 cleanup 收口阶段，后续真正的主线应该转到基于量化归因的 source cooling。**

建议正式固定为以下顺序：

1. **Phase 1：量化系统生产化** — 已完成，不再重建。
2. **Phase 2：FBO 用户可见问题 cleanup** — 只做 bugfix / 收口，不再作为性能优化主线。
3. **Phase 3：基于量化结果的主线优化** — 先做 `settings:tee / Work Drain`，再做 `server_browser / list_frame`。
4. **Phase 4：局部结构化重构** — 只对已证实热点抽取 helper / 合同，不做统一大 scheduler。

当前最需要修正的不合理点有 3 个：

1. 不能再把 FBO 写成“性能优化主线阶段”。
2. 不能把量化系统、FBO cleanup、source cooling 塞进同一份执行计划。
3. `avg/max/min FPS` 只能做端到端体感对比，不能替代 `Work Drain / List Interaction / UI Rebuild` 归因。

## 结论

当前最合理的正式阶段路径应固定为：

1. **Phase 1 已完成：量化系统生产化**
   当前任务不再重建 `qmclient_scripts/perf` 主干，只把它当作后续优化和回归判断基线。

2. **Phase 2 收口：FBO 用户可见问题 cleanup**
   目标是最小修复或绕开 Settings / TClient / QmClient 预热链路里的用户可见问题，保留 live fallback，不把它包装成性能主线。

3. **Phase 3 主线：`settings:tee / Work Drain` source cooling**
   后续正式 plan 的第一主线应是：减少主线程 merge / publish / drain 与交互帧重叠，而不是继续证明 FBO 命中率。

4. **Phase 4 次主线：`server_browser / list_frame` source cooling**
   紧接着再处理 `rows_iterated` 与 `rows_rendered` 差距过大的 Server Browser 同步列表成本。

5. **Phase 5：其它页面的 source cooling 与局部结构化重构**
   只在前四阶段完成后，再推进 Demo Browser、Assets、Tee 其他路径，以及小范围 helper / 合同抽取。

## 后续建议

1. 下一份正式 plan 应只覆盖一个主线问题，建议直接锁定 `settings:tee / Work Drain`，把 FBO cleanup 作为已知前置收口项引用，不并入主线实现。
2. 如果需要对外说明路径，统一口径应是：`量化系统已完成 -> FBO cleanup 收口 -> Work Drain 主线优化 -> Server Browser 次主线 -> 其它页面 source cooling`。
3. 正式 plan 写完后，执行阶段不要再同时扩展 FBO、Demo Browser 异步化和 Server Browser 列表优化，避免计划重新失焦。
