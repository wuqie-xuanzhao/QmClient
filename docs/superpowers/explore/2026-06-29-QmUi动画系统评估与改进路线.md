> 本文档调研 QmUi (v2) 动画系统的**现有能力**与**真实短板**，评估是否需要引入外部动画/UI 库，并给出增量改进的具体路线。

## 速答

**不需要引入外部动画或 UI 库。** QmUi 的动画引擎已经是一个工程水准较高的自研系统（弹簧物理 + 贝塞尔 + 4 种中断策略 + Motion Level 三级可调），覆盖了游戏 UI 绝大部分动效需求。

当前只需要在现有框架上做**6 个增量补齐**（总量约 600-800 行 C++），而非重写或引入第三方依赖：

| 优先级 | 改进 | 预估代码量 |
|--------|------|-----------|
| P0 | 滚动物理 + scroll container widget | ~200 行 |
| P0 | Layout transition / FLIP 自动动画 | ~150 行 |
| P1 | 进出场动画守卫（AnimatePresence） | ~120 行 |
| P2 | ResolveUiAnimValue 全局 static cache → 实例化 | ~50 行 |
| P2 | OKLAB 感知均匀颜色插值选项 | ~80 行 |
| P3 | 多轨道等待原语（组合完成回调） | ~80 行 |

本轮 review 后补齐的关键修复：

- `AwaitTracks`：取消任意 awaited track 时取消整个 group，并从所有 track 反向索引移除 group，避免其他 track 后续完成时误报 group completed。

- Custom easing：active track 快照注册时的 easing 回调与 `pUser`；`UnregisterCustomEasing()` 只影响未来 track，调用方必须保证已启动轨道使用的 `pUser` 存活到轨道结束。
- 栖梦拖拽开始：不再在 pre-render 阶段用上一帧 `ModuleCards` 命中，改在当前帧布局 `TargetBeforeRender` 上启动拖拽，降低起拖粘滞感。

## 2. 现有能力评估

### 2.1 核心动画引擎（优良）

`src/game/client/QmUi/QmAnim.h`

| 能力 | 现有实现 | 评估 |
|------|---------|------|
| 弹簧物理 | 固定子步长 1/240s，质量/刚度/阻尼，静止检测 + 保持定时器（33ms），Newton 积分 | 对标 iOS Spring 工程水准 |
| 贝塞尔曲线 | Newton-Raphson 迭代求解，8 次迭代 + 1e-5 容差截断 | 正确性有保证 |
| 缓动函数 | LINEAR / EASE_IN / EASE_OUT / EASE_IN_OUT / EASE_OUT_QUART / EASE_OUT_BACK / EASE_IN_OUT_CUBIC / CUBIC_BEZIER | 覆盖常见需求 |
| 命名曲线预设 | STANDARD / EMPHASIZED / DECELERATE / ACCELERATE / BOUNCE_OUT | 设计系统的标准手势 |
| 弹簧预设 | GENTLE / SNAPPY / WOBBLY | 3 种差异化手感 |
| 中断策略 | REPLACE / QUEUE / KEEP_HIGHER_PRIORITY / MERGE_TARGET | MERGE_TARGET 在 UI 框架中不常见，可保障目标跳变时速度连续性 |
| Motion Level | 0=关闭, 1=减少(0.45x 时长, 2x 静止阈值), 2=完整 | 从设计层面支持可访问性 |
| 属性覆盖 | POS_X/Y, WIDTH/HEIGHT, ALPHA, COLOR_R/G/B/A, SCALE | 基本覆盖 UI 动效维度 |

### 2.2 设计令牌绑定（优良）

`src/game/client/QmUi/UiTokens.h`


架构比 CSS transition 声明更清晰：组件语义直接映射到命名曲线，且 Motion Level 全局控制。

### 2.3 动画解决层（及格，有架构 debt）

`src/game/client/QmUi/QmAnimResolve.cpp`

`ResolveUiAnimValue` 提供了一个"声明式"帮助函数：只需传入目标值，自动检测变化、发起 MERGE_TARGET 请求、缓存最新 target。

**历史问题（已修复）**：早期使用 **static 全局 unordered_map** (`s_aLastTargets`) 做 target 缓存，存在跨页面 scope 共享、未来多 runtime 实例不安全、resolve helper 副作用不易归属等问题。本轮已把 target cache 与 color target cache 移入 `CUiV2AnimationRuntime` 实例状态；`ResolveUiAnimValue` 仍是声明式 helper，但缓存生命周期现在跟随 runtime。

### 2.4 渲染桥（简约）

`src/game/client/QmUi/QmRender.h`

只统计 draw call / clip push，不参与动画渲染本身。所有 UI 绘制走 DDNet 上游 `IGraphics` 接口——**无渐变、无描边（stroke）、无模糊（blur/glow）原语**。阴影通过纯色矩形模拟，无法做真正的高斯模糊阴影。

### 2.5 性能跟踪（良好）

`src/game/client/QmUi/QmRt.cpp`

- 分阶段计时：`tree_begin_frame` / `anim_advance` / `render_bridge_begin_frame` / `tree_end_frame`
- 上报：活动动画数、排队动画数、节点数、耗时（ms）
- 可接 perf_logging 体系

## 3. 真实短板与改进路线

### 3.1 P0: 滚动物理

**现状**：所有滚动走 DDNet 上游 `DoScrollbarH` / `DoScrollbarV`。无惯性滚动、无 overscroll bounce、无 scroll snap、无滚动条缓动动画。列表轻扫后"硬停"。

**方案**：自研两层 scroll 引擎
1. 下层：momentum + friction 积分（复用 spring 物理的数值积分器，改摩擦模型）
2. 上层：`ScrollContainer` widget，包裹内容并接管裁剪、滚动条、触摸/鼠标拖拽

**不需要外部库**——物理循环代码量 ~80 行，scroll container ~120 行。

### 3.2 P0: Layout Transition / FLIP

**现状**：元素插入/删除/重排时，位置直接"跳变"。`QmCardOrderModel` 有 drag-reorder 数据模型，但无对应动画。

**方案**：在 `CUiV2Tree` 或 `QmAnimResolve` 层加自动 FLIP（First-Last-Invert-Play）：
- 布局开始前快照所有节点位置
- 布局后 diff
- 对位置发生变化的节点自动发起 POS_X / POS_Y 动画

**为什么不引入外部库**：FLIP 的核心是"前后两帧的 rect diff + 自动发起 tween"，在已有动画引擎上做只是方向变化——不需要 CSS 或 JS 框架。代码量 ~150 行。

### 3.3 P1: 进出场动画守卫（AnimatePresence）

**现状**：节点从 `CUiV2Tree` 移除时立即消失。Modal 和 Toast 的进出各自硬编码，没有通用机制。

**方案**：在 `CUiV2Tree::EndFrame()` 中做"死亡节点延迟移除"：
- 当前帧未 Touch 到的节点标记为 `pending_removal`
- 自动发起 ALPHA→0 或 SCALE→0 动画
- 动画完成后才真正从树中移除
- 新增节点的首次渲染，自动从 ALPHA 0→1

**代码量 ~120 行**，集中在 `QmTree` 改动。

### 3.4 P2: 全局 Static Cache 实例化

**现状**：[QmAnimResolve.cpp:40](file:///e:/Coding/DDNet/QmClient/src/game/client/QmUi/QmAnimResolve.cpp#L40) 的 static unordered_map 是架构 debt。

**方案**：把 target cache 移入 `CUiV2AnimationRuntime` 实例的成员，或移入 `IUiContext`。改动量 ~50 行。

### 3.5 P2: OKLAB 颜色插值选项

**现状**：[QmAnimResolve.cpp:99-107](file:///e:/Coding/DDNet/QmClient/src/game/client/QmUi/QmAnimResolve.cpp#L99) 在 sRGB 空间线性插值。蓝色→绿色过渡中间色偏暗。

**方案**：加 `g_Config.m_QmUiColorInterpolation` 开关：
- `0=Linear-sRGB`（默认，兼容现有行为）
- `1=OKLAB`（感知均匀，中间色不偏暗）

OKLAB 变换只需要 `LinearRGB ↔ OKLAB` 矩阵运算 + gamma 校正，代码量 ~80 行，不需要导入外部库。

### 3.6 P3: 多轨道等待原语

**现状**：每个属性独立 track，`SUiAnimCompleteEvent` 独立发射。没有"等待多个属性动画完成后触发回调"的原语。

**方案**：在 `CUiV2AnimationRuntime` 上加：
```cpp
// 注册一组 trackId，所有都完成时发射事件
uint32_t AwaitTracks(const std::vector<uint32_t> &vTrackIds, SUiAnimCompleteEvent &EventOut);
```

代码量 ~80 行。

## 4. 不建议引入的外部库

| 库 | 不推荐理由 |
|----|-----------|
| **Dear ImGui** | 与 DDNet 上游 UI 系统不兼容，会与现有 QmUi 冲突 |
| **Qt** | 依赖过重，渲染管线不匹配游戏客户端 |
| **Rive** | 运行时 + 文件格式集成复杂，项目中暂无复杂矢量动画需求 |
| **Lottie (rlottie)** | Web/App 向，C++ 集成成本高，不匹配游戏客户端场景 |
| **Tweeny / tween.h** | 单头文件 tween 库，功能完全被现有 QmAnim 覆盖 |
| **glm / Eigen** | 线性代数能力已有 DDNet 自带数学工具覆盖 |

需要 SVG 图标时可以考虑 **nanosvg**（单头文件），但也属于"按需单点引入"，不属于动画/UI 系统改造。

## 6. 总结

现有 QmUi 动画系统的核心引擎已经达到了不需要外部库的水准。本轮已经补齐滚动物理、布局过渡、进出场、runtime cache 归属、颜色插值、多轨道等待、自定义 easing 与 widget 状态动画 helper。当前剩余风险不在代码能力本身，而在栖梦卡片拖拽释放动画的实际视觉手感，需要客户端人工验收。
