# QmClient i18n 系统现状与优化方向调查

## Quick Answer

当前 QmClient 的 i18n 运行时模型很简单：主语言文件先由 `g_Localization.Load(...)` 载入，然后再叠一层 `qmclient/<language>.txt` overlay；`Localize(...)` 在运行时只是把原始字符串和 context 做一次哈希查表，单次成本很低，真正偏重的是“语言文件加载”和“大量渲染路径里重复调用 + 文本容器重建”带来的累计开销，而不是 `Localize` 函数本身。`Localizable(...)` 不是翻译函数，它是一个 `constexpr` 空函数，只用于让提取脚本知道“这串文本将来要进入语言系统”。

把语言文件改成 TOML 从“可维护性”角度可行，但从“运行时性能”角度没有天然优势，反而会把当前极轻量的行解析格式改成更重的通用解析器。如果目标是先统一英文 key，再优化 i18n，优先级应该是：先去掉中文 key / 中文硬编码 / overlay 分叉，再做热点 UI 的本地化缓存与文本池策略优化；TOML 最多算次级工程化议题，不是性能主抓手。

## 核心问题

1. 当前 QmClient 的语言加载链是什么，overlay 是否仍在使用？
2. `Localize(...)` 和 `Localizable(...)` 的实际区别是什么？
3. 当前 i18n 系统的性能瓶颈更可能在哪里？
4. 语言文件改成 TOML、以及“从代码上减少硬编码”分别值不值得做？

## Key Evidence

1. QmClient 运行时仍然使用 overlay 二次加载。`LoadQmClientLanguageOverlay(...)` 把主语言文件名拼成 `qmclient/<lang>` 后再次 `Localization.Load(..., false)`；语言初始化和语言切换时都会执行这条链。

3. `Localizable(...)` 不是运行时翻译函数，而是一个 `static constexpr` 空函数，直接返回传入的 `pStr`。它的存在价值是“标记这串文本会被本地化脚本扫描到”。

## Conclusions

### 1. `Localize` 和 `Localizable` 的区别

- `Localize("key", "context")`
  - 运行时函数
  - 会实际查当前语言数据库
  - 找不到翻译时回退到原字符串
  - 应用于“马上要显示给用户”的文本

- `Localizable("key", "context")`
  - 只是标记函数
  - 运行时什么都不做，直接返回原字符串
  - 主要作用是让扫描脚本把这串文本纳入语言资源
  - 常见于列标题、静态元数据、结构体常量、错误模板等“先声明，后由别处显示”的场景

所以你问“`Localizable` 有啥用”，答案是：它对运行时几乎没用，对“提取语言 key”很有用。它是给工具链看的，不是给翻译查表看的。

### 2. 当前 i18n 系统的性能怎么样

从代码结构看，`Localize` 本身的单次性能损耗很小：

- 2 次 `str_quickhash`
- 1 次有序向量二分查找
- 命中则返回指针，未命中则返回原指针

这不是一个高成本函数。真正值得关心的是三类累计成本：

1. **语言切换 / 初始化加载成本**
   - 当前要先载主语言，再载 QmClient overlay
   - 切语言后还会触发字体 variant 更新、settings cache 失效、文本容器清空

2. **热点 UI 上的重复调用成本**
   - 如果某些 label 每帧反复 `Localize(...)`，调用本身虽然轻，但在大规模 UI 重绘里仍会累计
   - 这类问题通常应该通过“文本容器缓存 / 预热 / stable text key”来解决，而不是改文件格式

3. **多套语言链造成的工程成本**
   - `data/languages/` + `data/qmclient/languages/`
   - 主链路 + overlay + 某些模块私有简中库
   - 这会放大预热 miss、资源漂移和脚本维护成本

### 3. 把语言文件改成 TOML 值不值得

**结论：可以讨论，但不应作为当前统一英文 key 之后的第一优先优化。**

原因：

- 对运行时性能没有明显天然收益
  - 现在的格式是超轻量按行解析
  - TOML 解析通常更重
  - 如果最终还要编译/转换成运行时字典，TOML 只是“源码格式更好看”，不是“运行时更快”

- 会扩大改动面
  - `CLocalizationDatabase::Load(...)`
  - `languages/index.txt`
  - `scripts/languages/twlang.py`
  - `qmclient_scripts/languages_qmclient/*`
  - 所有生成/校验/并回脚本

- 当前主要痛点不是格式表达力不够，而是：
  - 中文 key 未统一
  - 硬编码残留
  - overlay 双轨
  - 运行时存在旁路查简中

如果以后真的要 TOML，更合理的方案是：

- **编辑态 / 源码态** 用 TOML 或其它结构化格式
- **构建产物 / 运行时** 仍编译成当前轻量格式或二进制表

这样才有可能同时兼顾可维护性和运行时成本。

### 4. “从代码上减少硬编码”该怎么理解

这里要区分两种“减少硬编码”：

1. **正确的减少**
   - 把用户可见文案从中文硬编码迁到英文 key
   - 把重复出现的相同 key 收口
   - 把可缓存的文本从每帧拼接改成缓存文本容器
   - 把语言旁路收口到统一主链

2. **错误的减少**
   - 为了“不写字面量”再包一层无意义常量
   - 把简单 key 过度抽象成配置驱动
   - 在没有热点证据时，为 `Localize` 调用做复杂缓存层

当前阶段最值得做的是第一种，不是抽象化。

## 建议顺序

1. 先完成英文 key 统一
   - `Localize("中文")`
   - `Localizable("中文")`
   - 中文 UI 硬编码

2. 再收口语言资源与 overlay
   - 合并回 `data/languages/`
   - 删除 `data/qmclient/languages/`
   - 删除 overlay 加载链

3. 再做 i18n 性能优化
   - 排查热点 UI 的重复 `Localize`
   - 配合文本池 / stable text / 预热策略看 miss
   - 优化语言切换后的缓存失效范围

4. 最后再评估 TOML
   - 作为工程维护性议题，而不是性能议题
   - 如果做，优先考虑“源格式 TOML，运行时仍使用编译产物”
