## 速答

这份最新日志里 `targetSettings.stableTextCoverage.hitRate = 0` 不是 analyzer 凭空算出来的，直接从 raw log 独立复算，`candidateTotal=5172`、`hitCount=0`、`missCount=5172`、`unplannedVisibleCount=3818`、`keyMismatchCount=290` 都能和 summary 对上，说明“0 命中”这个方向本身是真实的。证据链是 `parseLog()` 把 JSON payload 放进 `PerfEntry.fields`，`stableTextCoverage()` 再从 `fields.event/scope/...` 聚合，而不是从别的缓存源取值。`qmclient_scripts/perf/lib/parse.ts:33`, `qmclient_scripts/perf/lib/stats.ts:637`, `qmclient_scripts/perf/lib/stats.ts:836`, `C:/Users/11054/AppData/Roaming/DDNet/dumps/QmClient_Perf/Perf_Report/qm_perf_2026-06-18_15-39-32_summary.json:330`

但“不能全信”的部分也成立：`settings_text_usage` 在这份日志里每条都重复了 2 次，根因是设置页外层 `menus.cpp` 和内层 `menus_settings.cpp` 同时创建了 `CScopedMenuTextVisibleGuard`，导致同一批 per-frame usage counter 在两个析构点各 flush 一次。这样 `candidateTotal=5172` 这类绝对量被放大成了 2 倍，去重后真实 usage 总量是 `2586`，但因为 hits 仍然是 0，所以 hit rate 依然是 `0/2586 = 0%`，比例结论没变。`src/game/client/components/menus.cpp:2895`, `src/game/client/components/menus_settings.cpp:4754`, `src/game/client/components/menus.cpp:4907`, `src/game/client/components/menus.cpp:4929`

因此当前最准确的说法是：这份日志证明了“target settings 会话里的 stable text 没有命中”，但 summary 里的绝对 candidate/miss 数不能被当成无偏统计值。它更像“重复上报后的会话级 coverage 计数”，不是严格单窗口、单帧、单次 visible pass 的真实候选数。

## 细节

### 1. 命中率“真实”的边界

这次不能只看 `summary.json`。独立复算时，必须从 `PerfEntry.fields` 取 `event/scope/page/operation/text_class/candidates/hits/miss/...`，因为 `parse.ts` 的结构就是这么存的。如果像最初误用那样直接访问 `e.event/e.scope`，结果会全变成 0，不是 analyzer 错，而是脚本字段访问错。

这条链路已经确认：

- 原始日志样本里有明确 `settings_text_usage ... hits=0 miss=54`。
- `stableTextCoverage()` 的 `hitRate` 来自 `staticRelevantUsage.reduce(sum + hits) / reduce(sum + candidates)`。
- 最新 summary 里的 `0%` 与 raw log 独立复算一致。

因此，“0 命中”这件事在这份日志里是可信的。

### 2. 为什么绝对量不能全信

`CScopedMenuTextVisibleGuard` 的设计是：

- 构造时重置 `m_MenuTextStableCandidatesThisFrame/hits/misses/...`
- 析构时只要 `candidates > 0` 就 `LogSettingsTextPoolUsage(...)`

而当前设置页路径上有两层 visible guard：

1. 外层菜单页渲染：`menus.cpp` 在 `m_MenuPage == PAGE_SETTINGS` 时创建一层
2. 内层设置内容渲染：`menus_settings.cpp` 在 `!CollectingMenuTextPlan` 时又创建一层

这会导致同一轮可见文本遍历把 usage payload 原样打两次。独立复算结果里，全部 `settings_text_usage` payload 的重复度直方图都是 `2:269`，这是非常强的结构性证据。

所以这份日志的 usage 绝对量应理解为“重复 flush 后的计数”：

- summary 原值：`candidateTotal=5172`
- usage 去重后：`candidateTotal=2586`
- 两者 hit 都是 0，所以 `hitRate` 一样是 0%

`miss` 事件没有这个 2x duplication，说明问题不在 parser，而在 usage telemetry flush 位置。

### 3. 对 5 个性能主题的当前含义

#### 通用文本渲染

当前文本管线已有 `CreateTextContainer()` 和 `perf/text` runtime budget 统计，但它们是“有工作才记账”的阈值日志，不是每帧全量 profile。设置页的 stable text miss 只是文本问题的一部分，通用路径上仍要看：

- text container create/upload
- glyph rasterize/upload
- paragraph layout/cache

#### 文本池命中率

结论分两层：

- 比例层：`0%` 可信，这份 target settings 会话里确实没有 stable text hit。
- 绝对量层：summary 的 candidate/miss 总量被双重 visible-guard 放大了 2 倍，不能直接当真实候选规模。

#### Vulkan / 图形后端

当前仓库不是“没有 Vulkan 优化”，而是“已经有 Vulkan 后端，但缺少围绕 upload/sync 的专项量化”。下一步最值钱的方向是：

- 把 `vkMapMemory` 热点分成 staging/upload/readback 场景
- 避免 frame path 上 `vkQueueWaitIdle` / `vkDeviceWaitIdle`
- 对 fence wait 做更细粒度时间统计
- 把 text/glyph/container upload 和 backend upload 关联起来看

#### QmClient/TClient 的 visible-range / 列表虚拟化

模块/section 级裁剪已经存在：

- TClient/QmClient 都有 `IsSectionVisible()`
- QmClient 还给 glass card 背景补了额外裁剪
- 统一设置页滚动生命周期也已经抽到 `BeginSettingsScrollRegion()` / `FinishSettingsScrollRegion()`

但列表/卡片级别仍不是“全覆盖虚拟化”：

- `SettingsRuntimeCacheAllowsVisibleCompactText()` 仍是 `false`
- 现有 visible-range 主要偏 section/card/background，而不是所有 compact text/list item

#### QmClient/TClient 滚动抖动

当前最可疑的不是“单个卡”，而是滚动事件保障本身：

- `ui_scrollregion.cpp` 的 modifier hack 会强制吞掉 scroll direction / 停掉平滑推进
- TClient 设置页 begin 阶段先读旧 offset，end 阶段才产出最终 offset
- `perf/tclient` stage 没传 `Client()`，使逐帧关联能力比 `perf/qmclient` 弱

这些都符合“滚动时偶发抖动、难对齐到具体 stage”的症状。
