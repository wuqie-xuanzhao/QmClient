# 1. 现象与范围

2026-09-09 18:28 至 18:57，用户在更新 NVIDIA 驱动和 Windows 11 Insider Preview 后观察到：

- Vulkan 关闭垂直同步时撕裂严重，并出现明显掉帧和卡顿；
- Vulkan 开启垂直同步后撕裂减轻，但卡顿仍存在，输入延迟明显增加；
- OpenGL 相比 Vulkan 有改善，但仍然掉帧；
- 偶尔画面完全停滞，随后游戏连接中断。

本调查同时覆盖 Vulkan、OpenGL、Windows 合成/驱动、外部图形注入层、主循环等待和网络泵停顿。当前证据不足以把问题单独归因于 Vulkan、Vulkan 1.4、网络或 QmClient UI。

用户补充：同一台机器上的官方 DDNet、BC 客户端和 QmClient 都出现该问题，而其他机器没有反馈同样现象。该交叉客户端证据显著降低了“QmClient 单独的 renderer bug”作为首要假设的优先级，也意味着 MAILBOX/IMMEDIATE 调整不可能是完整修复。

# 3. Vulkan 1.1、1.3、1.4 在当前代码中的真实差异

当前 `backend_vulkan.cpp` 支持按 `1.4 -> 1.3 -> 1.1` 创建 instance/device，并记录 effective API version。但 `VkDeviceCreateInfo.pEnabledFeatures` 和 `pNext` 当前为空，后端没有因为选择 1.3 或 1.4 自动启用 dynamic rendering、synchronization2、timeline semaphore、descriptor indexing 或 Vulkan 1.4 的其他现代能力。

因此当前三个档位的主要实际差异是：

- instance/device 声明的 API version；
- 设备和 loader 是否接受该版本；
- 驱动和 implicit layer 进入的兼容路径；
- 核心命令/扩展的可见性边界。

它们目前不是三个不同的性能 renderer。若 1.1、1.3、1.4 在同一场景表现明显不同，优先怀疑驱动、loader、implicit layer 或版本协商路径，而不是认为 1.4 已自动使用更现代的 GPU 功能。

# 4. 已确认的代码风险

## 4.1 关闭 VSync 时优先 IMMEDIATE

Windows/Linux Vulkan 在 `gfx_vsync 0` 时按以下顺序选择 present mode：

```text
IMMEDIATE -> MAILBOX
```

`IMMEDIATE` 允许显示器在扫描过程中接收新图像，撕裂是该模式的预期风险。当前严重撕裂不能仅视为驱动回归。首轮修复候选是把无 VSync 的默认顺序改为 `MAILBOX -> IMMEDIATE`，但必须先确认帧延迟、刷新率和窗口模式下的实际结果。

该调整只属于显示策略优化，不是本次跨客户端卡顿的主修复。因为官方客户端、BC 和 QmClient 也复现，必须先完成机器级证据采集；不能用 present mode 改动掩盖共同环境问题。

## 4.2 VSync 的延迟与卡顿

开启 VSync 后优先 `FIFO`。当前架构的 graphics thread 只有一个待处理 command buffer 槽；`CGraphicsBackend_Threaded::RunBuffer()` 在提交下一批前调用 `WaitForIdle()`。如果 render thread 在 acquire、fence、present 或驱动内部阻塞，主线程会在后续 `graphics_swap` 被反压。

这可以解释 VSync 下输入延迟增大，也说明 `graphics_swap` 高耗时不等于纯 GPU 着色耗时。

## 4.3 网络泵与渲染等待位于同一主循环

`CClient::Update()` 每个主循环调用一次 `PumpNetwork()`，随后才进入 render/swap。若主线程长时间阻塞在 graphics swap、驱动调用或同步等待，网络收包和 `CNetClient::Update()` 也不会推进。足够长的停顿可能先表现为画面冻结，随后触发 snapshot gap、too weak connection 或 timeout。

因此“连接中断”可能是长时间进程/图形停顿的结果，而不一定是网络根因。现有 10 秒 hang watchdog 能记录主循环完全停止，但 1 至 9 秒的严重停顿仍可能影响连接且不会生成 hang report。

## 4.4 Vulkan profiling 缺口

现有 verbose Vulkan profile 已记录 fence wait、queue submit、queue/device wait 和 GPU timestamp，但没有单独记录：

- `vkAcquireNextImageKHR` 墙钟时间；
- `vkQueuePresentKHR` 墙钟时间；
- graphics thread command-buffer backpressure 等待；
- present mode、swapchain image count 和 Windows 窗口/合成状态的每会话 metadata；
- 同一时间窗口的 network pump、snapshot age 和 hang heartbeat gap。

没有这些字段时，无法区分 acquire/present、GPU fence、render thread backlog、CPU render、外部注入层和网络停顿。

# 5. 当前假设排序

1. **外部注入层与新驱动/Insider 系统组合问题。** Vulkan Loader 已发现多个 1.3 implicit layer；OpenGL 历史崩溃也加载了 OBS、GamePP、NVIDIA Overlay，并落在 NVIDIA 驱动。
2. **Vulkan IMMEDIATE present 导致撕裂。** 这是代码可直接证明的行为，但不能解释 OpenGL 掉帧和连接中断。
3. **驱动或 present/acquire 长停顿通过 graphics thread 反压主线程。** 可同时造成 Vulkan/OpenGL 掉帧、画面冻结和网络泵停顿。
4. **QmClient Vulkan 后端既有状态/生命周期缺陷。** render pass、command buffer 状态缓存和 render target 问题仍需修复，可能放大驱动差异。
5. **Windows 11 Insider build 29648 或 NVIDIA 620.02 回归。** 需要与稳定 OS/旧驱动或官方 DDNet 对照，当前无法仅靠源码确认。
6. **纯网络问题。** 目前优先级较低，因为掉帧同时影响两个图形 API，且连接中断前出现画面完全停滞；仍须用 packet/snapshot 时间线排除。

# 6. A/B 复现矩阵

每组使用同一地图、窗口模式、分辨率、刷新率、相机路径和客户端配置，至少运行 3 分钟；出现完全停滞时保留日志和 hang/crash dump。

| 组 | Backend | API | Present/VSync | 注入层 |
| --- | --- | --- | --- | --- |
| A | Vulkan | 1.4 | VSync off | 全部关闭 |
| B | Vulkan | 1.3 | VSync off | 全部关闭 |
| C | Vulkan | 1.1 | VSync off | 全部关闭 |
| D | Vulkan | 1.4 | VSync on/FIFO | 全部关闭 |
| E | OpenGL | 当前版本 | VSync off | 全部关闭 |
| F | OpenGL | 当前版本 | VSync on | 全部关闭 |
| G | Vulkan/OpenGL | 与无层基线相同 | 相同 | 逐个恢复 NVIDIA Overlay、OBS、GamePP、Steam、ReShade |

首轮不同时改变 API、VSync、限帧、窗口模式和注入层，避免无法归因。ReShade manifest 指向缺失 DLL，应先移除或通过其 `DISABLE_VK_LAYER_reshade_1=1` 对照；GamePP 和 OBS 使用各自 manifest 声明的 disable environment。不要删除 registry 项作为第一步。

# 7. 需要补充的诊断实现

实现前先增加低开销观测，不直接猜测性能修复：

1. Vulkan 记录 acquire、image-fence wait、command record、queue submit、queue present 的独立墙钟时间。
2. `CGraphicsBackend_Threaded::RunBuffer/WaitForIdle` 记录主线程等待 render thread 消费上一批命令的时间。
3. 每个图形会话记录 effective Vulkan API、driver、OS build、present mode、swap image count、窗口模式、刷新率和已发现工具层。
4. 卡顿窗口关联 `graphics_swap`、`client_update/PumpNetwork`、snapshot age、recv packet delta 和 hang heartbeat gap。
5. 将 hang watchdog 增加轻量级 1 秒以上 stall breadcrumb；10 秒才写 dump 的策略可保留。

## 7.1 日志分层要求

当前 `qm_perf_debug 1` 通过 `QmPerfEnabled()` 同时打开主循环、render、input、UI、菜单、资源、文本和图形相关阶段；`qm_perf_logfile 1` 也会让这些阶段进入同一个文件。该设计适合长期性能趋势，不适合驱动回归定位，容易产生 GB 级日志并掩盖真正的等待点。

后续应增加独立的图形诊断级别，不改变现有长期性能日志语义：

当前配置按作用域分为三类：

| 类别 | 配置项 | 作用 | 体积/用途 |
| --- | --- | --- | --- |
| 通用日志 | `logfile`、`debug`、`ec_output_level` | 控制基础日志目标与全局详细度 | 长期运行；不用于帧级采样 |
| 性能/业务 | `qm_perf_debug`、`qm_perf_logfile`、`qm_perf_debug_threshold_ms`、`qm_perf_stutter_diagnostics`、`qm_ui_runtime_v2_debug` | 主循环、UI、资源、文本和卡顿业务指标 | 适合组件归因；开启后可能高体积 |
| 图形/平台诊断 | `qm_graphics_trace` | backend、swapchain、GPU/CPU 等待和平台捕获；macOS signpost 也归入此级别 | 短时复现；独立 `perf/graphics/*` 通道 |

`qm_graphics_trace` 已落地为 0-3 级独立开关，不再由 `qm_perf_debug` 隐式开启 Vulkan backend 采样。旧的 `qm_macos_graphics_diagnostics` 保留为兼容别名，会被提升为至少一级图形 trace，不再维护第二套语义。`qm_perf_logfile 1` 仍负责把 `perf/*` 路由到专用文件；图形 trace 开启时也会自动创建该文件。

当前已实现的采样范围：Vulkan 的设备元数据、acquire/fence/submit/present/GPU timestamp、OpenGL 的上下文元数据与慢 `SDL_GL_SwapWindow`、渲染线程 `WaitForIdle` 反压，以及主循环 `PumpNetwork` 的执行耗时和两次调用间隔。网络采样只在 `qm_graphics_trace>=2` 且出现 8 ms 执行耗时或 100 ms 间隔时写入 `perf/graphics/network`；线程反压写入 `perf/graphics/thread`。

```text
qm_graphics_trace=0 关闭图形细分
qm_graphics_trace=1 每 120 帧图形摘要：API、present mode、swapchain、GPU/CPU 总时间
qm_graphics_trace=2 摘要 + acquire/fence/submit/present 分项；8 ms 以上写单帧异常
qm_graphics_trace=3 在级别 2 基础上允许详细 backend/validation 辅助信息，仅用于短时复现
```

图形诊断应写入独立文件或独立 `system`，而不是强制打开所有 `perf/*` 阶段。默认阈值建议为 8 ms；异常帧才记录完整上下文。单次采集目标是数十 MB，而不是数 GB。

在该分层完成前，最小采集方式是只开启 `qm_perf_debug 1` 的短窗口，复现后立即关闭；同时避免长时间运行设置页资源预览、文本生成和后台资源扫描路径。

## 7.2 QmClient 本机采集包

官方 DDNet 和 BC 的共同复现只作为外部归因证据；本项目不实现它们的日志适配或采集协议。QmClient 自身需要定义稳定的 machine/session metadata，用于把本机图形、主循环和网络时间线对齐：

```text
timestamp_utc
os_build / display_driver
gpu_name / pci_id / driver_version
monitor_id / refresh_hz / hdr / gsync_freesync
window_mode / drawable_size / dpi
backend / api_version / present_mode / swapchain_images
overlay_layers / capture_hooks
frame_cpu_ms / gpu_ms / acquire_ms / fence_wait_ms / present_ms
queue_submit_ms / render_thread_wait_ms
network_pump_gap_ms / snapshot_age_ms / recv_packets_delta
```

采集分三层，避免把高体积业务日志带入机器诊断：

1. **Machine layer**：OS build、驱动、显示器、DWM/overlay/hook、GPU 电源和系统事件；由一次机器诊断包提供。
2. **Present layer**：每帧或异常帧的 acquire、submit、present、fence、GPU timestamp、backpressure；由各客户端图形后端提供。
3. **Game/network layer**：主循环、`PumpNetwork`、snapshot age、连接状态和 hang breadcrumb；由 QmClient 提供。

QmClient 只需输出短时窗口和统一 CSV/JSONL 字段，随后按 `timestamp/session/frame` 对齐本机事件。这样不需要用户为每一个 Vulkan 版本和 present mode 重复跑长时间 A/B。

# 8. 修复决策门

- 无注入层后 Vulkan 撕裂仍存在：验证 `MAILBOX -> IMMEDIATE` 默认顺序和可配置 present mode。
- 无注入层后 Vulkan 卡顿消失：不先修改 renderer，增加工具层诊断和用户可见提示，逐层定位冲突者。
- Vulkan 1.4 卡顿而 1.3/1.1 正常：检查 instance API 与 implicit layer/driver 兼容路径；不能把结果描述成 1.4 GPU 功能回归，因为当前未启用这些功能。
- 官方、BC、QmClient 在同一时间窗口都有相同卡顿：将机器/驱动/DWM/overlay 作为首要调查面；QmClient 只修复能由自身日志和调用链证明的等待或生命周期问题。
- 只有 QmClient 的 `present_ms` 或 `render_thread_wait_ms` 异常：再进入 QmClient backend 修复；不能因其他客户端“感觉较轻”就排除系统层，只能以对齐后的时间线判断。
- Vulkan/OpenGL 都在 graphics-thread wait 处长停顿：处理 render thread backpressure、driver stall 隔离和主循环网络推进问题。
- GPU 时间正常但 frame/loop 时间异常：转查 CPU 组件、系统调度、hook 和日志/后台任务。
- 画面冻结时 network recv 仍正常：连接中断不是网络收包饥饿，需要继续检查客户端状态机和 socket 错误。

# 9. 与 GPU-driven 2D 架构的关系

本问题是 GPU-driven 2D 架构 P0 的阻断项。persistent upload、indirect draw、render graph 和 compute culling 都会增加同步与资源生命周期复杂度。在 present、render-thread backpressure、外部 layer 和网络泵关联未建立可靠诊断前，不应把新架构默认开启，也不能用大规模重写掩盖当前回归。

GPU-driven 实施可以继续进行 API-neutral 合同和测试设计，但首个运行时代码批次必须先完成本调查的诊断字段和无注入层 A/B 基线。

# 10. AMD 与 macOS 的专项边界

## 10.1 AMD

当前 QmClient 曾因分身小窗动态 viewport 崩溃，对 AMD 采用过厂商级强制单线程规避。现有证据只能证明当时某条小窗/viewport 路径存在 AMD 风险，不能证明 AMD Vulkan 多线程普遍不可用，也不能证明所有 AMD 驱动都需要单线程。

AMD 设备的日志必须额外记录：

- vendor/device/revision、驱动版本和 Vulkan effective API；
- 实际 render thread 数、secondary/primary command buffer 模式；
- viewport/scissor 更新、render pass 切换和 command buffer restart；
- queue/fence/present 等待，以及是否触发 AMD workaround；
- 小窗、强制宽高比、背景捕获、readback 和跨批次绘制的场景标记。

验证顺序应为“保留 workaround 的稳定基线 -> 修复应用侧 pass/状态问题 -> 同一设备逐步恢复 2/3 线程”，不能直接删除 AMD 限制。没有 AMD 真机和驱动版本证据时，不得把 NVIDIA 或 macOS 的结论外推到 AMD。

## 10.2 macOS

macOS 当前主路径是原生 Metal；Vulkan/MoltenVK 已不再作为默认路径。Metal 后端已经具备比 Vulkan 更完整的诊断计数，包括 frame slot wait、drawable acquire 次数/耗时、drawable unavailable、GPU completion wait、GPU execution timing、command processing、upload/readback、display sync、maximum drawable count 和 `presentsWithTransaction`。

macOS 的 machine/present 采集应额外记录：

- macOS 版本、Apple GPU family、Metal feature set、外接显示器和 ProMotion/刷新率；
- `CAMetalLayer.displaySyncEnabled`、`allowsNextDrawableTimeout`、`maximumDrawableCount`、`presentsWithTransaction`；
- `nextDrawable()` 等待、frame slot semaphore、command buffer status 和 GPU completion；
- 窗口切换、睡眠唤醒、HiDPI resize、后台/前台和外接屏变化。

Metal 不能简单套用 Vulkan 的 present mode 结论：它没有 `MAILBOX/IMMEDIATE` 同名选择，卡顿更应从 drawable 池耗尽、frame slot 等待、command buffer 完成时间和系统显示同步判断。已有 `perf/macos_metal` 每 120 帧摘要可以作为基础，但还需要统一字段名，以便和 Vulkan/OpenGL/官方客户端日志对齐。

macOS 验证必须使用原生 Metal 真机和 GPU capture；Windows Vulkan、MoltenVK 或 OpenGL 的结果不能替代 Apple 设备证据。
