## 详细发现

### 1. `extract_placeholders` 对 `%%` 匹配不完整 [必须修复]

`translate_with_local_http.py:512` 的正则：

```python
r"%(?:\d+\$)?[+#0\- ]?(?:\d+|\*)?(?:\.\d+|\.\*)?[hljztL]*[diuoxXfFeEgGaAcspn%]"
```

末尾字符类包含 `%`，因此 `%%` 被整体匹配为一个占位符。`system_prompt.md` 明确把 `%%` 列为需要保留的占位符（C printf 转义百分号）。

**失败场景**：源文为 `100%%`（表示显示 `100%`），译文被改成 `100%`，`extract_placeholders` 对两边各自提取出 `["%"]`，比较结果相等，不会触发 placeholder mismatch，质量检查漏报。

**修复建议**：把 `%%` 作为转义序列单独识别（在 `extract_placeholders` 结果中把成对的 `%%` 折叠为单一转义标记），或改用更严格的正则确保 `%` 只能作为 `%` 格式说明符的末尾、不能与另一个 `%` 拼成 `%%` 后再被当作普通占位符。

### 2. JSON 翻译输出校验分支冗余且不可达 [必须修复]

`parse_translation_output`（`translate_with_local_http.py:769-811`）先尝试 `json.loads`，成功且是数组时进入 `if isinstance(payload, list)` 分支：

- 若 `len(payload) == len(tasks)` 且每个元素都有 `translation` 字符串 → 进入顺序校验循环（783-798 行）；
- 否则才 fallback 到 `validate_json_translations`（799 行）。

**问题**：当 JSON 数组长度正确、每个元素都有 `translation`，但 `key`/`context` 顺序错乱时，函数在第 785-788 行报 `unexpected identity order` 并丢弃全部结果。而 `validate_json_translations` 中更宽松的"unexpected identity returned"逻辑（701 行）实际上永远不会被触发——因为顺序校验分支已经把整个数组判定为失败。

两份校验逻辑职责重叠，维护成本高。**修复建议**：统一为单一校验入口，移除 `parse_translation_output` 内的顺序校验循环，全部交给 `validate_json_translations` 处理（它已经能正确处理身份匹配和乱序）。

### 3. 生成产物排序不稳定 [建议修改]

`extract_strings.py:37-47`：

```python
unique_identities = sorted(
    {(record.key, record.context) for record in records},
    key=lambda item: (item[1].casefold(), item[0].casefold()),
)
```

用 set 去重后排序。当两个 key 的 casefold 相同（如 `"Classic next"` / `"Classic Next"`）时，stable sort 会保留 set 的迭代顺序，而 set 的迭代顺序在不同运行间不保证稳定。

`generate_all.py:165-168` 的 `write_language_file` 也经历 stable sort，输入来自 `read_strings()`（83-92 行），后者同样用 set 去重后再 sort，同样不稳定。

**实际证据**：运行 `extract_strings.py` + `generate_all.py` 后，`data/languages/*.txt` 和 `extracted_strings.txt` 都出现了大量大小写 key 位置互换的无意义 diff（例如 `Classic next` ↔ `Classic Next`、`Receive rate` ↔ `Receive Rate`、`Send Rate` ↔ `Send rate` 等），translations 内容完全不变。

**修复建议**：在排序键中，casefold 相同处再加一个确定性 tiebreaker（如原始 key 的码点序），确保"相同输入 → 相同输出"。

### 4. i18n commit 范围蔓延 [建议修改]

`feat(i18n): 完善多语言维护和通知栏文案` 的 commit message 中混入了大量非 i18n 内容：

- `src/game/client/components/menus.h:2051-2075`：新增 `SSettingsScrollRegionFrame`、`SSettingsUiBudgetFrame`、`BeginSettingsScrollRegion` / `FinishSettingsScrollRegion` / `LogSettingsUiBudget` 等设置页滚动和预算结构体；
- `src/game/client/components/menus_settings.cpp:2118`：引入 `SResourcePreviewTelemetry TeePreviewTelemetry` 和皮肤预览遥测（`menus_settings.cpp:2464-2471` 的 perf log payload）；
- `menus_settings.cpp:4459-4506`：重写语言选择页的滚动区域逻辑（`BeginSettingsScrollRegion` / `FinishSettingsScrollRegion`）；
- `src/test/qmclient_monitoring_test.cpp`：新增约 700 行测试，检查 settings perf window、assets upload budget、TClient section height consistency、settings_ui_budget telemetry 等，与翻译无关。

这些改动本身可能已通过构建和测试，但混在同一个 i18n commit 中违反了"一次只处理一个功能"的原则，导致审查、回滚和 cherry-pick 困难。**建议**：拆分到独立 commit，i18n commit 只保留文案接入和翻译维护源/产物改动。

### 5. UiDogfood 渲染中重复 Localize [建议修改]

`src/game/client/QmUi/UiDogfood.cpp:121`：

```cpp
const char *apTabLabels[] = {Localize("Overview"), Localize("Forms"), Localize("Data")};
```

每次渲染都在 lambda 内创建局部数组并调用 `Localize` 三次。虽然 Localize 返回持久指针、安全，但低效。建议把静态标签数组声明为 static 或在渲染函数入口一次性初始化。

`UiDogfood.cpp:130`：

```cpp
str_format(aLabel, sizeof(aLabel), Localize("Item %d"), i + 1);
```

把翻译后的字符串作为 `str_format` 格式模板。`language_quality_failure` 会校验占位符一致，但这是一个潜在风险点：翻译人员若错误修改占位符（如把 `%d` 改成 `%s`），会在运行时触发未定义行为。建议在 prompt 和质量检查中强化对格式说明符的约束。

### 6. `extract_digits` 排序键健壮性 [建议修改]

`translate_with_local_http.py:519-526`：

```python
def extract_digits(text: str) -> list[str]:
    digits = re.findall(r"\d+(?:\.\d+)?", text)
    word_digits = {"five": "5"}
    for word in re.findall(r"\b[a-zA-Z]+\b", text):
        digit = word_digits.get(word.lower())
        if digit is not None:
            digits.append(digit)
    return sorted(digits, key=lambda value: (float(value), value))
```

`sorted(..., key=lambda value: (float(value), value))` 假设所有元素都能被 `float()` 转换。`word_digits` 只处理了 `"five"`，若未来扩展为 `"1,000"` 或 `"0xFF"` 等会触发 `ValueError`。建议添加异常处理或限制排序键。

### 7. 其他维护性问题 [建议修改 / 仅供参考]

- `i18n_store.py:194-206`：`_parse_assignment_value` 在函数内 `import tomllib`，应提升到模块顶部。
- `generate_all.py:161-178`：`write_language_file` 不再读取旧 `simplified_chinese.txt` 做合并，完全以 TOML 为唯一真相源。这是有意为之，但行为变更未在注释中说明；如果有人在 `data/languages/*.txt` 上手动修改会被静默覆盖。建议加注释。
- `chinese_text_style.py:46`：`normalized.replace("QQ 群", "QQ 群")` 是无操作（前一行通用规则已产生 `QQ 群`），可删除。
- `extract_strings.py:27-30`：`classify_string` 返回 `"needs_review"` / `"key_or_non_zh"` 但 `main()` 从未调用，属于死代码。
- `local_http_client.py:43-56`：`extract_response_text` 在 `reasoning_content` 存在时抛出 `ValueError`，但某些 API 可能同时返回 `content` 和 `reasoning_content`，此时会忽略有效内容。
- `SAME_SOURCE_ALLOWED_BY_LANGUAGE`（`translate_with_local_http.py:29-318`）：各语言白名单硬编码 200+ 字符串，建议改为从 `terminology.toml` 中标记"跨语言同形词"的数据驱动方式。

## 正面评价

- **测试覆盖率高**：78 个单元测试覆盖翻译、生成、审计、TOML patch、中文排版等核心路径，且全部通过。
- **TOML patch 设计精巧**：`patch_module_store` 只重写被修改的 message block，保持未改动块的格式和注释，避免全量重写导致的 diff 噪音。
- **审计分类体系成熟**：`source_keys.py` 通过 `_looks_like_business_literal` 和 `_line_looks_like_business_data` 将大量非 UI 字符串自动归类为 `business_data`，显著降低人工 review 负担（`needs_review: 0`）。
- **语言质量检查实用**：`language_quality_failure` 包含占位符匹配、数字匹配、韩文/日文/俄文脚本检测、繁体中文简化字检测，能有效拦截 LLM 的常见问题。
- **提示词工程到位**：`system_prompt.md` 明确约束输出格式、占位符保留、术语表引用和排版规则。
- **文档同步及时**：`AGENTS.md`、`CLAUDE.md`、`verification.md`、README、scripts_overview 都同步更新了多语言 draft → 审核 → 回填流程，明确了 TOML 为唯一真相源。
- **HUD notification rules 重构干净**：把 `ShouldExcludeSystemNotification` 中内联的长串 `str_startswith` 拆分为 `IsHelpOrExampleServerMessage` / `IsBasicInfoServerMessage` / `IsJoinOrLeaveBroadcast`，可读性显著提升。

## 建议

1. **修复 `extract_placeholders` 对 `%%` 的匹配**，确保转义百分号在质量检查中被正确识别。
2. **合并 `parse_translation_output` 和 `validate_json_translations`** 的 JSON 校验逻辑，消除重复和不可达分支。
3. **稳定 `extracted_strings.txt` 和 `data/languages/*.txt` 的排序**，避免无意义 diff——在 casefold 相同处加确定性 tiebreaker。
4. **将 i18n commit 中混入的性能/设置页改动拆分到独立 commit**，遵循"一次只处理一个功能"。
5. **考虑把 `SAME_SOURCE_ALLOWED_BY_LANGUAGE` 改为数据驱动**，例如从 `terminology.toml` 中标记"跨语言同形词"。
6. **为 `extract_digits` 添加防御性排序**，避免未来扩展英文数字词时触发 `ValueError`。
7. **补跑 testrunner 子集**（`QmHudNotifications.*`、`QmHudNotificationRules.*`、`QmClientMonitoring.*`、`SettingsWarmup.*`），确认 C++ 侧回归。

## 结论

本轮 i18n 改动在功能上达到了 12 语言维护体系的目标，翻译覆盖和验证流程完备，可以合并。但合并前强烈建议至少修复第 1、2 条（必须修复），并处理第 3 条（排序稳定性），否则会在每次 `extract + generate` 后产生无意义 diff，长期影响产物可复现性。第 4 条（commit 拆分）不影响功能，但影响代码可维护性和审查效率，建议在后续整理时处理。
