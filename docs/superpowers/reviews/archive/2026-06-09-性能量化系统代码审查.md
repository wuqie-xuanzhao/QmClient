### 影响范围

系统是一个**本地分析工具**，读取游戏客户端生成的性能日志 (`qm_perf_*.log`) 并生成自包含 HTML 报表。不修改游戏行为。

- **TS → TS**：`parse.ts` → `stats.ts` → `report.ts` → `analyze.ts`（清晰的数据流管道）
- **C++ → TS**：C++ 客户端通过 `dbg_msg("perf/*", ...)` 写入日志，TS 解析器读取；格式合同通过 C++ 测试 `qmclient_monitoring_test.cpp` 验证
- **无外部 API 依赖**（除 ECharts CDN 用于图表渲染）

## 总结

审查了当前分支的性能量化系统（6 个 TypeScript 文件 + 1 个 C++ 测试，约 600+ 行新增代码）。整体架构良好：解析、统计、报表三层分离清晰，统计方法选用得当（nearest-rank 百分位、Tukey 箱线图、Silverman KDE、Abramowitz & Stegun 正态逆 CDF），HTML 输出有论文式排版和高交互性可视化。**主要风险**在于判定阈值与 KPI 卡片阈值之间存在不一致，以及采样偏差检测使用了与系统默认配置不同的阈值——这可能导致报告显示自相矛盾的结果。

## 详细发现

### Finding 1: KPI 卡片阈值与判定阈值不一致

- **严重程度：** [建议修改]
- **位置：** `qmclient_scripts/perf/lib/report.ts:269-270`，对比 `qmclient_scripts/perf/lib/stats.ts:493-496`
- **问题：** KPI 卡片对 p99 使用阈值 `(16, 33)` 做三态着色（≤16 OK, 16--33 warn, >33 bad），而判定逻辑使用帧预算阈值 `(16.67, 33)`：

`report.ts` KPI 卡片：
```typescript
kpiClass(p.p99, 16, 33)   // ≤16 = OK, 16-33 = warn, >33 = bad
```

`stats.ts` 判定：
```typescript
if (p.p99 >= 33 || spikeCount >= 5) return 'FAIL';
if (p.p99 >= 16.67 || spikeCount >= 1) return 'WARN';
return 'PASS';
```

- **失败场景：** p99 = 16.5ms 时，KPI 卡片显示 warn（橙色，因 > 16），但判定横幅显示 PASS（绿色，因 < 16.67）。用户会看到自相矛盾的信号。
- **修复建议：** 将 KPI 卡片阈值统一为 `BUDGET.h60` (= 16.67)：

```typescript
kpiClass(p.p99, BUDGET.h60, 33)   // 与 computeVerdict 对齐
```

同理，"Max" KPI 卡片第二个阈值为 `999`，使 "bad" 状态在实际上不可达--建议用有意义的阈值（如 2x 60Hz 预算=33ms）或移除三态。

### Finding 2: 采样偏差检测使用错误阈值

- **严重程度：** [建议修改]
- **位置：** `qmclient_scripts/perf/lib/stats.ts:81`
- **问题：** 系统默认采样阈值是 **4ms**（配置项 `qm_perf_debug_threshold_ms 4`），但 `isSamplingBiased` 使用 **4.17ms**（240Hz 预算）做判断：

```typescript
export function isSamplingBiased(durations: number[]): boolean {
  if (durations.length === 0) return false;
  return inferSamplingThreshold(durations) > BUDGET.h240;  // > 4.17ms ?
}
```

- **失败场景：** 当采样阈值为 4ms 且 p5 = 4.1ms 时（超过一半样本高于阈值），偏差检测不会触发（4.1 < 4.17），导致对采样偏差的**漏报**——报表不显示采样偏差警告，用户被误导以为看到的是完整帧分布。
- **修复建议：** 使用系统实际默认值 4ms，或更好的做法是将 `qm_perf_debug_threshold_ms` 作为参数传入：

```typescript
const SAMPLING_THRESHOLD_DEFAULT_MS = 4;

export function isSamplingBiased(durations: number[], thresholdMs = SAMPLING_THRESHOLD_DEFAULT_MS): boolean {
  if (durations.length === 0) return false;
  return inferSamplingThreshold(durations) > thresholdMs;
}
```

### Finding 3: 使用总体标准差而非样本标准差

- **严重程度：** [仅供参考]
- **位置：** `qmclient_scripts/perf/lib/stats.ts:31`
- **问题：** 方差计算除以 `n`（总体标准差），而非 `n-1`（样本标准差）：

```typescript
const variance = sorted.reduce((sum, v) => sum + (v - avg) ** 2, 0) / n;
const std = Math.sqrt(variance);
```

- **分析：** 对于帧时间分析而言，本次 session 的所有帧构成**总体**，因此除以 n 在统计上是正确的选择。但同一个 `calcPercentiles` 在 `kde`（Silverman 带宽）和 `qqNorm` 中也被复用计算标准差，这些场景的统计假设可能不同。选择总体标准差不会造成实际伤害，但值得在代码中加注释记录选择理由。
- **修复建议：** 在 `calcPercentiles` 的 `std` 计算上方添加注释：

```typescript
// 使用总体标准差（除以 n）：所有帧时间构成完整总体，不做样本推断
const variance = sorted.reduce((sum, v) => sum + (v - avg) ** 2, 0) / n;
```

### Finding 4: 空数据的合规率返回 100%

- **严重程度：** [仅供参考]
- **位置：** `qmclient_scripts/perf/lib/stats.ts:54-58`
- **问题：** 当从没有帧时间条目的日志调用 `complianceRate` 时，返回 100%：

```typescript
export function complianceRate(values: number[], budgetMs: number): number {
  if (values.length === 0) return 100;  // ← 0 帧 = 100% 合规？
  ...
}
```

- **失败场景：** 日志仅包含 `perf/interaction` 和 `perf/device` 事件（无 `perf/menu` 帧时间条目）。报表中的 KPI 卡片会显示所有刷新率合规率均为绿色 100%，而实际上没有可评估的帧数据。
- **修复建议：** 返回 `NaN` 并在 KPI 卡片中渲染为 "N/A"：

```typescript
if (values.length === 0) return NaN;
```

### Finding 5: `report.ts` 章节编号逻辑脆弱

- **严重程度：** [仅供参考]
- **位置：** `qmclient_scripts/perf/lib/report.ts:328-452`
- **问题：** 当 `pages.length > 1` 时触发分支，改变后续所有章节的编号：

```
条件 pages.length > 1 ?
  是 → §5="页面级耗时分解", §6="尖峰帧详细分析", §7="页面性能归因", ...
  否 → §5="百分位分析",    §6="尖峰帧详细分析",  ...
```

如果未来在两个分支之间或之前新增一个章节，开发者需要在多处手动重编号。对于自包含 HTML 报表不是 bug，但这种模式容易因疏忽导致编号跳号或重复。
- **修复建议：** 使用计数器变量或章节数组驱动渲染：

```typescript
let sectionNum = 5;
// renderSection(++sectionNum, '标题', content);
```

### Finding 6: 边界情况测试缺口

- **严重程度：** [仅供参考]
- **位置：** `qmclient_scripts/perf/test.ts`
- **问题：** 当前 10 个测试用例覆盖良好（解析、事件分类、归因、快照、对比、偏差检测、Section Top-10），但以下边界情况未覆盖：
  - 空日志文件（0 条有效条目）
  - 全相同帧时间（如所有帧均为 8.33ms — 此时标准差=0, KDE 带宽退化为 1）
  - 合成大数据集（验证 `qqNorm` 的采样节流和性能）
  - `parseLine` 中畸形 JSON 行与畸形 KV 行的对比
  - `entryDurationMs` 中非数字 `dur_ms` 值（如 `dur_ms=unknown`）
- **修复建议：** 按优先级补测试：
  1. 首先补空日志测试（最可能在生产中暴露问题的场景）
  2. 其次补全相同值测试（标准差=0 的 KDE/QQ 退化）

## 值得肯定的方面

1. **清晰的功能分离** — 解析（`parse.ts`）、统计（`stats.ts`）和报表（`report.ts`）模块独立，职责边界明确，数据流单向可预测。

2. **统计方法严谨** — 恰当选用了多种统计方法：
   - 最近秩法百分位（nearest-rank）
   - Tukey 箱线图（1.5×IQR 围栏）
   - Silverman 经验法则用于 KDE 带宽
   - Abramowitz & Stegun 有理逼近用于正态逆 CDF
   - Hazen 绘图位置用于 QQ 图

3. **HTML 注入防护** — `escapeHtml` 在所有日志内容插入 HTML 之前一致应用，无 XSS 风险。

4. **自我意识充分** — 报告明确警告：
   - Session 对比"不作为严格回归判定"
   - 采样偏差检测并高亮提示
   - Section 覆盖范围标记为不完整

5. **C++/TS 合同验证** — `qmclient_monitoring_test.cpp` 通过源代码检查验证性能日志格式字符串的一致性，保护 TS 解析器所依赖的数据格式合同。这是一种轻量但有效的跨语言合同测试方法。

6. **报表设计考究** — "论文式"主题 + 莫兰迪色系 + 响应式布局 + 全套可视化（时间序列、直方图+KDE、QQ 图、箱线图、水平柱状图），输出专业程度高。

7. **采样偏差检测巧妙** — 使用 p5 估计采样阈值是对截断数据集的聪明启发式方法，报表透明地警告用户而非隐藏问题。

## 建议

1. **统一阈值常量**：创建 `THRESHOLDS` 单一常量对象，供 `computeVerdict`、`kpiClass` 和 `detectSpikes` 共同引用，消除当前的不一致。

2. **将 `isSamplingBiased` 参数化**：接受实际采样阈值毫秒数为参数，而非用 240Hz 预算做代理值。

3. **`complianceRate` 空输入返回 `NaN`**：由 UI 层决定展示 "N/A" 而非伪造 100%。

4. **考虑为 `report.ts` 增加快照测试**：HTML 输出复杂，一份固定输入下的输出完整性快照测试可防止无意的渲染回归。
