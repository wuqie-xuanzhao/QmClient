DDNet 上游同步分层执行规格

本规格把“要不要和官方同步”拆成两个问题：哪些可以直接按普通补丁吸收，以及哪些属于硬兼容区，需要单独做兼容性审批后再决定。目标不是把所有差距一次性合并，而是给 QmClient 一个可执行、可回滚、可验证的同步顺序。

① 目标与边界 ② 同步分层策略 ③ 优先级执行清单 ④ 执行规则 ⑤ 验收标准 ⑥ 证据与来源

① 目标与边界

类型范围说明
目标把 DDNet 官方 `ddnet/master` 的高价值差距拆成可逐项吸收的清单。优先收敛稳定性修复、客户端体验修复和低风险兼容补丁。
目标把服务端玩法 / 物理 / 协议 / snapshot 格式语义放到“硬兼容区”而不是“普通同步区”。这些内容仍然应该和官方保持同步候选关系，但不能默认批量合并。
边界纯重构、纯风格、纯 i18n 同步不进入普通同步主线。这类提交通常只有整理价值，没有直接行为收益，且容易放大冲突面。
禁止不把硬兼容区提交当作“无风险补丁”处理。任何会改 demo、回放、预测、联网行为的提交，都必须单独审。
结论先说清：服务端玩法 / 物理 / 协议 / snapshot 格式语义不是“不该同步”，而是“要同步但必须单独审”。它们属于官方演进路径的一部分，但和普通 bugfix 不是同一条执行线。

② 同步分层策略

分层内容处理方式
P0 普通同步崩溃、OOB、栈溢出、泄漏、明显输入校验、客户端健壮性修复。可按单提交 cherry-pick；每条后跑 quick gate。
P1 客户端可见输入、dummy、网络浏览器、音频、轻量渲染修复、少量 0.7 兼容修复。可逐条合；先确认本地是否已改同区。
P2 兼容性审批服务端玩法、物理、协议、snapshot 格式语义、demo/teehistorian 格式、核心架构重构。必须单独建议案，先定兼容边界，再决定跟或跳。
P3 不入普通线纯重构、纯风格、纯 i18n 同步、CI / 构建杂项（除非明确依赖升级）。默认不进本轮同步清单。
“同步”在这里的意思是保持与官方方向一致，不是“自动合并所有上游提交”。对 P2 来说，正确动作是先确认语义和兼容风险，再决定是否吸收。

④ 执行规则

规则要求
单提交推进普通同步项一条一条合，不做整批 merge。
先判重叠合前先确认本地是否已改过同区，避免重复引入或冲掉本地行为。
硬兼容区单审服务端玩法 / 物理 / 协议 / snapshot 语义进入 P2 流程，先审再合。
验证节奏P0 / P1 每条至少跑 `python qmclient_scripts/gate/check_gate.py --mode quick`；P2 进入后再按风险提升到 default。
收口原则一批做完后只保留和当前同步目标直接相关的提交与说明。

⑤ 验收标准

检查项标准
边界清楚硬兼容区不会被当成普通补丁批量吸收。
优先级可执行P0 / P1 有明确顺序，P2 / P3 有明确分流。
同步可追踪每个被合入的提交都有对应主题、理由和验证要求。
兼容可审计凡是影响 demo / 回放 / 预测 / 网络行为的改动，都能追溯到单独决策记录。
