DDNet 上游同步分层执行规格

本规格把“要不要和官方同步”拆成两个问题：哪些可以直接按普通补丁吸收，以及哪些属于硬兼容区，需要单独做兼容性审批后再决定。目标不是把所有差距一次性合并，而是给 QmClient 一个可执行、可回滚、可验证的同步顺序。

① 目标与边界 ② 同步分层策略 ③ 优先级执行清单 ④ 执行规则 ⑤ 验收标准 ⑥ 证据与来源

① 目标与边界

类型范围说明
目标把 DDNet 官方 `ddnet/master` 的高价值差距拆成可逐项吸收的清单。优先收敛稳定性修复、客户端体验修复和低风险兼容补丁。
目标把服务端玩法 / 物理 / 协议 / snapshot 格式语义放到“硬兼容区”而不是“普通同步区”。这些内容仍然应该和官方保持同步候选关系，但不能默认批量合并。
边界纯重构、纯风格、纯 i18n 同步不进入普通同步主线。这类提交通常只有整理价值，没有直接行为收益，且容易放大冲突面。
禁止不把硬兼容区提交当作“无风险补丁”处理。任何会改 demo、回放、预测、联网行为的提交，都必须单独审。
结论先说清：服务端玩法 / 物理 / 协议 / snapshot 格式语义不是“不该同步”，而是“要同步但必须单独审”。它们属于官方演进路径的一部分，但和普通 bugfix 不是同一条执行线。

② 同步分层策略

分层内容处理方式
P0 普通同步崩溃、OOB、栈溢出、泄漏、明显输入校验、客户端健壮性修复。可按单提交 cherry-pick；每条后跑 quick gate。
P1 客户端可见输入、dummy、网络浏览器、音频、轻量渲染修复、少量 0.7 兼容修复。可逐条合；先确认本地是否已改同区。
P2 兼容性审批服务端玩法、物理、协议、snapshot 格式语义、demo/teehistorian 格式、核心架构重构。必须单独建议案，先定兼容边界，再决定跟或跳。
P3 不入普通线纯重构、纯风格、纯 i18n 同步、CI / 构建杂项（除非明确依赖升级）。默认不进本轮同步清单。
“同步”在这里的意思是保持与官方方向一致，不是“自动合并所有上游提交”。对 P2 来说，正确动作是先确认语义和兼容风险，再决定是否吸收。

④ 执行规则

规则要求
单提交推进普通同步项一条一条合，不做整批 merge。
先判重叠合前先确认本地是否已改过同区，避免重复引入或冲掉本地行为。
硬兼容区单审服务端玩法 / 物理 / 协议 / snapshot 语义进入 P2 流程，先审再合。
验证节奏P0 / P1 每条至少跑 `python qmclient_scripts/gate/check_gate.py --mode quick`；P2 进入后再按风险提升到 default。
收口原则一批做完后只保留和当前同步目标直接相关的提交与说明。

⑤ 验收标准

检查项标准
边界清楚硬兼容区不会被当成普通补丁批量吸收。
优先级可执行P0 / P1 有明确顺序，P2 / P3 有明确分流。
同步可追踪每个被合入的提交都有对应主题、理由和验证要求。
兼容可审计凡是影响 demo / 回放 / 预测 / 网络行为的改动，都能追溯到单独决策记录。

⑦ 需要单独开案的项，已补充调研结论

下面这些不是“普通同步补丁”，而是要么已经在本仓库里形成了自己的实现脉络，要么一旦跟随官方就会触碰兼容性、格式或默认行为，因此都应该单独开案，不能混进 P0 / P1 清单。

议题 当前状态 为什么单独开案 后续还要补的调研
CScrollRegion 横向滚动整组重构 当前实现仍是明显的纵向滚动模型：Begin/End/AddRect/RectClipped 配合 SetContentHeightForNextFrame，并且菜单、列表、下拉框和设置页都已经在大面积使用它；HEIGHT_MAGIC_FIX 仍然是现成的补丁位。src/game/client/ui_scrollregion.h:89-144，src/game/client/ui_scrollregion.cpp:36-304，src/game/client/ui_listbox.cpp:107-231，src/game/client/components/tclient/menus_tclient.cpp:3397-3430 这不是一个单点 bugfix，而是会波及所有依赖滚动区域的 UI；如果要吸收官方的横向滚动设计，得先统一滚动轴语义、裁剪语义和现有的 height fix 策略。 先确认官方那组改动是“新增横向能力”还是“替换现有 API”；再评估对菜单、设置页、下拉框和列表虚拟化的实际冲击。
CEditorMap / CEditorObject 封装整组重构 当前仓库已经有非常重的 CEditorMap：它直接持有 groups/images/envelopes/sounds/settings、history/tracker、保存加载和各类选中状态，编辑器对象也已经大量吃进 CEditorMap *。src/game/editor/mapitems/map.h:51-148，src/game/editor/mapitems/map.cpp:31-600，src/game/editor/editor_actions.h:12-669 官方这组更像是编辑器对象模型的重新分层，不是简单补一个函数；本地已经有自己的 map/object 组织方式，直接按提交粒度吸收会非常容易断链。 先确认官方目标到底是“多地图编辑”还是“状态搬家 + 统一对象生命周期”；再决定是否整组跟随。
snapshot Rust 化继续项 当前是双轨状态：Rust 侧已经有 snapshot/builder.rs、snapshot/delta.rs，Cargo 也已经拉了 libtw2；但 C++ 侧 snapshot.cpp 仍然保留 CSnapshotDelta::CreateDelta/UnpackDelta/CSnapshotBuilder，demo.cpp、client、server 还直接依赖这套接口。src/engine/shared/Cargo.toml:18-25，src/engine/shared/snapshot/builder.rs:3-154，src/engine/shared/snapshot/delta.rs:89-217，src/engine/shared/snapshot.cpp:313-862，src/engine/shared/demo.cpp:45-1544，src/engine/client/client.cpp:2772-2910，src/engine/server/server.cpp:1092-1111 这已经不是“同步一个 bugfix”，而是核心网络格式实现的架构迁移；一旦继续往前推，就会同时影响 client、server、demo、teehistorian 的数据路径。 决定是“补完双轨并清理 C++”还是“接受当前半 Rust 状态后只继续修 Bug”；再按这个决策拆下一批案。
demo / teehistorian 格式相关提交 CDemoRecorder/CDemoPlayer 和 CTeeHistorian 都是持久格式写入/读取主路径：demo 录放直接调用 CSnapshotDelta::CreateDelta/UnpackDelta，teehistorian 还带有 version_minor、join/rejoin/ready/drop 这些状态记录。src/engine/shared/demo.h:18-171，src/engine/shared/demo.cpp:45-1544，src/game/server/teehistorian.h:17-92，src/game/server/teehistorian.cpp:88-875 这些提交一旦碰到格式，就不是“今天能不能合”而是“旧回放和旧记录还能不能读”；必须按格式兼容和版本策略单独审。 需要单独列 demo / teehistorian 兼容矩阵，明确是否 bump 版本、是否保留旧格式读写、以及需要哪些样本回放做回归。
Vulkan 默认行为 当前配置默认值就是平台分支决定的：Android / Emscripten 走 GLES，Windows x64 和其他非 IA32、非 macOS 平台默认是 Vulkan，macOS / IA32 默认 OpenGL；设置页还会把后端显示成 Vulkan QmClient。src/engine/shared/config_variables.h:824-830，src/engine/client/backend_sdl.cpp:748-782，src/game/client/components/menus_settings.cpp:66-68 这不是格式问题，而是产品默认行为问题；一旦跟随官方“在 Windows 默认关 Vulkan”，就会直接改变用户启动后的首选后端。 需要先查当前 Windows 用户的后端占比和 Vulkan 失败率，再决定是否跟随官方默认策略，不能只看上游提交本身。
这里补完后的判断是：P2 项里最该单独开案的，不是“难读的提交”，而是“会改变长期行为或格式边界的提交”。反过来，那些只是边界修复的提交，仍然可以留在 P0 / P1 里一条条合。

如果你要，我下一步可以继续把 P0 / P1 再拆成真正的“可执行顺序版”，按每条提交的建议合并次序列出来。
