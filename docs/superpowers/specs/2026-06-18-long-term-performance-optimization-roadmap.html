① 当前代码真相（2026-06-18）

不凭印象，只看当前索引到的代码。这些事实是后续所有优化的现实着落点。

1.1 性能量化系统：基础已厚，缺自动化

  • qmclient_scripts/perf/lib/stats.ts 已具备 budgetCorrelationSummary、BudgetCorrelationWindow、UI section 归因、操作签名对比。
  • qmclient_scripts/perf/lib/quality.ts 已实现 aggregate-only 失败检测（AggregateOnlyTargetFpsFailures），但尚未实现按操作的 p99/max/menuMax 基线。
  • qmclient_scripts/perf/lib/report.ts 生成离线 HTML，但 report 未接入自动化回归对比，也无 CI 输出。
  • C++ 侧已有 QmPerfLogStage 统一输出到 perf/menu、perf/assets、perf/fps、perf/ui_runtime 等系统。

1.2 QmUI：骨架已有，渲染侧仍是透传

QmUI 位于 src/game/client/QmUi/，当前状态：

模块现状gap
CUiV2LayoutEngine已实现 flex 类布局（ROW/COLUMN、AUTO/PX/PERCENT/FLEX、gap、align、min/max）无缓存，每帧全量；无 dirty reason
CUiV2AnimationRuntimetween/spring 双驱动、优先级/队列/merge 策略齐全动画推进成本未拆分 per-property，缺少可见性裁剪
CUiV2Tree每帧 BeginFrame/TouchNode/EndFrame 追踪 node keynode 键未暴露为查询接口，无法做 retained 缓存
CUiV2RenderBridge仅记录 draw_calls / clip_pushes不做 batch、不做 draw list 缓存
CUiRuntimeV2每帧执行 tree → anim → render bridge → end frame；已输出 perf/ui_runtime未和 CUI 绘制解耦，底层仍走 DoLabel/DoButtonLogic

1.3 CUI：immediate-mode 仍是主路径

  • CUi（src/game/client/ui.cpp）是典型的 immediate-mode：每帧重建所有可见 widget。
  • DoLabel 有 47 个调用方跨菜单组件，是最高频文本入口。
  • CUIElement::SUIElementRect 已缓存 quad container 与 text container，但使用面未覆盖全部菜单路径。
  • CUiScopedQuadBatch 存在但使用有限，菜单仍多以独立 draw call 提交。

1.4 图形后端：命令缓冲 + quad container

  • CGraphics_Threaded（src/engine/client/graphics_threaded.cpp）是命令缓冲/线程化架构。
  • 已有 QuadContainer、tile buffer、quad buffer 批处理机制。
  • 纹理管理带 generation 跟踪，可识别 stale handle。
  • UI 未使用统一批处理层；每个 widget 独立 QuadsBegin/End 仍是常态。

1.5 文本渲染：atlas + container，中文首字是尖峰

  • ITextRender（src/engine/textrender.h）提供 text container、glyph 图集、paragraph layout。
  • SQmTextRuntimeBudgetSnapshot 已监控 glyph/container 新建、上传、耗时。
  • 稳定文本池（stable text pool）已落地，通过 PrebuildSettingsMenuTextPool / BuildIngameMenuTextPlan 提前创建 container。
  • 字形图集扩容时全量重传仍是潜在尖峰；未实现动态子图集或 LRU eviction 策略。

1.6 游戏内 FPS：已有局部优化，但缺统一 optimizer 与后端归因

  • Windows 高优先级已有基础实现：qm_process_high_priority 默认关闭，启动时在 Windows 上调用 SetPriorityClass(GetCurrentProcess(), HIGH_PRIORITY_CLASS)。它只能缓解 CPU 调度抢占，不能替代渲染、粒子、HUD、GPU upload 的实际减负。
  • 游戏主渲染路径仍是组件顺序遍历：CGameClient::OnRender() 逐个调用 m_vpAll 组件；当前只对 component_menus、components_total 等少量桶有 stage，粒子、HUD、TClient、NamePlates、Trails 等仍缺独立归因。
  • 粒子不是完全无优化：CParticles::RenderGroup() 已有视口裁剪和 QuadContainer 批量路径；缺口在 spawn/update/render 预算、按组限流、碰撞成本上限、纹理切换统计。
  • HUD/TClient 文本和图元仍有 per-frame 成本：statusbar.cpp 已有少量静态宽度缓存，但大量 TextWidth、Text、DoLabel 仍跟随每帧刷新。
  • BestClient 参考显示可行方向：其 optimizer 包含进程优先级、FPS fog、map tile culling、粒子最大渲染数、拖尾采样上限、碰撞检查上限。这说明优秀游戏客户端优化不是“让用户关特效”，而是保留体验同时给工作量设预算和可见性边界。

② 核心原则

本路线图不是追求"重构一次永逸"，而是建立长期、可验证、可持续的性能演进系统。

2.1 量化先行

任何优化在改变代码前必须先改变可观测性。没有 telemetry 的优化不可验收。

2.2 QmUI 优化是必选项

不依赖"看 fresh log 再决定"。无论当前瓶颈是否落在 QmUI，QmUI 当前只做计数、无缓存、无 batch 的架构决定了它必然成为后续瓶颈。必须系统性地补全：

  1. 布局缓存与 dirty 传播；
  2. draw call / clip push 合并；
  3. 动画推进的可见性裁剪；
  4. node 生命周期管理。

2.3 保持 DDNet 兼容

不替换官方 CUi 核心；不引入 RmlUI / retained-mode 大框架重写；不改变协议、地图、皮肤、物理、预测语义。

2.4 优先源头降温，后端不盲动

在证明 UI/layout/text 已优化到边际收益低之前，不启动 OpenGL/Vulkan backend 大重构。backend 优化只针对已被 telemetry 证明的 GPU-bound 场景。

③ 第一支柱：性能量化脚本系统（先行）

把 qmclient_scripts/perf 从"离线诊断工具"升级为"持续性能契约系统"。

  • 日志解析、百分位、尖峰检测、采样偏差检测；
  • FPS window 与 budget culprit 时间序列关联；
  • UI section 归因（ui_section:<stage>）取代 aggregate 归因；
  • offline HTML report 自包含。

④ 第二支柱：QmUI + CUI 框架 + 图形后端优化

这是长期优化的主战场。目标不是重写 UI，而是在现有 immediate-mode 基础上叠加缓存、批处理、可见性裁剪。

4.1 QmUI 优化路线

当前 QmUI 已输出 perf/ui_runtime 四段耗时，但无缓存与批处理。以下优化必须做：

4.1.1 布局缓存与 dirty 传播

  • 现状：CUiV2LayoutEngine::ComputeChildren 每帧全量计算 flex 布局。
  • 目标：引入 SUiLayoutCache，以 (page, node_key, viewport_size) 为键缓存结果；只有 style、size、content 变化时标记 dirty。
  • 验收：perf/ui_runtime 中新增 layout_dirty=0/1 与 dirty_reason=...；稳态 layout_ms 趋近于 0。

4.1.2 动画运行时可见性裁剪

  • 现状：CUiV2AnimationRuntime::Advance 推进所有 active tracks。
  • 目标：只推进可见、hover、focused、过渡中节点；离屏动画 track 进入 suspend，恢复时补时间。
  • 验收：perf/ui_runtime 中新增 active_anims / suspended_anims；大量列表滚动时 anim_ms 不随 item 数线性增长。

4.1.3 Render Bridge 真正做批处理

  • 现状：CUiV2RenderBridge 只计数，实际绘制仍调用 CUi 原语。
  • 目标：在 QmUI 原语层（button、card、form、navigation）收集 draw call，按纹理、clip、blend 排序后批量提交；同一 frame 内相同 quad 状态合并。
  • 验收：draw_calls 下降；clip_pushes 只在真正需要 scissor 时增加。

4.1.4 Node 生命周期与 retained 数据结构

  • 现状：CUiV2Tree 仅维护每帧存在的 node key 集合。
  • 目标：扩展为可持久化的 node 表，允许调用方挂布局结果、动画状态、render primitive；跨帧复用。
  • 验收：node_count 稳定；切换 tab 时 node 重建数量下降。

4.2 CUI 优化路线

QmUI 底层仍调用 CUI，CUI 不改则整体收益受限。

4.2.1 扩大 CUIElement 文本/矩形缓存覆盖

  • 把更多菜单 label、button、checkbox 迁移到 CUIElement 缓存；
  • 为 SUIElementRect 增加 dirty flag（text、font size、rect 任一变化才重建 container/quad container）。

4.2.2 统一 quad batch 层

  • 在 CUi 中引入按 frame 的 quad batch builder，允许 widget 提交带状态（texture/color/clip）的 quad，由 builder 在 frame end 时排序合并；
  • 优先对背景矩形、分隔线、icon 等纯色/同纹理图元做 batch。

4.2.3 视口外 section 与 widget 完全跳过

  • 对 settings page、server browser、demo browser 等长页，使用统一可见范围 helper；
  • 视口外只保留高度/状态，不执行 widget 逻辑、不创建 text container、不上传 quad。

4.3 图形后端优化路线

只在 telemetry 证明 GPU/backend 是瓶颈后启动。候选方向：

方向触发条件预期收益

⑤ 第三支柱：游戏内 FPS 与图形后端优化 PRD/spec

本节面向长期游戏内帧率、帧时间稳定性、画面撕裂/延迟权衡、粒子与 HUD 体验保留。目标是让 QmClient 在不要求用户关闭视觉效果的前提下，通过预算、裁剪、缓存、批处理和后端归因提高稳定 FPS。

5.1 PRD：问题定义

用户反馈的核心不是“某个特效能不能关”，而是：游戏内应保持流畅、输入延迟可控、画面不撕裂，同时粒子、拖尾、HUD、提示、QmClient/TClient 增强功能仍然可用。当前代码已有局部能力，但缺少统一的游戏内性能产品面、统一 optimizer 状态、和能解释“这一帧为什么慢”的后端/组件级归因。

用户问题当前体验产品目标
DDNet/QmClient 画面撕裂常见，开 VSync 又感觉延迟高 用户只能在撕裂和延迟之间手动取舍 提供可理解的 frame pacing 模式：低延迟、平衡、抗撕裂，并用 telemetry 解释 swap/sleep/vsync 成本。
粒子、拖尾、HUD 是体验，不希望靠关闭解决 部分功能高峰期可能造成帧时间尖峰 默认保留视觉效果，通过预算化、LOD、裁剪、分组批处理降低尖峰。
游戏内 FPS 和设置页首帧优化混在一起 report 容易只看到总桶或 UI 桶 分离 perf/game_render、perf/render_backend、perf/effects、perf/hud，明确是 CPU 渲染、GPU upload、后端 swap 还是文本问题。
Windows 高优先级是否有效不清楚 QmClient 当前只在启动时可选设置 high priority 升级为可开关、可恢复、可观测的 optimizer 子功能，并标注其收益边界。

5.2 PRD：目标与非目标

目标

  • 在不默认关闭粒子、拖尾、HUD、提示、增强渲染的前提下，降低游戏内 frame time p95/p99/max。
  • 把 CGameClient::OnRender() 下的主要组件拆成可解释的阶段：map layers、particles、trails、HUD、nameplates、TClient/QmClient overlays、backend swap。
  • 建立游戏内 optimizer：优先级、frame pacing、效果预算、可见区域裁剪、HUD 文本缓存都由统一状态和 telemetry 管理。
  • 参考 BestClient 的已验证思路，但不直接照搬用户可见语义；只吸收“预算、上限、可见性裁剪、恢复机制”的工程模式。

非目标

  • 不要求用户关闭粒子或 HUD 作为默认性能方案。
  • 不改变 DDNet 协议、物理、预测、地图语义、rank 可达性。
  • 不把 Vulkan/OpenGL 后端作为第一步大重构；后端改动必须由 telemetry 证明。
  • 不把进程高优先级宣传为“FPS 优化主方案”；它只是调度辅助。

5.3 当前代码落点

区域当前代码依据优化含义
Windows 高优先级 src/engine/shared/config_variables_qmclient.h 的 qm_process_high_priority；src/engine/client/client.cpp 启动时调用 SetPriorityClass 已实现“启动一次设置”。长期应改成 optimizer runtime：开启时记录旧优先级，关闭时恢复，避免重复系统调用，输出成功/失败 telemetry。
游戏主渲染循环 CGameClient::OnRender() 中遍历 m_vpAll，目前只对 menus 和 components_total 等少量阶段记录 需要 per-component / per-group stage，否则无法判断是粒子、HUD、TClient、map layers 还是 backend 慢。
粒子渲染 CParticles::RenderGroup() 已有 ParticleIsVisibleOnScreen 和 RenderQuadContainerAsSpriteMultiple 已有批量基础；下一步不是关闭粒子，而是控制 spawn/update/render 数量、按组限流、记录 texture switch/draw count。
HUD / statusbar statusbar.cpp 有静态宽度缓存，但仍大量实时 TextWidth/Text 把每帧变化值和稳定标签分开：稳定标签 text container 化，动态数值按变化/采样周期更新。
图形后端 CGraphics_Threaded 有 command buffer、QuadContainer、Vulkan/OpenGL/GLES backend、VSync command 先增加 draw calls、texture binds、buffer uploads、swap wait、vsync wait 的统计，再按证据优化。

5.4 参考项目：BestClient 可借鉴点

BestClient 的实现证明，游戏客户端优化不等于减少功能，而是把功能工作量纳入预算。可借鉴的是工程模式，不是直接复制配置名或 UI。

BestClient 参考观察QmClient 可转化方案
Optimizer priority 支持 DDNet 高优先级、Discord 降优先级，并缓存上次设置，避免每帧重复系统调用；关闭后恢复旧优先级。 把 qm_process_high_priority 从启动开关升级为 runtime optimizer 子功能，保留默认关闭和 Windows-only 边界。
FPS fog 按相机周围矩形/缩放百分比裁剪非必要渲染，并可选择 map tile culling。 QmClient 可先做“非关键视觉效果 fog”：粒子、拖尾、远端装饰、非交互 overlay 先裁剪；map tile culling 作为后续实验项。
3D particles 有最大渲染数、delta clamp、view margin、碰撞检查上限。 给 QmClient 粒子加 group budget：每组 spawn/update/render 上限，frame pressure 下自适应降采样，但不改变开关语义。
Trail / afterimage 限制采样数、跳变距离和历史帧数量。 TClient trails / afterimage 类功能按距离、速度、屏幕可见性控制采样密度，避免高速/多人时爆发。

5.5 功能需求

FR-1：Runtime Optimizer 状态机

  • 新增统一 optimizer 状态，不直接把每个优化散落在各组件开关里。
  • 状态包含：enabled、profile=quality|balanced|low_latency|performance、frame_pressure、backend_mode、effects_budget_scale。
  • Windows 高优先级：开启时记录旧 priority，关闭时恢复；调用失败必须日志和 telemetry 可见；默认关闭。
  • 禁止在 render hot path 每帧枚举系统进程；类似 BestClient 的 Discord 降优先级如果未来要做，必须节流到秒级并默认关闭。

FR-2：游戏内组件级 perf stage

  • CGameClient::OnRender() 对主要组件输出稳定 stage：component_particles_update、component_particles_render_group、component_hud、component_tclient、component_qmclient_overlay、component_nameplates、component_trails、component_map_layers。
  • 每个 stage 附带 state、spectating、particles_visible、draw_calls_delta、texture_binds_delta 等可选字段。
  • report 必须把游戏内 FPS 归因从 components_total 拆到具体组件，否则不能声称定位完成。

FR-3：粒子/拖尾保体验预算化

  • 按 group 设置预算：general、extra、trail、explosion、background 等分别统计和限流。
  • spawn budget：同一帧同一组最多新增 N 个；超过后按优先级丢弃低影响粒子或合并为更少粒子。
  • update budget：视口外粒子降低更新频率；远端粒子可按 2–4 帧更新一次，但生命周期视觉上连续。
  • render budget：超过 budget 时优先保留爆炸、命中、玩家附近粒子；背景/低 alpha/远端粒子优先降采样。
  • 碰撞预算：类似 BestClient 的碰撞检查上限，粒子数量过多时自动关闭低优先级粒子间碰撞或降频。

FR-4：HUD / TClient 文本与图元缓存

  • 稳定标签：FPS、Ping、Velocity、Position 等 label 部分使用 text container 或 width cache。
  • 动态值：按值变化或采样周期更新，例如网络统计、监控面板可 5–10Hz 更新，玩家坐标/速度仍按需要实时。
  • HUD icon/shape：优先使用已有 QuadContainer，减少每帧 QuadsBegin/End。
  • 监控 overlay 默认不应成为 FPS 测试噪声；开启时单独输出 perf/hud_monitoring。

FR-5：Frame pacing 与抗撕裂模式

  • 保留 DDNet 现有 gfx_vsync，但新增用户可理解的建议模式文案：低延迟、平衡、抗撕裂。
  • 低延迟模式：VSync off，支持 FPS cap 建议值（例如显示器刷新率的 2x/3x 或略高于刷新率），重点减少输入延迟。
  • 平衡模式：VSync off + 稳定 frame cap + frame pacing 观测，目标降低撕裂感和 sleep 抖动。
  • 抗撕裂模式：VSync on 或后续支持 adaptive vsync/late swap；明确提示可能增加输入延迟。
  • telemetry 必须区分：render CPU 时间、sleep wait、swap/vsync wait、GPU upload wait。

FR-6：图形后端统计与条件优化

  • 新增后端统计：每帧 draw calls、texture binds、quad container renders、buffer uploads、text texture updates、swap 耗时。
  • OpenGL/Vulkan 分别输出 backend name 和 capability：quad_container_buffering、text_buffering、tile_buffering。
  • 只有当 report 显示 backend-bound 时，才进入 UI atlas、ring buffer、scissor batching、async upload 等后端优化。

5.3.3 预算规则

  • 预热计划必须绑定 language、font face / variant、font size bucket；语言或字体变体变化后计划失效。
  • 进入游戏前可使用较高预算，但仍需要分帧，例如每帧 32–64 个 glyph，避免 loading 卡死。
  • 空闲预热只允许低预算，例如每帧 4–16 个 glyph，并在 frame time 高于阈值时暂停。
  • 首帧交互窗口（Esc、切 tab、滚动第一帧）禁止执行大批量 glyph warmup，只能复用已 ready 的 glyph 或入队。
  • 预热 API 应直接 warmup glyph，不应通过创建隐藏 text container 伪装预热，避免污染 text container 命中率和 container 统计。

⑦ UI 首帧专项指南（结合当前代码现状）

本节补充 2026-06-19 的 UI 首帧卡顿分析：当前短期问题不是单纯“文本渲染慢”，而是首帧同步工作分配不当、文本计划覆盖不足、以及热点功能模块在首帧构建过多控件。

6.1 ESC 首帧：可以复用文本池缓存，但不能首帧补齐缓存

当前 ESC 打开入口在 src/game/client/components/menus.cpp 的 CMenus::OnRender()。正确策略是：打开 PAGE_GAME 首帧只使用 ingame 文本池里已经 ready 的文本容器；如果命中失败，只允许排队到后续帧预算 drain，不允许为了“让缓存可用”在首帧同步创建 text container 或 paragraph layout。

不可访问崩溃的根因边界：文本池复用本身不是问题；风险来自未注册/未 ready 的 CUIElement::SUIElementRect、已失效 text container、或 cache miss 后仍直接访问 Rect/container。防线应放在渲染入口：ready 才渲染，miss 只入队，必要时用极小范围 immediate fallback 显示关键 chrome。
路径允许禁止
ingame_esc_open / PAGE_GAME 首帧 复用 MENU_TEXT_SCOPE_INGAME 中已有 ready container；预构建少量固定 tab/button 文本；渲染旧缓存或关键按钮 fallback 同步调用 server info 文本准备；同帧强制 DrainIngameUiTextRuntime(true)；创建 MOTD paragraph container
进入 PAGE_SERVER_INFO 触发 PrepareIngameServerInfoTextRuntime()，并用预算 drain 准备 snapshot text / MOTD paragraph 在 render 函数里直接 TextRender()->RecreateTextContainer 或绕过预算同步 layout
帧尾 ingame_text_runtime_drain 只在当前页相关时按 token drain；没有 server info 可见需求时只 drain 已有 snapshot 队列 因为存在 MOTD 就后台同步 prepare server info，导致 Esc 首帧背锅

6.2 文本池命中率：不要把 fallback 当优化成果

fallbackImmediate 和 unplannedVisibleCount 高时，优先解释为“计划收集覆盖率不足”或“style key/page/tab/subtab 不一致”，而不是文本池没用。文本池正确路线是提高 plan collection 覆盖，保证首帧可见文本先有 descriptor，再由预算化 prebuild/drain 建好 container。

  • 普通 settings 文本：cache miss 只入队，不能扩大 immediate fallback。
  • ingame 关键 chrome：tab、按钮、标题允许极小范围 fallback，避免不可读。
  • 动态文本：服务器名、玩家名、资源标题应走 snapshot/LRU 类缓存，不纳入 static stable 文本命中率分母。
  • 验收口径：planCollectionComplete=true、unplannedVisibleCount 下降、fallbackImmediate 只保留在白名单 chrome。

6.3 QmClient Functions：首帧轻量路径优先级

当前 functions 页热点集中在 pie_menu、block_words、gores。这些主要是功能 UI 构建问题，不是通用文本渲染问题。当前代码已具备 FunctionFirstFrameLightPath / function_first_frame_light_path 形态，应把它固化成长期规则。

模块首帧只做延后到后续帧建议 stage
pie_menu 卡片壳、标题、启用开关 扇形预览、颜色 picker、图标/标签循环、reset 控件 pie_menu_layout、pie_menu_controls、pie_menu_preview_draw

gores 标题、核心开关 绑定查询、key reader、密码输入框、条件分支控件 gores_layout、gores_controls、gores_bind_lookup

6.4 DDNet / Controls / TClient / HUD：先拆桶，再优化

当前 settings_page_content 仍是太大的归因桶。长期规则是每个设置页至少拆出 shell、section/list、interactive layer、text/cache layer。TClient 已有 LogTClientPerfStageEx() 模式，可作为其他页面的参照。

⑪ 风险与边界

  • QmUI 不要变成 retained-mode 大框架：保留 immediate-mode 的灵活性，只在必要处叠加缓存；node 生命周期必须可预测，避免 dangling 状态。
  • CUI 基础路径谨慎改动：涉及 DoLabel、DoButtonLogic、CScrollRegion 等高频上游 API 时，默认走外围适配，确需改动时要有更小补丁、更强测试和 rollback 方案。
  • backend 不盲动：必须有 telemetry 证明 backend 成本超过 UI/layout/text/game-render 后，才进入 Phase F。
  • 性能优化不绑定视觉重设计：每轮保持显示、输入、滚动、选择、资源 fallback 语义不变。
  • 避免过度工程：每引入一层缓存，必须同时引入命中率/成本/收益 telemetry；证明收益为负时立即回退。
