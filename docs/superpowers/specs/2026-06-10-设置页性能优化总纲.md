# 设置页性能优化总纲

> **规格状态**：`active`；最近更新：`2026-06-11`。
> **范围**：设置页全部 tab 的冷启动、切 tab、滚动性能；Tee 页皮肤列表；性能量化系统。
> **取代文档**：`2026-06-02-设置页UI性能优化第一性原理分析.md`、`2026-06-02-设置页性能量化系统设计.md`、`2026-06-11-最新日志设置页卡顿路径报告.md`、`2026-06-11-设置页P2日志根因与优化报告.md`、`2026-06-11-设置页预热系统风险与收益分析.md`。

## 速答

设置页卡顿的根因不是"缺 FBO"或"缺预热"，而是**每一帧做了不该做的工作**：不可见 section 的 widget 仍然执行、静态文本每帧重建、后台 job 结果集中合并且与交互帧重叠。

当前实际代码状况：

- **FBO 清理已完成**：设置页不再保留页面级、section 级 FBO / recorded render target / render-target runtime cache 路径；非 FBO 的 CPU/runtime metadata、文本池和 section 高度缓存仍存在，后续优化不再依赖任何 FBO 命中或预热方案。
- **CSectionLoader** 仍是核心调度器：它具备四状态机（`UNINITIALIZED → MEASURING → COMPACT → FULL`）能力，但当前 live 调用大多显式 `SetProgressiveEnabled(false)`，因此实际行为更接近“先测量，再按可见性与预算直接走 full render 或跳过 full render”；视口外 section 仍会被测量高度。
- **文本池方案不是取消，而是已经部分落地并继续扩展**：当前代码已有 `SettingsTextElement()` / `DoSettingsLabelStreamed()` / `InvalidateSettingsTextPool()`，按 `page + tab + text id` 复用稳定 `CUIElement`；General、Graphics、Sound、DDNet 基础页的静态 checkbox label 已通过 settings 专用 helper 接入，Tee 的 `Name` / `Clan`、DDNet 的部分 section 标题、TClient/QmClient 的部分标题也已接入。Language cache 已改为 standalone Language 页强制、General 页语言选择区域按文本预算分帧预热。缺口主要是 slider label、动态数值、TClient/QmClient 重页覆盖率、首帧可见文本冷创建摊销、以及全页面 `text_new` / `text_reused` 验收。
- **资源 Jobs** 已有完整的吞吐量控制器，但 `settings:tee / Work Drain` 必须强制按“后台 drain / session 归因热点”解读，不能单独当成主线程卡顿证据。可见区皮肤仍然优先加载，`IDLE_DRAIN` 的后台请求预算当前已收紧到 8；剩余问题更准确地说是**历史请求积压和 backlog 上限不足**。它值得作为后台吞吐和资源队列健康问题跟踪，但只有和同一目标操作窗口的 FPS/frame-time 长帧同帧相关时，才参与卡顿根因判断。
- **当前生效的设置页 runtime prewarm 入口** 是 `CMenus::PrewarmVisibleSettingsResources()`：它先走页面资源预热，再对 TClient / QmClient 页走 `PrewarmOnly` 渲染路径。预热仍有收益，但覆盖并不均匀，且不同页面的预热路径与首帧实际路径仍需逐页用 telemetry 验证。
- **预热系统不是纯资源加载**：当前 runtime prewarm 会直接执行一部分真实 UI 布局/渲染路径；TClient / QmClient 的 `PrewarmOnly` 路径仍会进入 section / module 处理并维护部分跨帧布局状态。`CSectionLoader::Warmup()` 仍在仓库中但不是当前设置页 runtime prewarm 主入口，也不能被默认视为“安全且一定提升性能”的启动加载阶段；所有预热收益必须用同路径 A/B `fps_summary` 验证。
- **P2 量化系统补全已落地，但验收口径必须看对字段**：当前代码已有 settings 操作窗口 `fps_summary`、online `ingame_esc_open` 样本、settings-only `targetSettings.verdict`、缺样本 quality warning 和 report/summary 输出。目标设置页结论以 `targetSettings.verdict` 为准，不看顶层混合 verdict；缺 online 样本当前是 warning，不会直接让 verdict 失效。
- **QmUI 已可分析，不应再写成“不能分析”**：当前代码里 `CUiRuntimeV2` 已经输出 `perf/ui_runtime` JSON 摘要，包含 `operation`、`nodes`、`anim_ms`、`active_anims`、`queued_anims`、`render_bridge_ms`、`duration_ms`，TS report 也会把它归入 `UI Runtime`。剩余缺口是补 `subtab/module/widget_scope`、`layout_ms`、`draw_calls`、`clip_pushes`，以及修复 `perf/qmclient` 目前 frame 为 0 导致无法和 runtime/render 逐帧对齐的问题。

当前 baseline（2026-06-10，post-FBO-cleanup，1ms 采样阈值）：
- **verdict: FAIL**，**p99 = 12.906ms**，**spike 帧 = 464 个**
- 第一热点：`settings:tee / Work Drain` — 后台 drain/session 归因热点，单次汇总 272 个 job 结果，耗时 **6839.642ms**；**不单独等价于主线程卡顿**
- 第二热点：`settings:tee / Work Drain` — 后台 drain/session 归因热点，单次汇总 495 个 job 结果，耗时 **3901.435ms**；**不单独等价于主线程卡顿**
- 第四热点仍是 `server_browser / List Interaction` — 68.325ms（不在本轮范围）

这份 `2026-06-10` 数据是**当前 FBO 删除后唯一基线**。它反映的是设置页侧 FBO 清理已经落地后的真实运行状态；后续所有性能计划、实现优先级和回归判断，都应默认以这份数据为起点。它仍然属于**混合操作路径**，因此如果要做严格的 settings-only 验收，仍需在这份基线之上继续补固定场景 session。

补充样本（2026-06-11，P2 量化补全后，P0 文本冷启动优化前）：`qm_perf_2026-06-11_02-38-33` 已能按 settings / ingame Esc 操作窗口验收，`quality.warnings=[]`，但 `targetSettings.verdict=FAIL`，`targetSettings.p99=335.999ms`，最差窗口为 `settings_open settings:general`、`ingame_esc_open online game`、TClient/QmClient 子 tab 切换。这个样本说明 Tee 滚动不是当前主因，文本池首帧冷创建、无条件语言页缓存构建、未进文本池的 checkbox/slider label、Tee 皮肤列表 key 分配和同步 tab 内容重建需要继续优化；其中无条件 Language cache 和基础页静态 checkbox label 已在 P0 文本冷启动轮次先行处理，收益仍需用新日志验收。

核心量化目标：**设置页任意交互（切 tab、滚动、打开页面）的帧时间 ≤ 8.33ms**（120Hz），最差帧 p99 ≤ 16.67ms（60Hz）。

## 1. 问题定义

### 1.1 用户感知到的问题

玩家在游戏中打开设置页、切换 tab、滚动皮肤列表时，画面会明显卡一下甚至卡住几秒。这不是"画面不流畅"，而是**帧时间尖峰**——某一帧突然耗时几十甚至几百毫秒，超过了显示器刷新周期。

具体的用户场景：

- **打开设置页**：按 Escape → 设置，画面停顿 100-500ms 才出现界面
- **切 tab**：从 General 切到 Tee，画面停顿 50-200ms
- **滚动皮肤列表**：在 Tee 页滚动时，滚动不跟手，偶尔卡一下
- **静止不动**：什么都不做时帧时间 2-3ms，很流畅

### 1.2 为什么会卡 — 帧预算

DDNet 每一帧要做两件事：游戏渲染（世界、实体、特效、HUD）和菜单渲染（设置页、服务器列表等）。这两件事跑在同一个线程里，共享同一帧的时间预算。

```
一帧 16.67ms（60Hz）
├── 游戏渲染：8-12ms
├── 菜单渲染：2-4ms（正常）
└── 剩余：给下一帧
```

当菜单渲染突然从 2ms 涨到 200ms，这一帧就"爆了"——游戏画面停顿，玩家感受到卡顿。

优化的目标不是让菜单渲染"更快"，而是让它**不要突然变慢**——消灭尖峰帧，保持帧时间稳定。

### 1.3 范围边界

**本轮只做设置页**。具体范围：

- 设置页全部 tab：General、Tee、Appearance、Controls、Graphics、Sound、Assets、DDNet、TClient、QmClient
- Tee 页的皮肤列表加载与滚动
- 性能量化系统（采集 + 分析 + 报表）

**明确不做**（延后到有证据时再考虑）：

- Server Browser 的列表交互优化（当前遍历 1281 行只渲染 24 行的效率问题）
- Demo Browser 的目录扫描异步化
- Assets / Workshop 的进一步优化
- 全局 scheduler 大重构
- 任何非设置页的页面

**为什么不做 Server Browser？** 虽然 perf 数据显示它有 78ms 的列表交互帧，但这是不同根因的问题（同步遍历 vs 设置页进入/切换路径），不应和设置页混在一起优化。当前 settings-only 卡顿判断只看 settings / ingame Esc 操作窗口的 FPS/frame-time；Server Browser、Internet 和 `settings:tee / Work Drain` 只能作为背景热点或吞吐健康信号。

## 2. 量化目标

### 2.1 帧时间分层目标

DDNet 是快节奏平台游戏，流畅性要求高于一般应用。在设置页上下文中：

| 指标 | 目标值 | 理由 |
|------|--------|------|
| UI 帧时间均值 | ≤ 4ms | 为游戏渲染留足 12ms+ 预算（60fps） |
| 交互帧（切 tab/滚动） | ≤ 8ms | 不超过 120Hz 刷新周期 |
| 最差帧 (p99) | ≤ 16ms | 不超过 60Hz 刷新周期；超出即用户可感知卡顿 |
| 首帧（冷启动进入设置页） | ≤ 33ms | 允许一次较长帧，但不能连续两帧超标 |

**关键洞察**：帧时间的 **p99** 比平均值重要得多。一次 50ms 的卡顿远比 10 次 5ms 的微波动更影响体验。优化应优先消灭"尖峰帧"。

### 2.2 无上限 FPS 指标

无上限 FPS 是设置页性能最直观的端到端指标。它不解释瓶颈来自哪里，但它直接回答"用户最终感受到的吞吐量有没有变好"。

| 指标 | 用途 | 解读 |
|------|------|------|
| `avg FPS` | 观察整体吞吐量 | 同路径优化后 avg 上升，通常说明总 CPU/GPU 成本下降 |
| `min FPS` | 捕捉最差体感和尖峰 | min 下降或长期偏低，优先回查 p99、长帧 timeline |
| `max FPS` | 观察稳态上限 | 只作辅助，易受计数窗口、后台负载、驱动限帧影响 |

采集时必须固定：操作路径、硬件、renderer、分辨率、UI scale、客户端版本、无上限帧率状态。FPS 只能和同一机器同一路径的 baseline 比较，不能跨机器比较绝对值。

### 2.3 量化验收标准

| 验收项 | 指标 | 测量方式 |
|--------|------|----------|
| 打开设置页首次渲染 | ≤ 1 帧 > 33ms, 后续帧 ≤ 16ms | `qm_perf_debug` 日志 |
| 切 tab（如 General → Tee） | ≤ 8ms | `qm_perf_debug` 日志 |
| 子 tab 切换 | ≤ 8ms | `qm_perf_debug` 日志 |
| 滚动一屏内 | 每帧 ≤ 8ms | `qm_perf_debug` 日志 |
| 滚动中快速翻页 | p99 ≤ 16ms | `qm_perf_debug` 日志 |
| 打开皮肤列表（100+ 皮肤） | 首帧 ≤ 16ms, 后续 ≤ 8ms | `qm_perf_debug` 日志 |
| 无上限设置页 FPS | 同路径 `avg/min FPS` 不低于 baseline | 客户端 FPS 统计 + perf report |

## 3. 实际代码现状

> 本章描述的是代码仓库中的实际实现，不是设计意图。所有结论基于当前分支 `codex/axiom-script-governance` 的代码。

### 3.1 设置页渲染路径

设置页每一帧的调用链：

```
CMenus::Render()                          # menus.cpp
  └─ RenderSettings(MainView)             # menus_settings.cpp:4423
       ├─ 绘制左侧标签栏（10 个 tab）
       ├─ 检测当前选中的 tab
       └─ 对选中 tab 的内容区域：
            └─ [实际渲染路径] RenderSettingsXxx(ContentView)
                 ├─ CScrollRegion::Begin/AddRect/End    # 滚动区域
                 ├─ CUi::DoButton_Menu/DoLabel/DoEditBox # CUI widget
                 └─ ui_widget::DrawCard/PrimaryButton    # QmUI widget
```

**核心调度器：CSectionLoader**（`src/game/client/components/section_loader.cpp`）

CSectionLoader 用一个四状态机管理每个 section 的生命周期：

| 状态 | 动作 | 说明 |
|------|------|------|
| `UNINITIALIZED` | 调用 `MeasureFn` 测量高度 → 进入 `MEASURING` | 每个 section 的起始状态 |
| `MEASURING` | 计算视口优先级；如果靠近视口则渲染紧凑版 → `COMPACT` | 预取边距 200px |
| `COMPACT` | 如果有预算（每帧 5ms，最多解锁 2 个）且优先级高 → `FULL` | 预算用完后保持在 COMPACT |
| `FULL` | 如果脏了则重新测量，调用 `RenderFullFn` 完整渲染 | 真正的"用户看到的渲染" |

**当前 live 调用方式**：设置页中的主要调用点会显式 `SetProgressiveEnabled(false)`。这意味着 section loader 的通用状态机仍然存在，但 live path 更接近：

- 先对 section 做高度测量
- 当前帧根据视口优先级与预算决定是否走 `RenderFullFn`
- 视口外 section 通常不会走 full render，但仍然会被测量高度

**关键问题**：视口外 section 虽然不一定会渲染完整 widget，但仍然会被测量；这意味着“不可见 section 仍做 CPU 工作”的根因仍然存在。

`CSectionLoader::Warmup()`（`section_loader.cpp:338`）仍存在，但它不是当前设置页 runtime prewarm 的主入口。当前 live prewarm 主要由 `PrewarmVisibleSettingsResources()` 调用页面资源预热，再对 TClient / QmClient 走 `PrewarmOnly` 渲染路径；TClient 的 `PrewarmOnly` 仍会进入 `CSectionLoader::Process()`，不是直接调用 `Warmup()`。

`Warmup()` 自身也不能被当作可靠的“真实视口 near/far 模型”：它会清理 `CachedHeight`，用固定 `m_MainView.y` 和当前缓存高度计算 section rect，且没有消费 compact return height。它最多说明仓库里仍有一个 scheduler/section 预热工具，不代表现网设置页预热已经安全、准确或有效。

**问题**：预热收益并不稳定。部分页面/section 的预热路径与首帧真实展示路径并不完全一致，导致“预热做了工作，但首帧仍有冷启动成本”。这不是一个统一结论，后续需要逐页用 telemetry 验证。

### 3.2 FBO：已完成清理

FBO（Frame Buffer Object，帧缓冲对象）曾被用来做 section 的静态层缓存：把 section 的不变部分（背景、标题、分隔线）预先渲染到一张纹理，后续帧直接贴纹理，只重绘交互部分。

**当前状态：设置页侧 FBO 清理已完成，代码已可编译并通过当前 quick gate 与相关测试。**

已完成清理的部分：
- `section_loader.h/cpp`：FBO 相关的渲染目标、缓存有效性、静态/交互层拆分全部剥离，`PrewarmStaticRenderTargets`、`DrawCachedSectionByName`、`RecordStaticRenderTarget` 等函数已移除
- `settings_runtime_cache.h/cpp`：FBO 枚举值、渲染目标注册表、section 注册表、预热计划全部移除
- `settings_warmup.h/cpp`：`RUNTIME_FBO` 预热类型移除
- `menus.h`：所有 FBO 缓存数组（`m_aSettingsPageRuntimeCaches[32]` 等）、FBO 函数声明全部移除
- `menus.cpp`：`DestroySettingsPageRuntimeCaches` 等 FBO 函数实现移除
- `settings_resource_jobs.cpp`：`SettingsPageCanUsePageFbo` 等 FBO 相关函数移除
- `config_variables_qmclient.h`：`qm_settings_fbo_cache`、`qm_settings_fbo_cache_debug` 已移除
- `settings_warmup_test.cpp` / `section_loader_test.cpp`：旧 FBO 测试用例移除，新增 cleanup contract tests，验证源码不再引用旧 FBO 合同

**文档立场**：FBO 删除是本仓库已经落地的方向。本文档后续所有优化都不依赖任何 FBO 路径。

### 3.3 资源 Jobs 系统

**文件**：`src/game/client/components/settings_resource_jobs.h` / `.cpp`

这个系统负责皮肤纹理的异步加载、上传与 drain 归因。核心是一个 PID 风格的吞吐量控制器，根据当前帧的状态自动调整预算。

**四种运行模式**（`ESettingsSkinThroughputControllerMode`）：

| 模式 | 触发条件 | 后台请求预算 | 说明 |
|------|----------|-------------|------|
| `SCROLL_ACTIVE` | 用户正在滚动 | 0 | 交互优先，不发后台请求 |
| `POST_SCROLL_RECOVERY` | 刚停止滚动 | 0 | 恢复期，仍不发后台请求 |
| `IDLE_VISIBLE` | 空闲但可见区未稳定 | 可变 | 温和推进 |
| `IDLE_DRAIN` | 空闲且可见区已稳定 | **8**（已收紧） | 继续推进后台请求，但仍需 backlog 上限 |

**更准确的说法**：`IDLE_DRAIN` 当前预算 8 不是“可见项被后台饿死”的根因。当前实现里，可见区皮肤仍然先于后台项被调度；真正的问题是，当用户做过一次大跨度滚动后，系统可能已经留下大量历史 `BACKGROUND_REQUESTED`。此时如果页面进入 `IDLE_DRAIN`，后台请求会继续推进这份积压；没有硬 backlog 上限时，队列健康仍可能恶化。perf 数据里的 5575ms / 6839ms `work_drain` 数值应优先解释为后台 drain / session 归因热点和队列健康信号；它本身不等价于主线程 frame-time，也不能单独作为“卡顿”证据。

**背景请求预算决策**（`SettingsSkinBackgroundRequestBudgetDecision`）：
```
backlog_high_watermark = max(visible_reserve * 8, count_fuse_limit * 2)
available = count_fuse_limit - real_inflight
```

当前逻辑在"健康进展"（有加载完成）时不会限制新的后台请求——只要还有东西在加载，就可以继续往队列里塞。这导致了 backlog 的无限膨胀。

### 3.4 皮肤加载链路

**文件**：`src/game/client/components/skins.h` / `skins.cpp`

每个皮肤有 7 个状态：

```
UNLOADED → BACKGROUND_REQUESTED → PENDING → LOADING → LOADED
                                                   → ERROR
                                                   → NOT_FOUND
```

在设置页上下文中，加载分为三层优先级：

1. **可见区（VISIBLE）**：立即升级到 `PENDING`，不受延迟限制
2. **预取区（PREFETCH）**：需要等待 100ms 后才能进入 `PENDING`（防止快速滚动时抖动）
3. **后台（BACKGROUND）**：由吞吐量控制器的背景请求预算控制

每帧处理流程（`UpdateStartLoading`）：
- 将 `PENDING` 转为 `LOADING`（启动作业），遵守 `CountFuseLimit`（最大飞行中负载）和 `VisibleReserve`（为可见区保留的槽位）
- `UpdateFinishLoading` 完成作业（纹理上传），限制每帧最多 12 个，且在 GPU 预算内

### 3.5 预热系统

**当前 runtime 入口**：`src/game/client/components/menus.cpp` 中的 `CMenus::PrewarmVisibleSettingsResources()`

当前设置页 idle prewarm 的实际流程是：

1. `PrewarmVisibleSettingsResources()` 根据当前页面计算 content view
2. 先调用 `PrewarmSettingsPageResources(Page, Tab, ContentView)` 进行页面资源预热
3. 对 TClient / QmClient 页，再分别走 `RenderSettingsTClient(..., true)` / `RenderSettingsQmClient(..., true)` 的 `PrewarmOnly` 路径

这意味着当前真正生效的是“页面资源预热 + 页面自定义的 PrewarmOnly 渲染路径”。

**补充说明**：`CSettingsWarmupScheduler`（`src/game/client/components/settings_warmup.h/.cpp`）仍保留在仓库中，也有单测覆盖，但它不是当前设置页 runtime prewarm 的主入口，不应再把它当成现网设置页预热链路本身。

**当前问题**：预热不是完全无效，而是收益不稳定、覆盖不均。不同页面中 `RenderCompactFn`、`RenderFullFn` 和真实首帧路径的一致性不同，需要逐页用 telemetry 验证哪些预热真正有效。

**当前代码风险**：

- `PrewarmVisibleSettingsResources()` 只在 settings 页空闲时运行，但它会直接调用 `RenderSettingsTClient(..., true)` / `RenderSettingsQmClient(..., true)`，因此它不是独立资源加载队列，而是执行一部分真实 UI 子树。
- `PrewarmSettingsPageResources()` 会为 General / Tee / Assets 请求资源，但调用方丢弃 ready 返回值；它更像持续尝试预热，而不是有验收状态的加载阶段。
- `CSectionLoader::Warmup()` 会重置并写入 section 状态、高度缓存和 `m_HasCachedHeight`，预算只在 section 边界检查；单个重 section 仍可超过预算。它不是当前 runtime 主入口，但如果未来重新接入，也必须先修正 fixed-y / cached-height / compact-height 语义。
- QmClient Config tab 在 `PrewarmOnly` 时跳过 `RenderSettingsTClientConfigs()`，所以它不能覆盖 Config 首帧重路径；但 QmClient `PrewarmOnly` 仍会清空/重建 `s_GlassCards`，并通过 `RegisterModuleCard()` 写 `s_aQmModuleLastHeights`。
- `PrewarmPlayerPreviewReady()` 仍会同步发起资源请求并轮询 readiness；这类“预热”本质是把资源请求、状态检查和 UI 子树成本搬到 idle 帧，不等于独立后台加载。
- 预热和启动资源加载不是一回事：皮肤资源加载路径有 VISIBLE/PREFETCH/BACKGROUND 优先级、后台 request budget、count fuse、GPU upload limiter、max-per-frame 和 frame budget；UI 预热路径没有统一的 per-frame CPU budget，也不能自动中断文本、布局、列表扫描或 widget 调用。

## 4. 第一性原理：UI 性能优化的本质

### 4.1 一帧里到底发生了什么

```
Frame Time = CPU 提交 + GPU 绘制 + 同步等待
           = (布局计算 + 文本创建 + 输入检测 + 状态更新 + Draw Call 提交)
           + (顶点处理 + 光栅化 + 像素着色 + 混合)
           + (SwapBuffers / v-sync + 驱动同步)
```

优化每一帧本质上就是**减少上述每一项的工作量**，且**只在变化时才做**。

DDNet 的特性决定了很多"通用优化手段"不适用：
- DDNet 是 2D 俯视角游戏，所有渲染通过 quad + sprite + texture 完成
- 没有后处理链（bloom、motion blur、SSAO）
- UI 和游戏渲染共享同一个 GL/Vulkan context，共享帧预算
- 菜单渲染不是独立线程，发生在 `CMenus::OnRender()` 中

### 4.2 六个优化维度（按影响力排序）

#### 维度 1：少做 — 只处理可见和变化的部分

**原则**：不可见的 UI 元素不应消耗 CPU/GPU 时间。

**反模式**：每帧遍历所有 section/行/项，即使 90% 在屏幕外。

**DDNet 现状**：CSectionLoader 虽有视口优先级，但 MEASURING 阶段仍会测量所有 section 高度；列表渲染没有真正的虚拟化（只渲染可见行）。

**对应策略**：B（视口外 section 跳过 widget）、C（列表虚拟化）

#### 维度 2：少提交 — 减少 Draw Call 和状态切换

**原则**：每个 Draw Call 都有 CPU 驱动开销（状态验证、命令转换）。合并提交减少开销。

**反模式**：每个 UI 元素单独触发一次绘制；不同纹理/着色器/混合模式频繁切换。

**DDNet 现状**：CUI 的 `DoButton_Menu()`、`DoLabel()` 直接调用 `Graphics()->QuadsDrawTL()` 或 `TextRender()->RenderTextContainer()`，没有统一的批处理层。

**对应策略**：E（Section 内 Quad 批处理）

**后端边界**：如果后续 telemetry 证明长帧主要落在 `render_bridge`、`draw_calls`、`flush` 或 GL/Vulkan pipeline 切换，再进入渲染后端提交路径优化；当前 settings 主线仍以 CPU 侧文本、布局、列表和 `work_drain` 为主，后端优化只能作为有条件的次级方向。

#### 维度 3：少画 — 减少 Overdraw 和像素填充

**原则**：每个像素被多次绘制浪费 GPU 填充率和带宽。

**反模式**：大面积半透明面板互相重叠。

**DDNet / QmUI 现状**：QmUI 的成本不能只看 `DrawCard()`。当前 `CUiRuntimeV2` 至少分成四段：

- tree begin/end：UI tree 的帧级构建与回收
- animation runtime：动画推进与状态解析
- render bridge：把 QmUI 结构提交到实际渲染桥
- card/widget draw：具体控件的背景、边框、高光与内容绘制

`DrawCard()` 的 4 层绘制确实带来 overdraw，但在 DDNet 这类 2D 桌面场景里，它更可能是**次级 GPU 成本**；QmUI 更需要先回答的是：当前慢的是 tree / anim / render bridge / 还是 widget draw。本轮文档默认把 QmUI 视为一个**独立 runtime 成本域**，而不是只把它当“卡片 overdraw 问题”。

**对应策略**：P2 优先级，低收益

#### 维度 4：少重建 — 缓存静态内容

**原则**：静态文本、布局、网格每帧重建白白消耗 CPU。

**反模式**：每帧重新创建文本容器；每帧重新计算布局。

**DDNet 现状**：CUI 的 immediate-mode 天然倾向每帧重建。当前仓库已经有设置页文本池：`SettingsTextElement()` 按 `page + tab + text id` 返回稳定 `CUIElement`，`DoSettingsLabelStreamed()` 复用 text container 并统计 `text_new` / `text_reused`。但覆盖率仍不足，很多静态 label 仍走不缓存的 `DoLabel(const CUIRect*, ...)`，且已缓存文本的首次可见帧仍可能集中冷创建。

**对应策略**：A（设置页文本池覆盖与首帧摊销）、F（布局脏检测）

#### 维度 5：少等待 — 异步化重活

**原则**：I/O、解码、GPU 上传和后台 drain 不应污染交互帧；是否造成卡顿必须以 FPS/window frame-time 为准。

**反模式**：用户滚动后后台请求积压无限扩大，report 把 session/drain 归因热点误当成主线程卡顿根因。

**DDNet 现状**：资源 Jobs 已有异步框架，`IDLE_DRAIN` 预算已收紧到 8，但 backlog 硬上限和健康进展条件仍需继续收敛。`work_drain` 可以暴露吞吐健康问题，但必须结合同帧 FPS/window 才能判断是否影响主线程体感。

**对应策略**：D（Job 合并帧预算限制）

#### 维度 6：少分配 — 避免每帧内存分配

**原则**：`malloc/free` 在游戏循环中导致不可预测的帧时间尖峰。

**反模式**：每帧创建临时 `std::vector`、`std::string`；回调 lambda 捕获大对象。

**DDNet 现状**：ImGui 式的 callback lambda 可能触发分配；`std::unordered_map` 的 rehash。这个维度的收益通常较小（几微秒级），在消灭了更大的瓶颈后再考虑。

**对应策略**：P3 优先级

### 4.3 优化决策树

面对任何 UI 性能问题，按这个顺序判断——这个顺序本身就是按"投入产出比"排的：

```
1. 能不做吗？        → 裁剪、虚拟化、跳过不可见区域（收益最大）
2. 能少做吗？        → 脏检测、缓存、只更新变化部分
3. 能做更快吗？      → 批处理、减少状态切换
4. 能异步做吗？      → 后台线程/Jobs 池、延迟提交
5. 能不分配吗？      → 对象池、预分配、零分配热路径
```

### 5.4 QmUI 当前可分析状态

当前仓库已经有 QmUI perf 数据，不能再写成“无法分析”。`src/game/client/QmUi/QmRt.cpp` 已经记录了：

- `perf/ui_runtime tree_begin_frame`
- `perf/ui_runtime anim_advance`
- `perf/ui_runtime render_bridge_begin_frame`
- `perf/ui_runtime tree_end_frame`
- `perf/ui_runtime ui_runtime_total`
- `perf/ui_runtime` JSON summary：`event=ui_runtime operation=... nodes=... anim_ms=... active_anims=... queued_anims=... render_bridge_ms=... duration_ms=...`

`qmclient_scripts/perf` 也已经把 `perf/ui_runtime` 解析为 `UI Runtime` 归因，输出 `operation`、`nodes`、`active_anims`、`anim_ms`、`render_bridge_ms`、`queued_anims`。因此，QmUI 已经可以回答“runtime 总成本、动画成本、render bridge 成本、节点数是否异常”。

QmClient 设置页也已经有独立 `perf/qmclient` 归因：tab 级 stage 包括 `tabbar`、`active_tab_total`、`visual_tab_total`、`function_tab_total`、`hud_tab_total`、`contributors_tab_total`、`config_tab_total`、`render_total`、`settings_total`；模块级统一使用 `模块总计`，模块身份靠 payload 里的 `module`、`tab`、`column`、`collapsed`、`search` 区分。这里不需要再引入“每个模块一个 stage 名”，真正的缺口是结构化字段与逐帧对齐。

剩余缺口是更深一层：

- `perf/qmclient` 当前没有真实 frame：wrapper 没传 `IClient *`，导致 `QmPerfFrameId(nullptr)` 返回 0，无法和 `perf/ui_runtime` / render / frame-time 对齐
- `subtab`、`module`、`widget_scope` 这类 QmClient/QmUI 归因字段
- `layout_ms` 的统一来源
- `draw_calls`、`clip_pushes`、`flush_count`、`flush_reason`、`vertex_count` 这类更接近渲染提交成本的字段
- CUI / QmUI 混合页面里“谁在主导这帧”的统一归因
- 非 settings runtime 事件的 page / operation 标注需要更稳定，避免出现无法归因的 `operation=unknown`

因此，QmUI 在本轮里不应再被归纳为单一的 `DrawCard overdraw`，也不应说“不能分析”。正确说法是：已有 runtime 级日志可分析，下一步先修 `perf/qmclient` frame 对齐，再补 subtab/module/widget 与 layout / draw-call / clip / batch 字段来支持更细优化。
### 5.5 哪些是根因，哪些是表象

**根因**（优化这些能从根本上减少工作）：
1. Language cache、checkbox/slider label、Tee preview key 这类首帧/热路径同步 CPU 工作（维度 4/5：重复创建、重复分配）
2. 视口外 section / 重列表 / 重 tab 仍在用户可见帧执行过多 widget 和列表工作（维度 1：做了不该做的事）
3. 文本池覆盖不足、已缓存文本首帧集中冷创建（维度 4：没缓存该缓的，或缓存没有提前/摊销）
4. 目标操作窗口内的同步 tab 内容重建和 online Esc 首帧 stage 未拆细（维度 1/4：同步工作集中在用户可见帧）
5. 预热路径本身未证明收益，且部分 UI 预热会写布局/交互相关状态；不能继续用强预热替代源头降温

**表象**（优化这些只能掩盖问题）：
1. FBO cache miss（真正的问题是为什么要重建，而不是为什么没缓存）
2. p99 高（真正的问题是尖峰帧是从哪来的）
3. `settings:tee / Work Drain` 超大耗时（这是后台 drain/session 归因热点；没有同帧 FPS/window 证据时，不得写成卡顿根因）

## 6. 优化策略

> 每个策略包含：对应维度、现状（代码实际）、改法、量化字段（设计意图）、预期收益

### 6.1 策略 A：设置页文本池覆盖与首帧摊销（对应维度 4）

**现状**：文本池基础设施已经存在，不需要重建一套系统。

- `SettingsTextElement(Page, Tab, TextId)` 返回稳定 `CUIElement`，key 来自 `settings:<page>:tab:<tab>:text:<id>`。
- `DoSettingsLabelStreamed()` 走 `CUIElement` 文本容器复用路径，并能在 active scope 内统计 `text_new` / `text_reused`。
- `InvalidateSettingsTextPool()` 会在语言、字体、后端、窗口/scale、配置 hash 等 invalidation reason 下清空文本池。
- 当前已接入的代表路径包括 General 标题、Language 列表、Tee `Name` / `Clan`、DDNet 静态标题、TClient 部分标题、QmClient 部分模块标题。
- 当前缺口不是“没有文本池”，而是覆盖率不足、首帧集中冷创建、以及 scoped telemetry 只覆盖部分页面/section。

```cpp
// 改前（每帧重建 text container）：
Ui()->DoLabel(&LabelRect, aLabelText, 10.0f, TEXTALIGN_ML);

// 改后（复用 text container，只在文本变化时重建）：
CUIElement &El = SettingsTextElement(SETTINGS_TCLIENT, TAB_GENERAL, "my_label");
DoSettingsLabelStreamed(El, &LabelRect, aLabelText, 10.0f, TEXTALIGN_ML);
```

**改法**：

1. 继续把静态 label、section 标题、稳定说明文字迁移到 `SettingsTextElement()` + `DoSettingsLabelStreamed()`。
2. General / Graphics / Sound / DDNet 基础页里的静态 checkbox label 已先接入 settings text pool；下一步再处理 slider label、TClient/QmClient 重页和更多动态控件。
3. `PrepareLanguagePageCache()` 已改为 standalone Language 页强制准备、General 页语言选择区域按固定文本预算分帧创建；普通 settings 首开不再同步创建所有语言 label。
4. 动态值、输入框内容、玩家名、皮肤名、实时状态、hover-only 且样式变化复杂的 tip 不进第一批。
5. 对 General / TClient / QmClient 的首个可见帧做文本池预热或分帧创建，避免 `text_new` 在用户可见首帧集中爆发。
6. 把 `CScopedSettingsTextPerfStats` 扩展到主要 settings 页面/section，使 `text_new` / `text_reused` 能用于全页面验收，而不是只看局部样本。

**量化字段**（已部分实现，仍需扩大覆盖）：
```
text_new=N       # 本帧新创建的 text container 数
text_reused=N    # 本帧复用的 text container 数
```

**验收口径**：

- 稳定帧：已接入页面的 `text_new=0`，`text_reused>0`。
- 首帧：`settings_open` / `settings_tab_switch` 不应因 `text_new` 集中创建出现 >33ms 长帧。
- 缓存失效：语言、字体、UI scale 或配置 hash 变化后允许重新创建；普通滚动和 tab 重绘不应清空文本池。

**预期收益**：稳定帧每 section 0.5-2ms；对 General 首开、Language cache 首帧和控件 label 密集页，收益取决于预热/摊销是否能把创建移出首个可见帧。改动量小到中等，风险低到中等（dirty/invalidation key 必须完整）。

### 6.2 策略 B：视口外 section 跳过 widget（对应维度 1）

**现状**：`CScrollRegion` 做 scissor 裁剪（GPU 端），但 CPU 端仍走完所有 widget 函数。即使 section 完全在视口外，依然执行布局、文本容器创建、`DoButtonLogic`。

**改法**：在 section 级别增加可见性判断。如果 section 完全在视口外（加上预取边距），只保留高度信息，跳过所有 widget 调用。

```cpp
// 伪代码
if(!SectionRect.IsIntersecting(ViewportRect, PrefetchMargin))
{
    pSection->SkipRenderHeight = pSection->CachedHeight;
    return; // 不调任何 widget
}
```

**量化字段**（C++ 侧待实现）：
```
sections=N         # section 总数
sections_visible=N # 可见 section 数
```

**预期收益**：视口外 section 节省 80%+ CPU。多 section 页面（如 General）节省 5-15ms。改动量中等（~30 行/页面），风险中等（需确保高度测量正确）。

### 6.3 策略 C：列表虚拟化（对应维度 1）

**现状**：Tee 皮肤列表已有可见范围渲染，但在进入可见循环前仍全量遍历 `SkinList.Skins()` 统计 ready 状态，并为每个 skin 构建 `SSettingsTeeListPreviewCache::Key(...)` 的 `std::string`；可见项循环又重复构建一次 key。

**改法**：

1. 把 ready/preview 状态统计改为基于可见范围 + 小 overscan，非可见总量只在 dirty 时更新 summary。
2. 将 preview cache key 改成零堆分配或预计算结构：例如 fixed buffer lookup、stable hash key，或把 key 缓存在 skin list entry 的颜色/emote dirty key 下。
3. 列表过滤、排序、ready 计数和 UI 渲染拆成不同 dirty key；滚动帧只处理可见行。

**量化字段**（C++ 侧待实现）：
```
rows_total=N     # 列表总项数
rows_visible=N   # 可见行数
rows_rendered=N  # 实际渲染的行数
rows_skipped=N   # 跳过的行数
```

**预期收益**：含 100+ 项列表节省 8-20ms，并减少切 Tee / 首帧的堆分配尖峰。改动量中等，风险中等（需确保高度计算、选中项滚动和 preview cache 命中正确）。

### 6.4 策略 D：后台资源 drain 积压限制（对应维度 5）

**现状**：`IDLE_DRAIN` 模式后台请求预算已收紧到 8，但"健康进展"时仍可能继续扩大 backlog。可见区项本身仍然优先，但在一次大跨度滚动已经制造出大量历史 `BACKGROUND_REQUESTED` 后，后台 drain 仍会继续推进积压。`work_drain` 日志用于暴露后台队列吞吐和 session 汇总问题；它不应被单独解释为主线程卡顿。

**改法**：
1. 保持 `IDLE_DRAIN` 当前后台请求预算 8，不再重复做“降到 8”任务
2. 在 `SettingsSkinBackgroundRequestBudgetDecision` 中增加硬 backlog 上限：`HardBacklogLimit = max(CountFuseLimit, DefaultBudget * 8)`，超过即阻塞
3. 收紧"健康进展"的判断条件：必须 loaded 和 admitted 的 delta 都 ≤ 0 才允许继续扩大 backlog

**量化字段**（已有，需要强制按后台吞吐/队列健康语义解读）：
```
event=work_drain page=settings:tee kind=merge count=N bytes=N dur_ms=N stop=pending|backpressure|budget
```

**预期收益**：限制后台请求积压和 session drain 极端归因值，降低它和交互窗口重叠的概率。它不是当前 settings-only 卡顿主线；验收时必须额外确认目标操作窗口的 `fps_summary` / frame-time 是否改善。改动量中等（集中在 `settings_resource_jobs.cpp`），风险：需要验证不会导致皮肤列表加载过慢。

### 6.4.1 策略 D2：预热系统收敛为可证明收益的 idle work

**现状**：`PrewarmVisibleSettingsResources()` 同时做资源请求和 UI `PrewarmOnly` 渲染。它有 idle gating，但 UI 子树没有统一 CPU 时间预算；部分路径还会写 section 高度缓存或 QmClient 布局状态。资源 jobs / skins pipeline 已经有后台 request budget、count fuse、GPU upload limiter、merge/finalize budget，不能笼统说“预热都没有限制”；缺限制的是 UI 子树预热和主线程批处理。继续“强预热更多页面”会把同步工作提前集中，容易复现 CPU 卡死。

**改法**：

1. 预热分成两类：资源 job 预热和 UI cache 预热。资源 job 走现有 VISIBLE/PREFETCH/BACKGROUND、GPU upload 和 frame budget；UI cache 预热必须单独有 CPU budget。
2. UI 预热只允许写明确 cache，禁止写交互状态、用户配置、展开/拖拽状态；必须写布局高度时，cache key 要包含 viewport、UI scale、语言、字体、配置展开状态和 scroll 相关输入。
3. `PrewarmOnly` 路径要逐页对齐真实首帧。不能覆盖真实重路径的预热项要么补齐，要么从“收益预热”列表移除。例如 QmClient Config tab 当前跳过 `RenderSettingsTClientConfigs()`，不能声明覆盖 Config 首帧。
4. 新增或复用 telemetry 记录 `prewarm_attempt` / `prewarm_ready` / `prewarm_cost_ms` / `first_use_hit` / `first_use_saved_ms`。没有同路径 A/B `fps_summary` 改善的预热不作为性能优化保留理由。

**验收口径**：预热不能只看 ready 日志或 work drain；必须比较开启/关闭预热时同一目标操作窗口的 `frame_ms_p95/p99/max` 和 spike count。若预热降低不了 `settings_open` / `settings_tab_switch` / `ingame_esc_open` 的 frame-time，就应削减或改成更小的 demand-driven 预取。

### 6.5 策略 E：Section 内 Quad 批处理（对应维度 2）

**现状**：`DoButton_Menu()` 内部：`RenderQuadContainer`（背景）+ `RenderTextContainer`（文字）= 每次 2 draw calls。一个 section 10 个 button = 20 draw calls。

**改法**：收集 section 内可以安全合并的 quad 到 `CUIElement` 批处理容器，尽量减少提交次数，但**不能改变现有的 immediate-mode 语义**。硬约束如下：

- 不改变原始提交顺序
- 不跨 `clip/scissor` 区间重排
- 不跨 text/quad 层级边界重排
- 任何批处理都必须保持 hover、边框、背景、文字的可见结果一致

**量化字段**（C++ 侧待实现）：
```
draw_calls=N  # 本帧 draw call 数
```

**预期收益**：每 section 0.3-1ms。改动量中等（~100 行 helper），风险中等（需确保顺序和裁剪正确）。

### 6.6 策略 F：布局脏检测（对应维度 4）

**现状**：section 高度、列宽、可见范围等布局输入每帧重算。单个 `HMargin`/`VSplit*` 成本很低，但累积到几十个 section、上百个 widget 时不可忽略。

**改法**：缓存 section 高度、列表行高、列宽、可见范围和静态文本测量结果。dirty key 至少包含：viewport 宽高、UI scale、语言/文本、字体大小、配置展开状态。不缓存每个普通 rect split 的中间结果（维护成本 > 收益）。

**量化字段**（C++ 侧待实现）：
```
layout_dirty=0/1          # 本帧是否重算了布局
dirty_reason=width_changed|lang_changed|config_changed|...
```

**预期收益**：多 section/大列表页收益明显。改动量中等（按 section），风险中等（dirty key 必须完整，否则会出现 stale 布局）。

### 6.7 策略优先级总结

说明：这里不是纯待办表。A / B2 / B3 / B4 / D2 / F 已经有部分代码落地；C / D / E 也都有前置实现或局部落地，但都还没到“完整验收完成”的状态。

## 7. 量化系统设计

> 本章描述的是量化系统的**设计意图**，不是进度报告。已实现的部分标注了"✅"，待实现的部分是设计目标。

### 7.1 设计目标

量化系统回答三个问题：
1. **哪里慢？** — 把一帧的耗时归因到具体的 stage（页面切换、列表处理、资源 drain、section 渲染）
2. **有多慢？** — p50/p90/p95/p99 百分位 + 尖峰帧检测 + 超标判定
3. **比以前好了还是差了？** — 同路径同环境的前后对比

两个层次的指标不能互相替代：
- **内部 perf 字段**（`duration_ms`、`stage`、`page`）：归因用，回答"哪里慢"
- **无上限 FPS**（`avg/max/min FPS`）：体感用，回答"用户觉得快了吗"

### 7.2 采集层（C++ 侧）

#### 阈值

当前客户端使用 **1ms** 作为默认采样阈值（`qm_perf_debug_threshold_ms 1`）。只有耗时超过阈值的 `LogPerfStage` 调用才会写入日志。阈值越低，捕获的长帧越完整，但日志量越大。

设计建议：
- 开发/自测期间：1ms（捕获所有超出 UI 预算的帧）
- 用户反馈收集：4ms（平衡信息量和日志量）
- 不应写死为固定值，保留配置项灵活性

#### 结构化字段

需要新增的最小字段集（按优先级排序）：

**P0 — 阻塞了最有价值的归因分析：**

```
# 页面切换事件
event=page_switch page=... from=... to=... dur_ms=...

# 列表帧事件
event=list_frame page=... items_total=... rows_visible=... rows_rendered=... rows_iterated=... rows_skipped=...

# Section 渲染事件
event=section page=... section=... dur_ms=... visible=0/1 dirty=... text_new=... text_reused=...

# 工作排空事件
event=work_drain page=... kind=merge/finalize/upload/publish count=... bytes=... dur_ms=... stop=...

# 操作路径 FPS 摘要（不是每帧事件，是操作结束后输出一次；已实现，字段应保持兼容）
event=fps_summary operation=... context=offline|online page=... tab=... sample_frames=... sample_seconds=... fps_avg=... fps_min=... fps_max=... frame_ms_avg=... frame_ms_p95=... frame_ms_p99=... frame_ms_max=... menu_ms_max=... cap_limited=0/1
```

`fps_summary` 的操作窗口已经覆盖 `settings_open`、`settings_tab_switch`、`settings_subtab_switch`、`settings_tee_scroll`、`ingame_esc_open`。其中 `settings_open` / `settings_tab_switch` / `settings_subtab_switch` / `ingame_esc_open` 是 30 帧 fixed window；`settings_tee_scroll` 是从滚轮输入开始，到 250ms 无滚动后结束的 scroll window。Report 的目标设置页结论必须读取 `targetSettings.verdict`，不能用顶层混合 `verdict` 代替；`server_browser`、`internet`、`work_drain` 只能作为背景热点/归因参考。

当前实现中，缺少 target `fps_summary` 会让 report 显示“不足以验收”；缺少 online 覆盖目前是 `quality.warning`，不会直接让 `targetSettings.verdict` 失效。当前 online 覆盖检查是“至少一个 online target window”，不是严格要求 `ingame_esc_open`；如果后续要把游戏中 Esc 作为硬验收项，需要单独改 quality 规则。

`targetSettings.p99` 当前是对各目标 `fps_summary.frame_ms_p99` 再计算百分位，不是对所有原始帧重新汇总；`targetSettings.spikeCount` 当前是 `frame_ms_max > 16.67ms` 的目标窗口数，不是原始尖峰帧数。对单个窗口的原始帧级判断仍应看该窗口自身的 `frame_ms_p95/p99/max`。

**P1 — QmUI 单独归因：**

```
event=ui_runtime page=... operation=... subtab=... module=... widget_scope=... nodes=... layout_ms=... layout_dirty=0/1 dirty_reason=... anim_ms=... active_anims=... render_bridge_ms=... draw_calls=... clip_pushes=... flush_count=...
event=qmclient page=... operation=... frame=... subtab=... module=... stage=... duration_ms=... search_len=... visible_count=... snapshot_pending=...
```

QmUI 走的是 `CUiRuntimeV2`（tree + layout engine + animation runtime + render bridge），不能把它的成本和 CUI 的 `DoLabel`/`DoButtonLogic` 混在同一个字段里。当前 `QmRt.cpp` 已经有 `perf/ui_runtime` runtime/anim/render bridge 摘要；缺的是 subtab/module/widget 级归因、draw/clip/batch counters，以及 `perf/qmclient` 的真实 frame 对齐。
