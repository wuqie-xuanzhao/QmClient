① 第一性原理：UI 性能优化的本质

这一章解释为什么要这样优化。原理不变，代码会变。

1.1 一帧里到底发生了什么

DDNet 每一帧要做两件事：游戏渲染（世界、实体、特效、HUD）和菜单渲染（设置页、服务器列表等）。这两件事跑在同一个线程里，共享同一帧的时间预算。

Frame Time = CPU 提交 + GPU 绘制 + 同步等待
           = (布局计算 + 文本创建 + 输入检测 + 状态更新 + Draw Call 提交)
           + (顶点处理 + 光栅化 + 像素着色 + 混合)
           + (SwapBuffers / v-sync + 驱动同步)

一帧 16.67ms (60Hz)
├── 游戏渲染：8-12ms
├── 菜单渲染：2-4ms（正常稳态）
└── 剩余：给下一帧

当菜单渲染突然从 2ms 涨到 200ms，这一帧就"爆了"——游戏画面停顿，
玩家感受到卡顿。优化目标不是让菜单"更快"，而是让它不要突然变慢：
消灭尖峰帧，保持帧时间稳定。

这是理解整个系统的第一性原理：优化的对象不是"平均 FPS"，而是帧时间的尾部稳定性。一次 50ms 的卡顿远比 10 次 5ms 的微波动更影响体验。

1.2 immediate-mode 与 retained-mode 的根本取舍

UI 渲染架构在两种模式间选择。理解这个取舍是判断"哪些优化适用"的前提：

维度immediate-mode（CUI / Dear ImGui 系）retained-mode（React / Qt 等通用对照）
状态归属调用方持有，UI 系统每帧从头重建绘制描述UI 系统持有节点树、布局、动画状态
每帧成本O(all visible) —— 即使 90% 不可见也会跑 widget 逻辑O(changed) —— 只在 model change 时重算位置
优势无需预先规划、无状态同步问题、无 invalidation bug可做跨帧缓存、动画运行时、render bridge 批处理
劣势必须靠外部手段（视口裁剪、虚拟化、文本池、脏检测）把成本降到 O(visible)状态一致性维护成本高，retained 树本身也是每帧 CPU 成本
重要澄清（2026-06-14 代码核对）：QmUI（CUiRuntimeV2）不是 retained-mode。代码证据：UiButtons.cpp 注释直接写 Wraps CMenus::DoButton_Menu，内部全部调 Ctx.m_pUi->DoLabel() / Ctx.m_pMenus->DoButton_Menu() / Ctx.m_pUi->DoButtonLogic()（CUI 底层 API）；CUiV2RenderBridge（QmRender.cpp）只做 BeginFrame / RecordDrawCall / RecordClipPush / LastFrameStats——只计数，不绘制；m_Tree 每帧 BeginFrame/EndFrame（immediate）。QmUI 实际是：CUI 底层 immediate-mode 封装层 + 动画运行时（CUiV2AnimationRuntime，唯一跨帧状态，缓存动画值）+ token 设计系统（ui_token::color/radius/font）+ 帧级 render bridge 计数。底层都走 CUI 的 DoLabel/DoButtonLogic，不存在 retained 树维护成本。

对 QmClient 的含义：设置页跑在 CUI（immediate）和 QmUI（CUI 封装 + 动画运行时）两套调用风格上，但底层都走 CUI。perf/ui_runtime 能拆出 tree_begin/end、anim_advance、render_bridge、ui_runtime_total 四段，可观测 QmUI 的动画与 render bridge 额外开销。归因时按"纯 CUI 路径"和"QmUI 封装路径"分流即可。

1.3 DDNet/QmClient 的架构约束

DDNet 是 2D 俯视角 sprite 游戏，决定了哪些"通用优化"不适用：

  • 所有渲染通过 quad + sprite + texture 完成，没有后处理链（bloom / motion blur / SSAO）。
  • UI 和游戏渲染共享同一个 GL/Vulkan context，共享帧预算。
  • 菜单渲染不是独立线程，发生在 CMenus::OnRender() 中。
  • FBO / recorded render target 在设置页侧已清理完毕，本轮不再回到纹理录制式页面缓存（2D UI 的 FBO 创建+录制+blit 成本 1-3ms 常高于实时渲染 0.3-0.5ms）。
  • 文本渲染走字形图集（CTextRender + atlas），首次出现新字形会触发 atlas 扩容 + 全量纹理重传——这是中文界面首帧卡顿的根因之一。

1.5 优化决策树

面对任何 UI 性能问题，按投入产出比顺序判断：

1. 能不做吗？   → 裁剪、虚拟化、跳过不可见区域（收益最大，维度 1）
2. 能少做吗？   → 脏检测、缓存、只更新变化部分（维度 4）
3. 能做更快吗？ → 批处理、减少状态切换（维度 2）
4. 能异步做吗？ → 后台线程/Jobs 池、延迟提交（维度 5）
5. 能不分配吗？ → 对象池、预分配、零分配热路径（维度 6）

1.6 immediate-mode 的缓存悖论与解法

核心洞察：immediate-mode GUI 天生没有缓存——每帧从头重建。但它仍然需要一个轻量的 retained 缓存来避免每帧 heap churn 和重复的文本布局计算。Dear ImGui 内部就为每个 widget 维护一个稳定的 ID 字符串，渲染好的文本布局（glyph 位置、断行、font metrics）存在一个短生命周期的容器里。当 widget 的 ID 或文本内容变化时缓存失效，否则复用。

这正是 m_MenuTextPool 的设计依据：它是一个"immediate-mode 之上的显式 retained 缓存层"，用六元组 key（scope/page/tab/subtab/text-id/style fingerprint）标识每个稳定文本，跨帧复用 CUIElement 文本容器。这是在 DDNet CUI immediate-mode 架构约束下，把"少重建"（维度 4）落地的标准做法。

② 架构与全局调度工作流

当前主线不是单点优化，而是一套分层调度系统。这条链路是当前架构的主流程；所有页面级优化都必须能落到这条链路的某一层，而不是单独写一个局部补丁。

loading/prewarm (budget-bounded, recoverable) -> plan collection cursor (collect descriptor only: scope/page/tab/subtab/key/style) -> prebuild cursor (build real CUIElement by token, skip m_Built) -> visible guard (reuse only; record miss/stale, no first-build) -> visible-ready presentation (assets: ready-then-show or stable skeleton) -> background jobs (demo meta / skin / decode / upload / preload: leftover tokens only) -> telemetry emit (text_prebuild / text_usage / adaptive_budget / visible_preflight) -> report + quality gate (targetSettings verdict, not mixed verdict) -> acceptance decision

一句话：loading 阶段允许预热但必须可预算、可恢复、可观测；可见阶段只复用、不首建；后台工作只能吃剩余预算；报告只认目标窗口，不认"看起来不卡"。

2.1 全局不变量（跨层约束）

  1. remaining=0 只表示某一层计划完成，不表示整个页面已通过验收。
  2. targetSettings 仍然是稳定文本的唯一验收源；顶层混合 verdict 不替代它。
  3. 可见阶段只复用稳定文本容器，不允许首建，也不允许 stale entry 现场重建。
  4. 资源预热与 UI cache 预热是两条不同的链路：资源走 VISIBLE/PREFETCH/BACKGROUND + GPU upload 预算；UI cache 走 plan collection + prebuild 游标。
  5. 后台工作（demo metadata / skin loading / resource decode / upload / preload）只能吃 adaptive budget 的剩余 token，不能抢占 visible。

策略 D2：预热系统收敛为可证明收益的 idle work（维度 4/5）gap

⑥ 量化模型与 baseline

6.1 分层帧时间目标

DDNet 是快节奏平台游戏，流畅性要求高于一般应用。p99 比平均值重要得多：一次 50ms 的卡顿远比 10 次 5ms 的微波动更影响体验。优化应优先消灭"尖峰帧"。

指标目标值理由
UI 帧时间均值≤ 4ms为游戏渲染留足 12ms+ 预算（60fps）
交互帧（切 tab / 滚动）≤ 8ms不超过 120Hz 刷新周期
最差帧 p99≤ 16ms不超过 60Hz 周期；超出即用户可感知卡顿
首帧（冷启动进入设置页）≤ 33ms允许一次较长帧，但不能连续两帧超标

6.2 尾部指标论证

量化系统必须同时描述平均吞吐和尾部体验。对滚动列表和首屏切 tab 场景，尾部比均值更重要。

指标用途状态 / 解释
fps_avg整体吞吐已采集 只能看大致是否偏慢
fps_min / frame_ms_max绝对最差点已采集 帮助发现首帧或极端阻塞，但会被单个离群值放大
frame_ms_p95 / p99尾部分布已采集 当前 report 主线
1% low尾部体验gap 以最慢 1% 帧的平均值反推 FPS，直接反映滚动/翻页/打开面板的"掉帧感"。皮肤列表滚动必须纳入
scroll recovery交互恢复部分 PostScrollRecoveryFrames 帧计数器已广泛落地用于预算控制；但恢复耗时（ms）未采集到 report，无法量化"滚动停止后多久恢复稳定帧"
外部依据：1% 和 0.1% low 量化卡顿，比 avg FPS 更重要——avg FPS 是 deeply flawed metric，constant smooth 120 avg FPS 优于波动的 60 avg（SuperTuxKart 开发博客论证）。本项目应把 1% low 提升为一等指标。落地口径：fps_summary 继续保留 avg/min/max/p95/p99，同时增加 frame_ms_1pct_low；scroll window 增 scroll_recovery_ms。

#结论外部依据对本仓库的含义
1 UI 优化核心是少提交、少切换、少重建；FBO 是高级技巧不是基本策略 Dear ImGui 文档强调批处理、零分配、clipper 虚拟化 先做源头降温（维度 1/4/5），再考虑缓存
2 immediate-mode UI 性能关键在于每帧只做 O(visible) 工作 ImGui ListClipper（处理 586k 项只渲染可见行 + 小 overscan 的标准实践）；Wikipedia「Immediate mode (computer graphics)」——immediate-mode 中"屏幕整体每次都从头渲染" 列表虚拟化 + visible guard 优先于任何缓存（维度 1）
3 immediate-mode 内部仍需轻量 retained 缓存避免 heap churn；widget 用稳定 ID 字符串标识，渲染好的文本布局存在短生命周期容器，glyph 数据在持久纹理 atlas 「Immediate Mode GUI Is A Mirage」（geoffprewett）；Hacker News immediate-mode 讨论；Reddit r/cpp「Proving Immediate Mode GUI's are Performant」 这正是 m_MenuTextPool 的设计依据：immediate-mode 之上的显式 retained 缓存层，用六元组 key 跨帧复用文本容器
4 retained-mode 只在 model change 时重算，但状态一致性维护成本高 Hacker News / StackOverflow immediate vs retained 讨论 通用原理；QmUI 不是 retained，是 CUI 封装 + 动画运行时
5 1% low / 0.1% low / p99 比 avg FPS 更能反映流畅度。avg FPS 是 deeply flawed metric——constant smooth 120 avg FPS 优于波动的 60 avg SuperTuxKart 开发博客「Why average FPS and 1% low FPS are misleading」；ASUS ROG「What are 1% Lows?」；Android Game developer docs 把 P99 FPS（1% percentile）定义为 stutter indicator；HowToGeek「Why 1% Lows Matter」 把 1% low 提升为一等指标（P0 落地）
6 60fps = 16.67ms/帧，120fps = 8.33ms/帧。p99 比平均帧时间更能反映流畅度 Wikipedia Frame Rate；游戏行业标准 p99 ≤ 16ms 为目标
7 FBO readback 是同步阻塞点，强制 GPU pipeline flush Khronos OpenGL Wiki 已删除 FBO 的另一个原因，不回退
