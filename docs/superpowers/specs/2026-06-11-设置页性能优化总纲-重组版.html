摘要

设置页当前的主问题已经收敛到：settings:tclient、settings:qmclient 与 ingame_esc_open 的可见阶段 CPU 尖峰。general / language 仍是文本热点，但已经不是主线矛盾。最新体感和日志都说明：只做局部 settings 文本池、只补少量热点 label，无法解决 TClient / QmClient 首切和游戏中菜单打开的长帧。

本轮路线图因此调整为：建立 CMenus 级通用菜单文本池，先只在 settings 作用域启用，把 settings 内文本内容与样式都稳定的 UI 文案统一迁移到同一套池化、失效、预构建和缺口日志机制。旧的 m_SettingsTextPool 只能视为过渡雏形，不再作为设计边界；可见页命中不到稳定文本池项或命中 stale 池项时，视为 coverage bug，而不是接受“可见阶段分帧补齐”。Tee 和后台 work_drain 只作为背景健康信号；Vulkan / OpenGL 后端优化只在渲染提交本身成为主因时才进入。

范围

  • 设置页全部 tab 的冷启动、切 tab、切子 tab、滚动
  • Tee 皮肤列表与其后台工作队列
  • 游戏中按 Esc 打开菜单的 settings 路径
  • 设置页量化系统与 report 归因

不把 server browser、internet/offline 热点、demo browser 作为 settings-only 达标主证据。

现状映射

本节吸收原 docs/superpowers/explore/2026-06-12-设置页预热与列表渲染现状映射.md 的结论，并按当前工作区代码重新校正：文本池、启动预热、section 级渐进渲染、局部视窗裁切、后端能力分流和 GPU 上传限流都存在；但“统一 helper 文本池”和“通用 item 级列表虚拟化”仍不能视为已经完成。

说法 当前判断 实际代码锚点 与总纲关系
设置页 / 菜单页首次打开前预构建标题、标签和 helper 文本 部分存在：已有 m_SettingsTextPool、SettingsTextElement()、DoSettingsLabelStreamed() 与 loading 阶段文本预构建，但作用域仍偏 settings label/title 和少量热点登记，不是菜单级 helper 文本池。 src/game/client/components/menus.cpp、src/game/client/components/menus_settings.cpp、src/game/client/components/tclient/menus_tclient.cpp、src/game/client/components/qmclient/menus_qmclient.cpp 支持 P0/P1：把 settings 局部池升级为 CMenus 级通用菜单文本池，先只开放 settings scope。
进入游戏前先做 settings 相关预热 明确存在：启动流程会进入 PrewarmSettingsRuntimeCachesDuringLoading()，通过 loading 画面 pump 文本和资源预热；但它不是整个菜单系统的统一 cold-start 预热图。 src/game/client/gameclient.cpp、src/game/client/components/menus.cpp 保留现有 loading 预热，但总纲要求稳定文本首建继续前移，不允许可见 settings 页面补洞。
大列表只保留可见窗口附近项活跃 不能算完整实现：当前有滚动区、section 级优先级、cached height 和局部 cull，但没有通用 visible range / item recycler / row provider 抽象。 src/game/client/components/section_loader.h、src/game/client/components/section_loader.cpp、src/game/client/components/qmclient/menus_qmclient.cpp、src/game/client/components/tclient/menus_tclient.cpp 避免把 section loader 误写成“列表虚拟化已完成”；Tee 列表和重 tab 的 item 级成本仍在“仍待做”。
只在可见视窗内完整渲染，远区延后 基本存在：CSectionLoader 有 UNINITIALIZED / MEASURING / COMPACT / FULL 状态，ComputeViewportPriority() 区分 in / near / far，远区可复用 cached height 或只做测量。 src/game/client/components/section_loader.h、src/game/client/components/section_loader.cpp 作为 P2 的既有基础设施；后续重点是把重 tab 同步 CPU 和动态控件成本继续拆小。
可见性判断与布局脏检测避免全量重算 部分存在：section/config 级 dirty、runtime key、cached height、layout_dirty telemetry 已有；但不是完整 layout tree dirty propagation，也不是 item 级 dirty 系统。这部分结论仍成立，只是原文里的旧行号不再可靠。 src/game/client/components/settings_runtime_cache.cpp、src/game/client/components/section_loader.cpp、src/game/client/components/tclient/menus_tclient.cpp 总纲中仍保留“section / module 同步 CPU 收口”，不能只靠文本池宣称完成。
OpenGL / Vulkan 后端按能力分流并走 buffering / specialized path 明确存在：后端 capability、tile/quad/text buffering、OpenGL/Vulkan 专门实现和提交路径分支都存在；但它们当前不是 settings-only 的首要矛盾。 src/engine/client/graphics_threaded.h、src/engine/client/graphics_threaded.cpp、src/engine/client/backend_sdl.h、src/engine/client/backend/opengl/backend_opengl3.cpp、src/engine/client/backend/vulkan/backend_vulkan.cpp 维持 P3 条件性方向：只有 render_bridge、draw_calls、flush 成为主因才进入。
上传限流 / 分帧上传避免 GPU 上传打满一帧 明确存在：CGpuUploadLimiter 每帧重置预算，资源热点路径上传前可检查 CanUpload()；它解决上传抖动，不等同于完成 UI 首开性能。 src/engine/client/gpu_upload_limiter.h、src/game/client/gameclient.cpp、src/game/client/components/skins.cpp、src/game/client/components/menus_settings_assets.cpp 放在背景健康信号；不要用上传限流结果替代 settings / ingame Esc 目标窗口验收。

当前结论：基础设施不是从零开始，但剩余风险集中在“统一稳定文本 coverage”和“section / module / list 同步 CPU”。因此本文保留文本池优先、section/module 其次、backend 条件进入的排序。

判断顺序固定：先看 settings / ingame Esc 目标窗口，再看 Tee / work_drain 背景热点，最后才考虑 backend 提交路径。

验收口径

  1. 只用 settings / ingame Esc 的目标窗口判定 settings-only 结论，不再用 server browser、internet/offline 或 work_drain 代替。
  2. 目标窗口必须有 fps_summary，并且 report 读取 targetSettings.verdict，不是顶层混合 verdict。
  3. 如果某个窗口里 render_bridge、draw_calls、flush 不是主因，就不要把优化方向提前切到 Vulkan / OpenGL；先把可见页文本首建彻底移走。
  4. 如果 perf/qmclient 仍然没有真实 frame，就先补帧对齐，再谈 QmUI / QmClient 的细粒度重构。
  5. 文本池构建只能发生在不可见阶段；可见页命中不到稳定文本池项或命中 stale 池项时，必须记录 scope / page / tab / subtab / key / reason，并视为 coverage 缺口，而不是接受“分帧补齐”。checkbox、slider 等高频 helper 也必须显式携带 subtab，不能依赖人工 key 命名隐式区分。
  6. 除 miss/stale/prebuild remaining 外，还必须有文本池利用率调查口径。针对目标设置页窗口，report 或 summary 至少要能回答：候选总数多少、命中多少、复用多少、miss 多少、hit rate / reuse rate 各是多少，以及它们与 text_new / text_reused 是否一致。
  7. 稳定文本候选审计必须扫描原始 UI API、settings wrapper 和 QmClient helper / 变量路径；QmNewFeatureLabel、RainbowColor、DoModuleHeadline 必须显式进入候选和 allowlist，不能被过滤器静默跳过。
  8. m_SettingsTextPool 不再是最终设计边界；最终方案是 CMenus 级通用菜单文本池，settings scope 先启用，后续如要扩到其它菜单再单独验收。
  9. settings_text_miss、settings_text_stale 或目标窗口前预构建仍有 remaining 时，report 必须把 targetSettings 标为“不足以验收”，不能只显示正文 warning。
