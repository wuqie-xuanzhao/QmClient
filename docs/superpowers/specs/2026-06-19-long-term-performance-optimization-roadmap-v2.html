① 五大判断修正详解

v1 路线图基于"印象中的代码现状"做判断；v2 基于 SubAgent 实际读代码后的发现做修正。每个修正都有具体代码指针支撑。

修正 1：CUI 已实现 ImGui 60-70% 优化，不需要 retained node

v1 4.1.4 计划把 CUiV2Tree 扩展为可持久化 node 表（retained-mode）。但实际读代码发现：

  • CUi::RenderQuadContainerBatchable（ui.cpp:599-626）已实现 draw call 合并
  • CUi::QuadBatchRectContainer（ui.cpp:578-597）按 (w,h,rounding,corners) 缓存 QuadContainer
  • CUiScopedQuadBatch 提供 RAII batch scope
  • CListBox + CScrollRegion::RectClipped()（ui_listbox.cpp:116-136）已实现 list virtualization，且比 ImGui 原生 clipper 更强（支持变高行）
修正后方向：删除 v1 的 retained node 计划。QmUI 真正的三大短板是：(1) frame-local arena 缺失（QmLayout.h:100 用 std::vector 每帧分配）；(2) DrawCmd header 不统一（没把 ClipRect 纳入 memcmp，跨 clip 不能合并）；(3) 动态文本走"重建容器"（聊天、计时这种每帧变化的文本应该走 ImGui 风格 inline reserve/unreserve）。

修正 2：纯英文卡顿真因不在字符集

v1 把文本渲染卡顿主因归咎于"中文图集扩容"，建议"sparse atlas 化"。但 6/19 fresh log 显示 frameMsP99=299ms 时 backend/upload/glyph 各项全为 0，且纯英文 UI 也会卡顿。SubAgent 基于业界经验（ImGui FONTS.md、Hypersect 博客、Unreal Slate、Qt QTextLayout）锁定真因：

  • 最高嫌疑 每帧重建 text container / quad buffer（CPU 侧 alloc + memcpy）
  • 高匹配 Paragraph layout / wrap / word-break 每帧重算
  • 次要 Per-frame TextWidth 调用累积
  • 排除 GPU upload 同步阻塞（log 中 upload=0）；字形 atlas 全量重传（这是中文次因，不是英文主因）
修正后方向：放弃"sparse atlas 是答案"的预设。Phase C 文本优化按 ImGui 持久 buffer + Unreal dirty-cache 路线：(1) text container 加 dirty 标记 + (string,font,size,wrap) 缓存；(2) 持久 arena 分配器消除每帧 malloc/free；(3) 验证每帧 per-label TextWidth 调用是否累积。CJK 走 ImGui 1.92 动态字体系统的"按需增量扩展 atlas + 仅对新增 glyph 上传"路线。

修正 3：scheduler 是 menus-private 不是 service

v1 ⑧.7.3 提出 scheduler_coverage 口径，暗示"调度器在工作但没覆盖最重同步 UI"。实际读代码发现架构层面根本没接通：

  • grep gameclient.cpp 找 AdaptiveBudget / PrebuildSettingsMenuTextPool / DrainIngameUiTextRuntime —— 零结果
  • 所有调度逻辑封死在 CMenus 类内部（settings_resource_jobs.cpp:839 的 SettingsAdaptiveBudgetStep）
  • 4 份独立 state 字段（menus.h:2197-2201），命名硬绑场景：m_SettingsTextAdaptiveBudgetState / m_IngameTextAdaptiveBudgetState / m_AssetsAdaptiveBudgetState / m_DemoBrowserAdaptiveBudgetState
  • 每加一个新场景就要新加一个 state 成员

更重磅：RenderServerInfo（menus_ingame.cpp:1748-1759）每帧手工调用 ComputeSettingsUiFrameSchedulerBudget，但 token 唯一用途是 snapshot text 队列。同步渲染路径 DoIngameMenuLabel 系列本身不消费 token——即使 scheduler 拒绝发 token，可见 UI 那帧依然会执行实时 container build。

这就是 6/19 log 里"scheduler 在跑（eventCount=2478）但 frameMsP99=299ms"的根本原因——scheduler 在跑，但架构上根本管不到 immediate-mode 渲染路径。这不是"覆盖率不足"，是"架构没接通"。

修正 4：图形后端优化方向是 Vulkan 主战场（OpenGL 暂缓）

v1 把图形后端优化放在 Phase F 条件触发。用户判断"长期必然要优化，FPS 的提高需要它"——方向对。代码现状比 v1 假设的好得多，但仍有具体优化空间：

  • CGraphics_Threaded + backend_sdl.cpp:54 真有 graphics thread（CGraphicsBackend_Threaded::ThreadFunc，不是伪线程化，仅 Emscripten 退化）
  • Vulkan backend 5 项基础优化已实现：
    • ✅ 持久映射 ring buffer（backend_vulkan.cpp:7156 CreateStreamBuffer）
    • ✅ staging buffer + device local 两阶段上传（行 3305 + 3614）
    • ✅ 内存子分配器（SMemoryHeap，行 1825）
    • ✅ 多线程 command buffer 录制（行 7700 + 9113-9124，默认 on，但AMD GPU 强制 off）
    • ✅ 内置 frame profiler（行 7632-7666，未暴露到 perf report）
  • Vulkan 仍有具体优化空间（"已实现"≠"已最优"）：
    • 🔥 AMD GPU 单线程 fallback（行 9120-9124）：所有 AMD 用户被迫单线程录制，原因是"dynamic viewport usage"导致驱动崩溃。这是 Vulkan backend 最大杠杆
    • Descriptor set / Pipeline cache 优化（未量化）
    • HOST_CACHED vs HOST_COHERENT 按 GPU vendor 适配
    • pipeline 深度 2→3（9 处 WaitForIdle）
  • Vulkan 同步原语全在非帧热路径（纠正 6/18 误判）：
    • vkQueueWaitIdle/vkDeviceWaitIdle 4 处（行 1791、6310、7886、9087）全在 shutdown / swapchain recreate / surface destroy / 截图读取路径
    • vkWaitForFences 行 2840 是每帧开始的标准 N-buffer swapchain image fence 等待，是必要同步
    • vkMapMemory 是 buffer 创建时一次性调用，非每帧 map/unmap
OpenGL backend 严重落后（暂缓）：backend_opengl.cpp（2344 行）无 PBO、无 glMapBufferRange、无 persistent mapping、无 staging buffer、无内存子分配器。用户决策：OpenGL 放放，先优化 Vulkan 和其他方向。
修正后方向：图形后端从 Phase F 提前到 Phase D 并行。Vulkan 是主战场，Phase D 优先级：
  1. 暴露 Vulkan 内置 frame profiler（m_CPUQueueSubmitTime、m_FenceWaits、m_CPUCommandPrepareTime、m_MainCommandRecords）到 perf report——所有后续优化的前置基线
  2. UI 渲染路径 telemetry（QuadsBegin/End vs RenderQuadContainer 调用频次 + 各自耗时）——判断 UI QuadContainer 推广的真实收益
  3. 基于 profile 数据决定后续优化（QuadContainer 推广 / Descriptor cache / scissor batching 等）
暂缓：AMD GPU 多线程 fallback（无 AMD 测试环境）、OpenGL backend 补 staging/PBO（用户决策放放）。

修正 5：粒子 budget 简化，不做完整优先级系统

v1 FR-3 列了 4 层 budget（spawn/update/render/碰撞）。用户反馈："DDNet 粒子和拖尾，实际游戏中就是一个视觉的效果，所以一般而言不会引入物理检测"。

修正后方向：移除"碰撞预算"，简化为 spawn budget + viewport culling + group render budget 三层。工程量从"几乎重写粒子系统"降到 2-3 周。

② 修正后的六根支柱

基于四份调研，原 v1 的"四支柱 + 文本 + 图形后端"重构为六个独立支柱。每个支柱都标注：现状、真问题、优化方向、代码指针。

Pillar 1：CUI/QmUI 优化（借鉴 ImGui，不 retained）

现状

  • CUI 已实现 QuadBatch + QuadContainer 缓存 + 变高行 clipper（v1 误判为"裸 immediate-mode"）
  • QmUi 是新写的 declarative-style，但大量用 std::vector，无 frame-local arena

真问题

  1. QmUi 无 frame-local arena：QmLayout.h:100 用 std::vector<SUiLayoutChild>，每次 ComputeChildren 都分配
  2. DrawCmd header 不统一：UiPlanQuadBatchSubmission 基于 color/containerIndex 判断，没把 ClipRect 纳入 memcmp，跨 clip 不能合并
  3. 动态文本走"重建容器"：聊天、滚动数字、计时器每帧变化的文本走 CreateTextContainer 全量重建，应该走 ImGui 风格 inline reserve/unreserve
  4. 潜在退化点：CUi::m_vQuadBatchSprites.clear()（ui.cpp:643）需确认是否释放 capacity

优化方向

  • P0 引入 CQmFrameArena（bump allocator）+ std::pmr::vector，替代 QmUi 的 std::vector
  • P0 引入 SDrawCmdHeader POD，把 (ClipRect, TextureHandle, QuadContainerIndex, Color) 塞成连续 32 字节做 memcmp
  • P1 给 ITextRender 加 RenderTextInline 路径，绕过 container 缓存给动态文本用
  • P1 CQmUiStorage（有序 vector + 二分）替代散落的 std::unordered_map

明确不做

  • ❌ retained node 表（v1 4.1.4 删除）
  • ❌ ImGuiListClipper 等高假设（QmClient 变高行 clipper 已经更好）
  • ❌ 直接搬 ImFontAtlas（DDNet textrender 已有等价机制）
  • ❌ Docking/multi-viewport（单窗口游戏 UI 不适用）

Pillar 2：粒子简化 budget

现状

  • CParticles::RenderGroup() 已有 ParticleIsVisibleOnScreen 和 RenderQuadContainerAsSpriteMultiple
  • DDNet 粒子是纯视觉，无物理检测（用户反馈确认）

优化方向（三层 budget，无碰撞预算）

  • P0 spawn budget：按 group 限流，同一帧同一组最多新增 N 个
  • P0 viewport culling：扩展现有 ParticleIsVisibleOnScreen，远端粒子降低更新频率（2-4 帧更新一次）
  • P1 group render budget：按 group 限制最大渲染数，超了降采样（优先保留爆炸、命中、玩家附近粒子）

明确不做

  • ❌ 碰撞预算（用户确认无物理检测需求）
  • ❌ 优先级丢弃系统（DDNet 粒子无 per-particle priority 概念，强加等于重写）

Pillar 3：文本渲染真因分析（重新做）

现状

  • 稳定文本池 + plan collection + prebuild（ad-hoc 实现）
  • SQmTextRuntimeBudgetSnapshot 监控 glyph/container 新建、上传、耗时
  • 关键反常：6/19 log 显示纯英文场景也卡顿，frameMsP99=299ms 但 backend/upload/glyph 全为 0

真因（基于业界调研）

纯英文卡顿真因在 CPU 侧、draw 提交之前，与字符集无关：

  1. 每帧重建 text container / quad buffer（immediate-mode 经典问题）
  2. Paragraph layout / wrap / word-break 每帧重算
  3. Per-frame TextWidth 调用累积

优化方向

优先级措施借鉴来源预期收益
P0text container vertex buffer 加 dirty 标记 + (string,font,size,wrap) 缓存Unreal FCachedGeometry、Qt QTextLayout直接消除纯英文卡顿主因
P0text container 改用持久 arena/线性分配器ImGui ImDrawList纯英文+中文通吃
P1验证并消除每帧 per-label TextWidth 调用（缓存 advance 之和）通用中-高
P1CJK 走"按需栅格化 + 增量 patch 纹理子区域"ImGui 1.92 动态字体系统、Hypersect解决中文卡顿

明确不做

  • ❌ SDF/MSDF 字体（解决任意尺寸高质量渲染，不解决 CPU 卡顿）
  • ❌ GPU-resident text（Slug、compute-shader raster）—— 当前问题在 CPU 同步路径
  • ❌ 整体引入 Qt/Unreal 文本栈（工程量大，收益小）
关键参考：Hypersect "Improving the Font Pipeline"（blog.hypersect.com/improving-the-font-pipeline）—— 业界 CJK 字体工程经验，作者明确承认"自己也没全做对"，业界没有银弹。

Pillar 4：图形后端提前可行性

基于 2026-06-20 完整代码调研（读 backend_vulkan.cpp 9268 行 + backend_opengl.cpp 2344 行 + graphics_threaded.cpp 4000 行 + backend_sdl.cpp graphics 线程）。纠正 6/18 命中率核验文档里的多处错误判断。方向：Vulkan 是主战场，OpenGL 暂缓。

现状（重新核实）

  • 真 graphics 线程：CGraphicsBackend_Threaded（backend_sdl.cpp:54 ThreadFunc）独立线程跑 GPU 命令，mutex + condition_variable 同步，双缓冲 pipeline（graphics_threaded.h:839 m_apCommandBuffers[2]）。仅 Emscripten 退化到单线程。
  • Vulkan backend 5 项基础优化已实现（"已实现"≠"已最优"）：
    • ✅ 持久映射 ring buffer：backend_vulkan.cpp:7156 CreateStreamBuffer，一次 vkMapMemory，按 m_CurImageIndex 分桶；HOST_VISIBLE | HOST_CACHED（行 7192）+ 显式 FlushMappedMemoryRanges（行 7627）
    • ✅ staging buffer + device local memory 两阶段上传：行 3305 CreateImage(OPTIMAL) + 行 3614 vkCmdCopyBufferToImage
    • ✅ 内存子分配器：SMemoryBlockCache + SMemoryHeap（行 1825）
    • ✅ 多线程 command buffer 录制：行 7700-7746 + 行 9113-9124。默认 on（gfx_render_thread_count=3，config_variables.h:832），clamp 到 [3, hardware_concurrency]。但 AMD GPU 强制设为 1（行 9120-9124："forcing single-threaded rendering on AMD to avoid driver crashes with dynamic viewport usage"）
    • ✅ 详尽内置 frame profiler：行 7632-7666（m_CPUQueueSubmitTime、m_FenceWaits、m_CPUCommandPrepareTime、m_MainCommandRecords 等）—— 未暴露到客户端 perf report
  • Vulkan 同步原语真相（纠正 6/18 误判）：
    • vkQueueWaitIdle / vkDeviceWaitIdle 4 处（行 1791、6310、7886、9087）全在 shutdown / swapchain recreate / surface destroy / 截图读取路径，不是帧热路径
    • vkWaitForFences 行 2840 是每帧开始的标准 N-buffer swapchain image fence 等待，是必要同步不是浪费
    • vkMapMemory 是 buffer 创建时一次性调用，非每帧 map/unmap
  • OpenGL backend 严重落后（暂缓优化）：无 PBO、无 glMapBufferRange、无 persistent mapping、无 staging buffer、无内存子分配器；纹理上传直接 glTexImage2D，缓冲上传 glBufferData/glBufferSubData。用户决策：OpenGL 放放，先优化 Vulkan 和其他方向。

优化方向（Vulkan 优先，按收益重排）

优先级方向现状工程量收益
P0 暴露 Vulkan 内置 frame profiler 到 perf report 已有详尽字段（行 7632-7666），未暴露到客户端。当前无法判断是否 GPU-bound 低 高——所有后续优化的前置基线

明确不做

  • ❌ Vulkan backend 推倒重写（5 项基础已对，做具体优化即可，不做架构性大重构）
  • ❌ OpenGL backend 补 staging/PBO（暂缓；用户决策先优化 Vulkan 和其他方向，不为旧 GL 投入）
  • ❌ 多 backend 统一抽象（投入大、回归风险高、对最终 FPS 提升路径短）
  • ❌ render graph / frame graph（DDNet pass 数量很少，不需要复杂 pass 管理）
  • ❌ 3D 引擎优化（draw call batching 大场景、GPU-driven pipeline、indirect draw）—— DDNet 是 2D tile-based，draw call 数量本身受 QuadContainer/tile buffer 已大幅减少
关键纠正（6/18 命中率核验文档）：原文档列出的"Vulkan 同步热点"（vkMapMemory/vkQueueWaitIdle/vkDeviceWaitIdle/vkWaitForFences）不成立：
  • vkMapMemory：buffer 创建时一次性调用，非每帧 map/unmap
  • vkQueueWaitIdle/vkDeviceWaitIdle：4 处全在 shutdown/swapchain recreate/surface destroy，不在帧热路径
  • vkWaitForFences 行 2840：是必要 swapchain image fence 等待，是标准 N-buffer 模式
6/18 文档的相关条目应删除或标注"已纠正"。同时该文档还误判"DDNet 没有线程化"——实际有真 graphics 线程。
已知但暂缓：AMD GPU 单线程 fallback（行 9120-9124）：所有 AMD 用户被迫 m_ThreadCount = 1，原因是"dynamic viewport usage"导致驱动崩溃。用户决策：暂缓——本地没有 AMD 显卡，无法验证修复效果，贸然改可能引入新崩溃。等后续有 AMD 测试环境再说。

Pillar 5：测试深化

现状

  • source-contract 测试形式主义多，断言字符串存在不能 catch 行为 bug
  • 单元测试覆盖率优先，没有"为什么这个测试存在"的 intent
  • 缺集成测试，gate 里跑不了渲染相关的东西
  • 性能测试是 happy path，没覆盖 stress 场景

优化方向

测试类型问题改造方向
source-contract 测试形式主义，断言字符串存在改成行为断言（function call + output verification）
单元测试无 intent 文档每个测试加 intent 文档（说明它 catch 什么 bug）
集成测试缺失加 visual regression gate（reference screenshot + PSNR/SSIM）
性能测试happy path加 stress scenarios（大量 text、长列表、多语言切换）

4.1 Scheduler 架构问题

4.1.1 当前工作模型：纯 opt-in，不是自动发现

整个调度器是 CMenus 类的私有实现，没有以 service 形式暴露给 gameclient/components。gameclient.cpp 中 grep 不到任何 AdaptiveBudget / PrebuildSettingsMenuTextPool / DrainIngameUiTextRuntime 调用——所有调度都嵌在 menus 帧循环里。

4.1.2 不通用的具体表现（代码事实）

  1. 命名硬绑 settings/ingame：menus.h:2197-2201 有 4 个独立 state 字段，每加一个新场景就要新加一个 m_XxxAdaptiveBudgetState 成员
  2. 没有公共注册接口：例如 demos 页（PAGE_DEMOS）完全没接入 text pool
  3. token 消费点硬编码：RenderServerInfo（menus_ingame.cpp:1748-1759）token 唯一用途是 snapshot text 队列，同步渲染路径 DoIngameMenuLabel 系列本身不消费 token
  4. 跨帧状态多份但无统一管理：4 个独立 state 互不感知，UI 在 settings 和 ingame 之间切换时各自 reset/recover，token 摆动剧烈
  5. fallback 是"那一帧不做"：RequestMenuTextContainerBuild（menus.cpp:4754）当 token ≤ 0 直接返回 false，drain 队列堆积，文本持续打不中，用户实际看到的还是同步 fallback

4.1.3 与业界对比

业界做法是否有"plan collection"概念失效机制
Dear ImGui❌ 没有，每帧重建声明即渲染，无状态分歧
Unreal UMG / Slate❌ 没有，retained widget treeInvalidate(EInvalidateWidgetReason) 精粒度
Qt QML❌ 没有，scene graph batch属性变更信号触发
QmClient 当前✅ 三阶段分离（plan→prebuild→visible）Generation bump + dirty 标志

核心洞察：业界都没有"先收集 plan、再后台 prebuild、再 visible 命中"这种三阶段分离。QmClient 实际上试图把 immediate-mode UI 拆成两个虚拟执行路径，但 immediate-mode 的强项（声明即渲染、无状态分歧）被这个拆分破坏了。

4.2 Stable Text Pool 架构问题

4.2.1 key mismatch 8424 的根因（设计层面，不是 bug）

mismatch 的判定是 HasDescriptor && !KeyPlanned。直接来源是 plan 收集时算的 Rect 用 MenuTextSettingsContentView(Screen)（重放路径），visible 渲染时算的 Rect 用真实 MainView，两者亚像素差异 × MaxWidthBucket = round_to_int(width * 10)（0.1 像素粒度）抖动。

这是设计层面问题：plan collection 试图"重放渲染"但重放路径不可能和真实路径完全一致（UI 状态、time-based 动画、scroll position、tab 切换瞬间都不一样）。

4.2.2 双重记账根因（设计 bug + 实现 bug 组合）

  • 设计 bug：guard 的构造函数无脑清零所有 m_MenuTextStable*ThisFrame 计数器（menus.cpp:4960-4976），假设全帧只有一次 guard，违反 RAII 的可组合性
  • 实现 bug：RenderSettings 不应该再建 guard，因为 caller (RenderMenuShell) 已经包过了；这是耦合泄漏
  • 位置：外层 shell guard（menus.cpp:2904-2906、3013-3015）+ 内层 content guard（menus_settings.cpp:4875-4877）

4.3 三个改造方向

方向 A（推荐中期）：scheduler 抽成全局 service

  • 工程量：中（核心算法已独立，主要是接入点重写）
  • 收益：scheduler 真正通用，5-8 个固定 consumer 注册即可获得预算分配；覆盖率从 4 个硬编码点扩展到全 gameclient
  • 风险：当前魔法数（threshold 1.35x、HealthyFrames=2 等）需重新调参
  • 关键边界：5-8 个固定 consumer，service 内部硬编码 list，不要完全动态注册（避免 microservice 反模式）

方向 B（长期）：删除 plan collection 双路径

  • 工程量：中-大（删除约 15+ 个 m_SettingsMenuTextPlan* 成员，但代码净减）
  • 收益：自动消除 key mismatch（不再有两套 key 路径）；自动消除双重记账（不再需要 visible guard 区分）；新加 tab/页面零接入成本
  • 风险：失去"planned vs unplanned"区分能力；失去对"invisible-but-planned"的预热能力
  • 前置 PoC：临时短路 BuildVisibleSettingsMenuTextPlan / PrebuildSettingsMenuTextPool，跑 perf benchmark；如果差异 <5%，方向 B 可直接执行

方向 C（短期止痛）：局部修复

  • MaxWidthBucket：round_to_int(width * 10) 改为 round_to_int(width / 4.0) * 4（4 像素粒度而非 0.1 像素），消除亚像素抖动
  • guard 栈式语义：构造 push 而非清零，析构 pop 时检查栈深度决定是否 flush
  • 工程量：小（1-2 天）
  • 风险：治标不治本，复杂度仍在

4.4 综合建议

SubAgent 推荐 C 短期止痛 → A 中期重构 → B 长期简化 的组合路径。

不要为了"通用"把 scheduler 设计成完全动态注册式 microservice。QmClient 是单线程游戏 client，过度抽象（generic token consumer 注册）反而引入间接调用成本和调试难度。方向 A 的边界应该是"5-8 个固定 consumer，service 内部硬编码 list"。
方向 B 不是"完全 ImGui 化"——DDNet 的 CUi/CUIElement 是 retained-mode（CUIElement 跨帧存活），完全 ImGui 化需要重写 UI 框架，工作量超出 QmClient 范围。方向 B 是"保留 CUIElement 但删除 plan collection 这层"。

⑧ 风险与边界

8.1 scheduler 改造边界

  • 不要做完全动态注册 microservice：5-8 个固定 consumer，service 内部硬编码 list。完全动态注册会引入间接调用成本和调试难度。
  • 方向 B 不是完全 ImGui 化：保留 CUIElement 跨帧存活（retained-mode），只删除 plan collection 这层。
  • 魔法数调参风险：当前 state machine 是手工调参的（threshold 1.35x、1.60x、HealthyFrames=2 等），重构后需要重新调参，可能短期回归。

8.2 图形后端改造边界

  • Vulkan 不要大改：已做对 80%，只新增 telemetry 暴露和小修小补。
  • OpenGL staging buffer 兼容性：staging buffer / PBO 是 OpenGL 3.0+ 标准，兼容性好；persistent mapped 需要 4.4+，需检查 QmClient 最低 OpenGL 版本要求。
  • 图形后端提前可能与 CPU 侧优化竞争资源：6/19 log 显示当前卡顿是 CPU 侧，图形后端优化短期内不解决眼前问题，是长期方向。

8.3 文本渲染边界

  • 不预设答案：纯英文卡顿真因必须先 profile 验证（per-label TextWidth 调用次数、text container 每帧 alloc/free、layout/wrap 重算次数）。
  • ImGui 1.92 动态字体系统是 CJK 长期方案，但工程量大，需要 PoC。
  • 不要 SDF/MSDF 或 GPU-resident text：当前问题在 CPU 同步路径，不解决。

8.4 上游 cherry-pick 边界（替代 v1 的 rebase 风险）

用户已确认 QmClient 已偏离 DDNet 上游太远，现在是 cherry-pick 模式（一个提交一个提交地看改动）。因此：

  • ✅ 不需要考虑上游兼容性
  • ✅ 改动可以隔离在 qmclient/ 目录
  • ⚠️ 但反过来更要严格隔离 QmClient 私有改动，方便识别"哪些是 QmClient 私有"vs"哪些值得贡献回上游"

8.5 测试深化边界

  • visual regression gate 不能替代功能测试：PSNR/SSIM 只能 catch 视觉回归，不能 catch 行为 bug。
  • 重审现有测试时不要一刀切：先识别"形式主义"测试（断言字符串存在），逐个改造为行为断言。
  • 每个测试加 intent 文档：说明它 catch 什么 bug，方便后续 Agent 判断测试是否还有价值。

8.6 内存预算约束（v1 缺失，v2 补充）

  • 所有缓存（layout cache、text LRU、texture atlas）都会增加内存占用
  • 每个新增缓存的内存上限必须显式声明，超过预算时降级或 evict
  • 建议内存预算：PC 上 1-2GB（含游戏纹理+UI+font atlas+缓存）

8.7 telemetry 字段膨胀（v1 缺失，v2 补充）

  • 每个新增 stage 必须按 frame pressure 节流，不能让 perf logging 本身成为 hot path
  • 当前 6/19 log 已经 694425 行，再加新 stage 需要谨慎
  • 建议：低优先级 stage（如 glyph_warmup）用阈值触发输出，不每帧输出
