## 1 · 愿景（用户确认）

卡片是 **first-class 全局组件**，用 stableId 唯一标识，**不绑定页面**。每张卡片有一个「当前位置」`(tab, column, order)`，用户可任意排布、迁移到任何 tab / 列 / 位置。**tab 既是默认分类，也是可改的位置维度**（不是卡片的固有属性）。默认布局 = 出厂布局，可一键 reset。

一句话：**卡片是组件库里的组件，tab/页面是画布上的视图，用户在画布上任意摆放组件**。

## 2 · 数据模型

```text
Card        = 全局组件 { stableId, ...卡片内容 }        // stableId 唯一，不含位置
Placement   = 位置     { tab, column, order }          // 每卡当前唯一位置
GlobalLayout = 所有卡片的 Placement 集合                // 全局唯一权威
```

- **v1：单实例可迁移**（iPhone 主屏模型）——每卡一个 Placement，可从 tab A 整体搬到 tab B。简单、兼容现状、符合 spec 一直沿用的 iPhone 类比。
- **v2（留口，不实现）：多 tab 共享**——同一卡可出现在多个 tab（Placement 列表）。v1 的 stableId 设计不阻碍未来升级（仅需把 Placement 标量改为列表）。

> ⚠️ 这是**待你拍板的核心决策**（见 §7-1）：若你其实想要「一张卡同时出现在多个 tab」，数据模型要改。下文默认按 v1 单实例展开。

## 3 · stableId 命名规范

两级：`<ns>:<name>`

| ns（命名空间） | 含义 | 来源 |
|---|---|---|
| `qm` | 栖梦侧栏模块（38 个） | 现 `QmSidebarCardOrder` |
| `tclient` | Tclient section 卡（15 个） | 现 `qm_settings_card_order`（已用 `tclient:` 前缀） |
| `deck` | 设置 deck 卡（graphics/sound/ddnet/bindwheel/statusbar，~16 个） | 现内存 map（无持久化） |

**规则**：
- `<name>` 保留各卡现有的本地标识，做最小规范化（不重命名，降低迁移风险）。
- **stableId 不编码 tab**——tab 是可变位置，写进 id 会让「迁移到别的 tab」变成「换 id」，破坏稳定性。
- Tclient 现有 `tclient:<name>` **天然兼容**新规范，零改动。

**迁移映射规则**（旧 → 新，机械前缀化为主）：

| 旧体系 | 旧样例 | 新 stableId | 规则 |
|---|---|---|---|
| 栖梦（裸 key） | `chat_bubble` | `qm:chat_bubble` | 加 `qm:` 前缀 |
| 栖梦（**QiaFen 陷阱**） | `qiafen` | `qm:qiafen` | 加 `qm:` 前缀；**以持久化 key `qiafen` 为权威**，绝不用 UI 名 `keyword_reply` |
| Tclient section | `tclient:visual-nameplates` | `tclient:visual-nameplates` | 不变（已兼容） |
| 设置 deck | `graphics-display` | `deck:graphics-display` | 加 `deck:` 前缀 |

> ⚠️ **QiaFen 三名分裂**（枚举 `QiaFen` / UI 名 `keyword_reply` / 持久化 key `qiafen`，见 `menus_qmclient.cpp:1416 vs :1480`）是迁移最大陷阱。映射表与解析**一律以 `m_pKey`（持久化字符串）为权威**，否则会把用户已有的 `qiafen:` 条目判为未知 key 丢弃。

## 4 · 默认值系统（出厂布局）

### 4.1 组件注册表（单一事实源）
每张卡片在代码内声明默认 Placement：

```cpp
struct SCardDefault {
    const char *m_pStableId;   // "qm:chat_bubble"
    const char *m_pDefaultTab; // "visual"
    EColumn m_DefaultColumn;   // Left / Right / Full
    int m_DefaultOrder;        // 列内序
};
// 全局一张静态表，卡片增删在此维护
static constexpr SCardDefault s_aCardDefaults[] = { ... };
```

这份表 = 全局卡片的**组件注册表**，是默认值、迁移兜底、新卡补位的唯一依据。

### 4.2 SmartDefaults（贪心左右高度平衡）
栖梦现有 `ApplySmartQmModuleLayoutDefaults`（`menus_qmclient.cpp:1636-1692`）的贪心算法（按分组累加估算高度、哪列矮放哪列）**下沉为全局共享能力**，所有 page 复用。各 page 只需提供一个「高度估算」回调（高度是 page/卡特定的）。

- 触发时机：config 为空 / 用户 reset / 新增卡片补位。
- **reset = 清空 config → SmartDefaults 重算出厂布局**（语义清晰，无需单独的 reset 存储）。
- Tclient / 设置 deck 当前没有智能平衡 → 全局化后**自动获得**这个能力（纯增益）。

### 4.3 数据债清理（全局化前必须做）
调研发现两张「有默认布局但未归入任何 tab 分组数组」的卡（visual/function/hud 三组都不含），智能默认走兜底槽，渲染可见性存疑。B1 前需给它们补 tab 归属：
- **`nameplate_text`**（Right/18，`:1500`）
- **`laser`**（Right/3，`:1485`）—— ⚠️ 早期调研误判为「死分支」，实为活卡：枚举（`:1369`）、默认布局（`:1485`）、IdName（`:1419`）、UI 元数据（`:2824`）、搜索（`:2468`）5 处皆有引用。

清理遵循既有先例（`qm_lyrics_hud.md` 记录的 Lyrics 36→35 流程）。

## 5 · 稳定持久化模型

### 5.1 存储
单一 config `qm_global_card_order`（替代 `QmSidebarCardOrder` + `qm_settings_card_order` + 设置 deck 内存 map 三套）。

### 5.2 格式
```text
<stableId>|<tab>|<column>|<order>;<stableId>|<tab>|<column>|<order>;...
```
样例：
```text
qm:chat_bubble|visual|left|0;tclient:visual-nameplates|tclient|left|0;deck:graphics-display|graphics|left|0;
```

**字段分隔用 `|` 而非 `:`**——因为 stableId 本身含 `:`（`qm:chat_bubble`），用 `:` 分隔字段会产生歧义。`|` 在 config 字符串里安全且可读。

- `column`：字符串 `full`/`left`/`right`（保留栖梦的 **Full 列语义**，`info` 卡依赖）。
- 兼容旧格式：解析时检测分隔符——含 `|` 走新格式，否则按旧 `key:col:order;`（栖梦）或 `id:col:order;`（Tclient 数字列）回退。

> 格式字符串本身是 B1 实现时定稿的细节；设计层只要求：**无歧义、容错、兼容旧三套格式**。

### 5.3 模型：全量用户布局（沿用栖梦，已验证）
持久化 = 用户当前布局的**全量快照**（所有卡的当前位置），非 override diff：
- 加载 = 组件注册表（default）作基准 + Parse 用户值覆盖。
- 新增卡片（注册表有、config 没）→ 按默认 Placement 补。
- 删除卡片（config 有、注册表没）→ 残留条目容错跳过。
- 这套「全量 + 默认补全 + 容错」正是栖梦 `SyncQmModuleLayout`（`:1959-1983`）已验证稳定的模式，泛化到全局。

**为什么不用 override diff**：override 更紧凑，但要额外处理「显式隐藏 / 显式重排 vs 未改动」的状态机，复杂度高。全量模型简单、已验证，v1 用它；override 留作未来优化。

### 5.4 容错（复用栖梦骨架，泛化到全局）
| 情况 | 处理 |
|---|---|
| 未知 id | 跳过该条 |
| 重复 id | 取首次，忽略后续 |
| 非法 tab/column/order | 跳过该条，回退默认 Placement |
| Full 列保护 | Full 卡（如 `info`）不可拖出 Full；非 Full 卡不可拖成 Full |
| order 空洞 | `NormalizeColumns()` 连续化 |
| 新增卡片 | 按注册表默认补 |
| 删除卡片残留 | 跳过 |

### 5.5 迁移（一次性，幂等）
- 新增 `qm_card_order_migrated` 标志，已迁移则跳过。
- 三套旧源 → 新 config：
  - `QmSidebarCardOrder`（栖梦）：按 §3 规则加 `qm:` 前缀，QiaFen 特殊处理。
  - `qm_settings_card_order`（Tclient）：id 已兼容，仅转换列格式（数字→字符串）。
  - 设置 deck 内存 map：**无旧持久化**，迁移时直接用注册表默认（对用户纯增益）。
- 旧 config 迁移后**不立即删除**，保留一版本作回滚锚点。
- buffer 容量：`qm_global_card_order` 需容纳 ~69 卡 × ~40 字符 ≈ 2.8KB，按栖梦现有 2048 buffer 不够，**B1 需扩容**（建议 4096）。

## 6 · 设计决策（我定的 + 理由）

| 决策 | 选择 | 理由 |
|---|---|---|
| 卡片实例模型 | v1 单实例可迁移 | iPhone 类比、兼容现状、简单；多 tab 共享留 v2 口子 |
| 持久化模型 | 全量用户布局 | 栖梦已验证稳定；override diff 复杂度高，v1 不值 |
| stableId 分隔 | `<ns>:<name>` 冒号 | Tclient 现有 id 零改动；业界常见（URI scheme 风） |
| 字段分隔符 | `\|` | 避免与 id 内 `:` 歧义 |
| 列语义 | 保留 Full（字符串） | 栖梦 `info` 卡依赖；Tclient/deck 获得 Full 能力 |
| SmartDefaults | 下沉全局共享 | 栖梦独有能力泛化，Tclient/deck 纯增益 |
| 迁移权威 | 以旧持久化 key 为准 | 规避 QiaFen 三名分裂丢数据 |

## 7 · 待你拍板

1. **单实例 vs 多 tab 共享**（最关键）：v1 我按「单实例可迁移」设计。若你要「一张卡同时出现在多个 tab」，数据模型改为 Placement 列表，设计要返工——请确认。
2. **SmartDefaults 下沉 vs 各 page 自定义**：我推荐下沉共享（Tclient/deck 白赚平衡能力）。若你担心全局算法不适合某些 page，可改为「下沉骨架 + page 可覆盖」。
3. **字段分隔符 `|`**：纯实现细节，若你有偏好（如坚持沿用 `:` 并接受 id 不含冒号）可调整。
4. **buffer 扩容到 4096**：是否接受，或你有 config 长度规范。

## 8 · 性能考量

基于代码核实（`menus_qmclient.cpp` 热路径），全局化（38→69 卡）的性能要点。

### 8.1 当前热路径（栖梦 38 卡，已核实）
| 路径 | 每帧成本 | 评价 |
|---|---|---|
| 让位 lerp（`:7876-7906`） | O(N)，`GetQmModuleStateIndexById` **O(1)** 枚举下标（`:1594`） | ✅ 健康 |
| 卡片背景合批（`:894-967`） | 1 drawcall，QuadContainer + cull | ✅ 健康（优化成果） |
| `SyncQmModuleLayout`（`:1959-1983`） | **每帧** Serialize 拼 2KB + str_comp×2 + str_copy | 🟠 冗余 |

### 8.2 🔴 全局化关键：state index 必须保持 O(1)
栖梦 `GetQmModuleStateIndexById`（`:1594-1595`）用 `EQmModuleId` 枚举值直接当 state 数组下标，O(1)——这**依赖栖梦模块是连续枚举 0..37**。全局化后 Tclient/deck 卡用字符串 stableId，**没有连续枚举**，若退化成线性查找会让位变 O(N²)（69 卡 ≈ 37 卡的 3.5 倍成本）。

**要求（B1 必做）**：启动时构建 `stableId → 连续 index` 注册表（数组下标或 hashmap），让位 lerp 保持 O(1) 查找。这是全局化的**性能地基**，和 §4.1 的组件注册表可合并为一张表。

### 8.3 🟠 每帧 Serialize 冗余 → IsDirty 触发
`SyncQmModuleLayout` 每帧 `SerializeQmModuleLayoutEntries`（`:1976`）拼 2KB 字符串 + 2×str_comp + str_copy，**即使 config 未变**。全局化 69 卡 + 4KB buffer → 翻倍。

CModel **定义了** `IsDirty`（`QmCardOrderModel.h:43`）但**生产链路尚未接入**（当前仅测试用）。B1 必须把 `SyncQmModuleLayout` 从操作 `s_aQmModuleLayout` 切到操作 `CModel`，`IsDirty` 才生效 → **只在 `Move` 后序列化一次**，每帧仅留 1 次轻量 str_comp 检测外部改动（或改 config 版本号彻底消除）。

### 8.4 🟡 其他放大点与对策
- **切页 69 卡同时 lerp**：组件编辑器跨 tab 迁移会让切页时整页 `TargetRect` 突变，所有卡同时 lerp → 可能帧卡顿。对策：**非拖拽态切页时 `DisplayRect` 直接 snap 到 `TargetRect`**（不走 lerp），仅拖拽态走让位 lerp。
- **让位预览无缓存**：`UpdateDropPreview` 每帧重算。对策：DropIndex/被拖列不变时缓存复用预览布局（spec 3.4 已提）。
- **迁移大 Parse**：首次迁移 69 卡，`FindQmModuleIndex` 线性（`:1585`），O(条目×N)。一次性但可能卡启动。对策：异步/分摊 + log 耗时；或启动时建 key→index map 让 Parse 降 O(条目)。

### 8.5 性能验证口径
- 拖拽 69 卡时 frame time 监控（现有 `LogQmPerfStage` 已埋点 `:1982`，复用）。
- 目标：让位 lerp + 合批 < 1ms/帧（亚毫秒），切页 snap 无卡顿。
- 迁移耗时单独 log，纳入 B2 验收。
