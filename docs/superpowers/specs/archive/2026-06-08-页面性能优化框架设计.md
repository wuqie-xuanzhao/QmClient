# 页面性能优化框架设计

日期：2026-06-08
状态：active

## 结论

本文档是 QmClient 菜单页面性能优化及其量化、复现、回归闭环的当前统一入口。新特性、内存生命周期、debug 工作流、安全性或通用重构任务只有在涉及菜单页面性能证据时才联读本文档；其它专项任务仍按 `docs/ai-workflow/advanced/README.md` 的最小阅读路由进入。

核心结论：

1. `qmclient_scripts/perf` 和 C++ `perf/*` 日志按生产级性能诊断系统建设，不再按 MVP 口径规划。
2. 再按页面切换、列表滚动、资源完成、文本 / 布局重建四类成本分别降温。
3. FBO 路线明确停止：不新增、不扩展、不补 shadow 统计，也不把删除 / 禁用 FBO 作为本框架的后续性能任务。
4. 资源 Jobs 继续保留，但只作为页面性能框架中的一个子系统，不再把所有卡顿问题都归结为资源加载问题。
5. 每个后续优化项必须能回答：操作路径是什么、长帧归因是什么、采样是否可信、是否有同路径前后对比、如何防止回归。
6. 量化体系同时保留两类指标：内部 `perf/*` 阶段耗时用于归因；同路径、无上限帧率下的菜单页面 `avg/max/min FPS` 用于端到端体感对比。

本设计覆盖 `Settings`、`Server Browser`、`Demo Browser`、`Assets`、`Tee`、`QmClient/TClient` 等菜单页面切换与列表交互。目标是建立一套行为保持的重构路线，而不是增加新功能或重写 UI 框架。

## 目标

1. 页面切换不再出现可感知长帧，尤其是首次进入设置页、服务器列表、Demo 列表、资源页和 Tee 页。
2. 列表滚动只处理可见范围和近邻预取，不在交互帧推进重型后台结果。
3. 所有性能结论先有日志、报表、固定场景或 A/B baseline 证据，再进入实现。
4. FBO 不再作为优化工具；已有 FBO 已经出现用户可见 bug，不作为后续投入方向。
5. 将资源 Jobs 的预算、优先级和 telemetry 经验复用到页面切换与列表交互，但不把所有页面强行塞进同一个资源管线。
6. 性能量化系统可被开发、审查和用户反馈流程长期使用：报告自包含、边界数据不误导、阈值一致、采样开销受控、缺失信息明确标为 N/A。
7. 性能问题修复后进入回归防护闭环：同操作路径对比、固定场景、必要测试或 checklist 至少保留一个。
8. Settings 等重页面应能输出无上限帧率下的同路径 `avg/max/min FPS` 摘要，作为用户可直观看懂的优化前后对比指标。

## 非目标

1. 不引入 RmlUI 或 retained-mode UI 替换当前 DDNet CUI。
2. 不做全局 draw list 重写。
3. 不改变协议、皮肤格式、地图格式、物理、预测或游戏内渲染语义。
4. 不把性能优化和 UI 视觉重设计绑定为同一轮任务。
5. 不继续扩展 FBO、readback、render target 维护、FBO shadow telemetry 或 FBO A/B 评估任务。

## 行为边界

本框架下的重构必须保持：

1. 菜单页面、tab、子 tab、搜索、筛选、排序、选择和滚动行为不变。
2. 服务器列表、Demo 列表、资源列表和 Tee 列表的可见内容和选择结果不变。
3. 现有配置项语义不变；需要新增性能配置时使用 `qm_` / `Qm` 前缀。
4. 资源 fallback 路径不变：缓存或异步结果缺失时，必须继续安全显示现有 source / live 路径。
5. 性能日志只在 `qm_perf_debug` 或 `qm_perf_logfile` 开启时输出，不污染普通运行。

## 第一原则

后续优化按这个顺序判断：

1. **不做**：交互帧不处理不可见 section、不可见列表行和远端后台结果。
2. **少做**：静态文本、布局、列表 plan、排序结果和筛选结果只在 dirty 时重建。
3. **分帧做**：目录扫描、列表合并、decode 结果、GPU upload、preview publish 按帧预算推进。
4. **异步做**：文件 I/O、图片 decode、列表 plan build 等不依赖 GPU context 的工作进入 Jobs。
5. **证明后再缓存**：缓存和派生产物必须用 telemetry 证明命中率、成本和收益。
6. **明确停止 FBO 路线**：FBO 已经出现用户可见 bug，且收益不清晰；后续页面性能优化不再围绕 FBO 做新增、扩展、shadow 统计或保留论证。

## FBO 决策

### 当前判断

FBO 不再是设置页或页面切换优化路线。原因：

1. 现有实测材料显示稳态设置页帧时间已经可以低到 2-3ms，真正问题集中在冷启动和页面切换尖峰。
2. 已有 FBO 路径已经出现用户可见 bug，不能继续作为页面性能优化的可靠基础。
3. FBO 命中率和收益缺少可靠证据，已有日志更多显示 miss / not_ready。
4. FBO 维护引入了静态层 / 交互层拆分、render target 生命周期、readback、失效原因和花屏、错位、stale 内容风险。
5. 对 DDNet 这种 2D immediate-mode UI，FBO 的典型高收益场景有限。

### 规则

1. 新页面、新 section、新列表优化默认不允许新增 FBO。
2. 不为已有 FBO 补 shadow 统计、命中率报表或 A/B 保留证明。
3. FBO 清理属于已知用户可见 bug 的 bugfix / cleanup 范围，不作为页面性能框架的性能优化阶段。
4. 已知用户可见 bug 涉及的 FBO 路径，应作为单独 bugfix / cleanup 最小绕开或移除；目标是消除用户可见问题，不是继续证明或挽救 FBO。
5. 剩余已有 FBO 代码视为技术债，不作为保留对象；只有它阻塞非 FBO 优化或维护时必须触碰时，才按最小 cleanup 处理。

## 统一性能模型

页面性能事件分四类，而不是只看资源：

1. **Page Switch**
   - 切换主页面、设置页 tab、QmClient / TClient 子 tab、ServerBrowser tab、Demo tab。
   - 重点记录切换帧、首个稳定帧、是否触发同步刷新或同步扫描。
2. **List Interaction**
   - 滚动、快速跳滚、筛选、搜索、排序、选择。
   - 重点记录总 item、可见 item、实际处理 item、跳过 item、可见范围计算成本。
3. **Work Drain**
   - job result merge、CPU finalize、GPU upload、preview publish、cache restore。
   - 重点记录交互帧是否 defer、预算 stop reason、单帧推进数量和字节数。
4. **UI Rebuild**
   - CUI：文本容器、section 高度测量、可见范围、widget 绘制。
   - QmUI：runtime tree、调用方 layout、animation、render bridge、QmUI 原语绘制。
   - 重点记录 dirty reason、新建 / 复用数量、section render cost、QmUI node count、draw calls 和 clip pushes。

这些事件可以复用 `perf/menu`、`perf/section`、`perf/interaction`、`perf/settings-resource`、`perf/device` 等系统，但字段语义要统一。

## 页面分类与策略

### Settings / QmClient / TClient

核心问题是 CUI section 和 widget 的重建成本：

1. 静态文本统一走 `CUIElement` / `SettingsTextElement` 缓存。
2. section 高度和布局只在 dirty 时重算。
3. 视口外 section 只保留高度和状态，不调用 widget 逻辑。
4. 子 tab 切换记录 `page_switch` 事件，区分布局重建、文本重建、资源 drain 和纯绘制成本。
5. 不新增 section FBO，也不为已有 section FBO 继续补 shadow / A/B / 保留评估。

QmUI 相关页面或覆盖层单独看 `CUiRuntimeV2` 路径，不能把 QmUI 问题简单归到 CUI immediate-mode：

1. 记录 runtime node count、layout cost、anim advance、render bridge cost、draw calls 和 clip pushes。
2. layout 由调用方外部计算，必须记录 dirty reason；不要默认每帧全量 layout。
3. 动效只应推进可见、active、hover、focused 或过渡中的节点。
4. `DrawCard`、overlay、navigation、form 等 QmUI 原语按原语统计成本，不和 `DoLabel` / `DoButtonLogic` 混为同一个指标。

### Server Browser

核心问题不是资源 Jobs，而是列表交互和刷新触发：

1. 保持 `CListBox` 可见项渲染模型。
2. 记录每帧 server 数、可见行数、跳过行数、排序 / filter 是否在本帧发生。
3. 页面切换时避免同步触发过重刷新；必要刷新应可被日志标记为 `refresh_triggered`。
4. 不把 ServerBrowser 强行迁入资源 Jobs 框架。

### Demo Browser

核心问题是目录扫描和首次列表建立：

1. 首次进入不应在同一交互帧完成大型目录扫描和完整列表更新。
2. Demo list plan 可以先 shadow 化：记录同步扫描耗时和条目数，再决定是否异步化。
3. 若异步化，UI 先发布稳定骨架和当前目录状态，条目分帧合并。

### Assets / Workshop

核心问题是资源完成链路，但前面已经优化过不少：

1. 保留已有 decode、finalize、upload、merge budget。
2. 继续把 Workshop metadata、Workshop thumb、本地资源 decode 区分开。
3. 与通用框架共享的是阶段、优先级、预算、telemetry，不是共享同一类实现。
4. 交互帧中只允许 visible 必需工作，prefetch / background 必须可 defer。

### Tee

Tee 已有较完整资源调度，后续重点不是继续堆缓存，而是证明和稳定：

1. source / live path 是正确性基线。
2. preview cache 是可选显示加速，不允许成为首次可见或正确显示的唯一前提。
3. 已成功显示过的 preview 不应因 source 回收而回退到 loading。
4. FBO / readback 不作为 Tee 列表可见路径前提。

## 量化与验收

### 采集要求

性能优化前必须先采集基线。默认阈值按当前系统配置使用 4ms；4.17ms 只表示 240Hz 帧预算线，不作为采样偏差默认阈值。

```text
qm_perf_debug 1
qm_perf_logfile 1
qm_perf_debug_threshold_ms 4
```

使用：

```bash
cd qmclient_scripts/perf
npx tsx analyze.ts
```

报告必须记录操作路径、环境和可信度：

1. 操作路径：例如打开 Settings、切到 Tee、滚动一屏、刷新 Server Browser、首次进入 Demo Browser。
2. 环境：平台、renderer、窗口模式、刷新率、UI scale、客户端版本。
3. 可信度：采样阈值、采样偏差、样本数量、是否同一操作路径、是否有官方 DDNet A/B baseline。
4. 缺失数据：字段缺失、空日志、畸形行和不可比样本必须显示为 unavailable / N/A，不允许伪造成优秀指标。

端到端 FPS 基线也要同步采集。采集时开启无上限帧率，并固定同一操作路径、硬件、renderer、窗口模式、分辨率、UI scale 和客户端版本。报告至少记录 `fps_avg`、`fps_max`、`fps_min`、采样秒数、样本帧数和 `fps_cap_limited`。如果 vsync、驱动或系统限帧无法关闭，FPS 摘要只能作为本次运行的参考，不能参与严格 A/B 结论。

### 目标指标

| 场景 | 目标 |
| --- | --- |
| 主页面切换 | p95 ≤ 8ms，p99 ≤ 16ms |
| 设置页 tab 切换 | p95 ≤ 8ms，p99 ≤ 16ms |
| 列表滚动 | p95 ≤ 8ms，p99 ≤ 16ms |
| 首次进入重页面 | 允许 1 帧 ≤ 33ms，不允许连续长帧 |
| 无上限 FPS 摘要 | 同路径 `avg FPS` 不低于 baseline；`min FPS` 不出现无法归因的明显退化 |
| Work drain | 交互帧必须有 defer / stop reason，不允许无解释的集中合并 |
| FBO | 不作为本框架验收项；后续优化不得依赖新增、扩展或证明 FBO |

### 必要字段

后续 C++ telemetry 优先补这些字段：

```text
event=page_switch page=... from=... to=... dur_ms=...
event=list_frame page=... items_total=... rows_visible=... rows_rendered=... rows_iterated=... rows_skipped=...
event=section page=... section=... dur_ms=... visible=0/1 dirty=... text_new=... text_reused=...
event=work_drain page=... kind=merge/finalize/upload/publish count=... bytes=... dur_ms=... stop=...
event=ui_runtime page=... nodes=... layout_ms=... layout_dirty=0/1 dirty_reason=... anim_ms=... active_anims=... render_bridge_ms=... draw_calls=... clip_pushes=...
event=fps_summary operation=... page=... fps_avg=... fps_max=... fps_min=... sample_frames=... sample_seconds=... cap_limited=0/1
```

字段可以先用 key=value；JSON Lines 是后续增强，不作为第一步阻塞。

### 报表与日志合同

性能量化系统按生产级诊断系统维护：

1. KPI、verdict、文字结论、图表标线和采样偏差判断必须共享同一组阈值语义。
2. `page_switch` 是边界事件，不应被报表误当作全部耗时归因；它要帮助定位切页帧内后续的 list / section / drain 成本。
3. 热路径日志必须 threshold-gated；低于阈值时不得构造逐帧大 payload、完整列表明细或昂贵格式化字符串。
4. `list_frame` 这类高频事件默认记录摘要字段；逐项明细只允许在高阈值、显式 debug 或固定复现场景中启用。
5. `fps_summary` 是操作路径级摘要事件，不允许作为每帧高频日志输出；它只能和同一路径、同环境、同限帧状态的 baseline 比较。
6. `ui_runtime` 是 QmUI 摘要事件，必须和 CUI `section` / `list_frame` 分开展示，避免把 QmUI tree / anim / bridge 成本误写成 CUI widget 成本。
7. 边界输入必须有测试：空日志、单样本、全相同耗时、畸形行、缺字段、只有高阈值截断样本、不同 operation 混合样本、FPS 被限帧的样本。
8. FBO hit rate 不作为页面性能报告入口，也不作为后续优化优先级依据。

### 反馈与复现

后续 report / debug bundle 应能支持这个闭环：

```text
真实使用 -> 看见异常 -> 复现 -> 修复 -> 加观测 / 测试 / checklist -> 下次更容易发现异常
```

建议 debug bundle 至少包含：

```text
client_version.txt
system_info.txt
config_sanitized.cfg
last_log.txt
perf_summary.json
repro_steps.txt
```

bundle 必须脱敏；不能包含 token、密码、私密聊天和完整个人历史。

### Phase 1：生产级性能量化系统收口

1. 复用现有 `qmclient_scripts/perf` 和 C++ `perf/*` log，不重建另一套量化系统。
2. 基于 `2026-06-02-设置页性能量化系统设计.md` 的稳定结论，保留百分位、尖峰、采样偏差、离线自包含 HTML 报告和同路径对比。
3. 基于 `docs/superpowers/reviews/2026-06-09-性能量化系统代码审查.md` 的审查结论，持续保证 KPI / verdict / 图表阈值一致、采样阈值语义一致、边界样本不误导。
4. 给 page switch、list frame、section、work drain 补最小日志字段；不补 FBO 相关字段。
5. 增加 QmUI `ui_runtime` 摘要，按 nodes、layout、anim、render bridge、draw calls、clip pushes 单独展示。
6. 增加操作路径级 `fps_summary`，把无上限 `avg/max/min FPS` 放进 perf report 和同路径对比，但不把它当作长帧归因来源。
7. 扩展 perf 报表，让它能按页面切换、列表处理、资源 drain、CUI rebuild、QmUI runtime、device bound 归因长帧。
8. 接入 debug bundle 和固定场景输出，使用户反馈和开发自测能复用同一套摘要。

完成标准：

1. 能回答一次卡顿是来自页面切换、列表处理、资源 drain、UI rebuild 还是设备瓶颈。
2. 报表不再把 FBO 命中率或保留收益作为页面性能框架的判断入口。
3. 同一操作路径能产出可对比的 perf report，采样偏差和长帧尖峰有明确提示。
4. 无上限 FPS 摘要能显示 `avg/max/min FPS` 和限帧状态；不可比样本不会生成严格 delta 结论。
5. QmUI 成本能单独显示为 runtime tree / layout / anim / bridge，不和 CUI section/widget 成本混写。
6. 空日志、畸形行、缺字段、单样本、截断样本等边界情况不会生成误导性结论。

### Phase 2：清理 FBO 用户可见问题

1. 将已知用户可见 bug 涉及的 FBO 路径作为 bugfix / cleanup 处理。
2. 最小绕开或移除问题路径，不新增替代 FBO、不补 FBO shadow、不做 FBO A/B 保留证明。
3. 保持页面显示、输入、滚动、资源 fallback 和配置语义不变。
4. 清理过程中只触碰必要路径，不把 FBO 清理扩展成 UI 重写或全局性能重构。

完成标准：

1. 已知 FBO 用户可见 bug 不再影响目标页面路径。
2. 后续页面性能优化不再依赖 FBO 记录、绘制或 readback 路径。
3. 没有引入新的 FBO 能力、FBO telemetry 或 FBO 保留评估。

### Phase 3：源头降温

1. Settings / QmClient / TClient：补文本缓存、dirty 布局、视口外 section skip。
2. ServerBrowser：记录并减少页面切换时不必要的刷新和排序重算。
3. DemoBrowser：先记录目录扫描成本，再决定是否拆成异步 plan + 分帧 publish。
4. Assets / Tee：收紧交互帧 drain 预算，不新增缓存复杂度。

完成标准：

1. 主要页面切换 p99 降到 16ms 内，或剩余超标都有明确 stage 归因。
2. 优化前后有同一操作路径的 perf report 对比。

### Phase 4：局部结构化重构

1. 只对证据指向的热点做局部抽取，例如 list visible range helper、section dirty state、work drain budget helper。
2. 不做全局 scheduler 大重构。
3. 每一步都保持行为边界并跑对应 gate。

完成标准：

1. 代码复杂度下降，性能指标不退化。
2. 没有把资源页、服务器列表、Demo 列表强行统一成同一种实现。

### Phase 5：工作流与回归闭环

1. 为 Settings、Server Browser、Demo Browser、Assets、Tee 建立固定操作路径和失败信号。
2. 形成官方 DDNet A/B baseline 表：同环境、同操作、同指标，不把不同操作路径的日志当严格回归结论。
3. 每个性能 bugfix 或优化项至少补一个观测项、测试、固定场景或 checklist 项。
4. 让 `/debug_client`、`/export_diagnostics` 或后续同类入口能导出脱敏 debug bundle。

完成标准：

1. 以后同类问题能通过 perf report、固定场景、debug bundle 或 checklist 更早发现。
2. release 前可以按 Performance / Diagnostics / Regression prevention 维度说明本轮质量变化。

## 执行规则

1. 先看证据，再写代码。不能归因的长帧先补 telemetry，不直接套缓存、异步或重构。
2. 实现前必须先排查同一页面 / 操作路径上的现有 UI bug，尤其是上一轮性能优化、预热、FBO、缓存、异步 publish、列表虚拟化或 QmUI 动效相关的用户可见问题。不能把已有 bug 当成优化后新增问题，也不能在有未解释 UI bug 的路径上直接扩大优化。
3. 如果现有 UI bug 与性能优化路径相关，可以在同一轮做最小修复或绕开，但必须把它标成 bugfix / cleanup，不把修 bug 包装成性能收益。
4. 涉及官方 DDNet 长期稳定、很久未动的 CUI / 菜单基础路径时，默认提高门槛：先读调用点和 upstream 语义，说明为什么必须改这里，优先选择外围适配；确实要改基础路径时，需要更小补丁、更强测试、视觉 / 输入 / 回归验证和清晰 rollback 方案。
5. 每轮只处理一个明确页面、操作路径或系统合同问题，不把 Settings、Server Browser、Demo Browser、Assets 和 Tee 混成一次大重写。
6. 优化必须保持菜单显示、页面切换、列表交互、资源 fallback、配置语义和 DDNet 兼容性。
7. 新字段、新配置和新工作流优先补测试或 gate 约束；不能只靠文档声明。
8. 性能量化系统本身的改动优先保护可信度：阈值一致、边界样本可解释、缺失信息明确、观察开销受控。
9. 资源 Jobs 只共享阶段、优先级、预算和 telemetry 语义；不要为了统一而把不同列表强行迁入同一个实现。
10. FBO 只作为已知用户可见问题的 cleanup 范围处理，不作为优化路线、报表入口或保留证明对象。

## 实现前 UI Bug Audit

每个页面性能优化实现前，先完成一次最小 UI bug audit，并把结论写入对应 plan / PR 描述：

1. **路径确认**：列出本轮要验证的页面、tab、列表、滚动、输入、hover、选中、弹窗、返回和资源 fallback 路径。
2. **既有问题搜索**：查当前计划、探索、review、TODO、已知用户反馈和相关 perf log，确认是否已有花屏、错位、stale 内容、焦点丢失、输入吞掉、滚动跳动、选择错误、loading 卡住或资源回退问题。
3. **上一轮优化风险**：重点检查之前做过的 FBO、预热、缓存、异步 jobs、分帧 publish、列表可见范围和 QmUI 动效改动；这些改动未必可靠，不能假设无 bug。
4. **官方基础路径风险**：如果要改上游 DDNet 很久未动的 `CUi`、`CUIRect`、`CScrollRegion`、`CListBox`、菜单通用按钮 / label / editbox / popup 逻辑，必须先证明外围修复不可行，并记录影响面。
5. **决策**：如果发现影响同一路径的 UI bug，先决定 bugfix / cleanup / telemetry / 暂缓优化四选一；不要在未知显示或输入错误上继续叠性能重构。
6. **验证清单**：至少覆盖正常 UI scale 和一个非默认 UI scale；涉及输入时覆盖鼠标、键盘焦点、文本输入、滚动和 modal；涉及列表时覆盖空列表、少量项、大量项、搜索 / 筛选 / 排序和快速滚动。

## 验证要求

| 改动类型 | 最小验证 |
| --- | --- |
| 纯文档或工作流入口 | `python qmclient_scripts/gate/check_docs.py --sync-only --prefer agents`，再跑 `python qmclient_scripts/gate/check_docs.py` |
| `qmclient_scripts/perf` 报表 / 统计 / 解析 | `cd qmclient_scripts/perf && npm test`，`cd qmclient_scripts/perf && npx tsc --noEmit`；作为生产级诊断系统代码改动收口时，还必须跑 `python qmclient_scripts/gate/check_gate.py --mode quick`，不能只用 TS 检查替代 gate |
| C++ telemetry 合同 | 相关 C++ 单测，优先覆盖 `qmclient_monitoring_test`；Windows 使用 `qmclient_scripts/cmake-windows.cmd --build cmake-build-release --target run_cxx_tests -j 14` |
| 常规 C++ 性能优化 | 同操作路径优化前后 perf report，相关 C++ 测试，至少 `python qmclient_scripts/gate/check_gate.py --mode quick` |
| 触碰官方长期稳定 CUI / 菜单基础路径 | 影响面说明、外围替代方案说明、相关 C++ 测试、目标页面视觉 / 输入 / 非默认 UI scale 检查，至少 `python qmclient_scripts/gate/check_gate.py --mode quick` |
| jobs / GPU upload / resource publish | 交互帧 stop reason、预算耗尽原因、fallback 行为验证、相关 C++ 测试 |
| 用户反馈 / debug bundle | 脱敏检查、bundle 字段检查、文档或测试覆盖 |

没有跑的验证必须在最终汇报中写成 gap；不能写成已通过。

## 后续优先级

1. 先把性能量化系统收口到生产级可信：合同、阈值、边界样本、同路径对比、debug bundle、固定场景。
2. 再清理已知用户可见 bug 涉及的 FBO 路径，按 bugfix / cleanup 最小绕开或移除。
3. 用 perf report 把长帧归因到页面切换、列表处理、资源 drain、UI rebuild 或 device bound。
4. 把无上限 `avg/max/min FPS` 纳入同路径对比，让开发者和用户都能直观看到优化是否改善体感吞吐量。
5. 每轮实现前先做同路径 UI bug audit，特别是上一轮性能优化和官方长期稳定基础路径的风险。
6. 按证据指向做源头降温：不可见不做、dirty 才重建、重活分帧、I/O 和 decode jobs 化。
7. 最后做局部结构化重构，只抽取已经被多个证据点证明有价值的 helper 或合同。
