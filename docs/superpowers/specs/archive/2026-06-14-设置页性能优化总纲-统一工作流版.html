① 摘要与统一原则

当前主线不是单点优化，而是一套分层调度系统：loading 阶段允许预热，但必须可预算、可恢复、可观测；可见阶段只复用、不首建；后台工作只能吃剩余预算；报告只认目标窗口，不认“看起来不卡”。这套工作流已覆盖设置页 tclient / qmclient / 基础页、ingame_esc_open、资源页、demo browser、Tee 皮肤列表与通用稳定文本池。

新的判定重心也一并调整：卡顿不再只看平均 FPS 是否低于显示器刷新率，而是同时看 frame time spike、p95 / p99、1% low、scroll recovery。其中 1% low 对皮肤列表这类滚动场景是第一类指标，因为用户最先感知到的是尾部掉帧，而不是均值。

统一原则（跨层不变量）：
  1. remaining=0 只表示某一层计划完成，不表示整个页面已通过验收。
  2. targetSettings 仍然是稳定文本的唯一验收源；顶层混合 verdict 不替代它。
  3. 可见阶段只复用稳定文本容器，不允许首建，也不允许 stale entry 现场重建。
  4. 资源预热与 UI cache 预热是两条不同的链路：资源走 VISIBLE/PREFETCH/BACKGROUND + GPU upload 预算；UI cache 走 plan collection + prebuild 游标。
  5. 后台工作（demo metadata / skin loading / resource decode / upload / preload）只能吃 adaptive budget 的剩余 token，不能抢占 visible。

② 第一性原理：UI 性能优化的本质

这一章是三份旧文档中只在 2026-06-10 完整出现过的内容，恢复并按 2026-06-14 代码现状重写。它解释为什么要这样优化，而不只是怎么优化。

2.1 一帧里到底发生了什么

DDNet 每一帧要做两件事：游戏渲染（世界、实体、特效、HUD）和菜单渲染（设置页、服务器列表等）。这两件事跑在同一个线程里，共享同一帧的时间预算。优化每一帧本质上就是减少每一项的工作量，且只在变化时才做。

Frame Time = CPU 提交 + GPU 绘制 + 同步等待
           = (布局计算 + 文本创建 + 输入检测 + 状态更新 + Draw Call 提交)
           + (顶点处理 + 光栅化 + 像素着色 + 混合)
           + (SwapBuffers / v-sync + 驱动同步)

一帧 16.67ms (60Hz)
├── 游戏渲染：8-12ms
├── 菜单渲染：2-4ms（正常）
└── 剩余：给下一帧

当菜单渲染突然从 2ms 涨到 200ms，这一帧就“爆了”——游戏画面停顿，
玩家感受到卡顿。优化目标不是让菜单“更快”，而是让它不要突然变慢：
消灭尖峰帧，保持帧时间稳定。

2.2 immediate-mode 与 retained-mode 的根本取舍

UI 渲染架构在两种模式间选择。理解这个取舍是判断“哪些优化适用”的前提：

维度immediate-mode（CUI / ImGui 系）retained-mode（通用对照：React / Qt 等）
状态归属调用方持有，UI 系统每帧从头重建绘制描述UI 系统持有节点树、布局、动画状态
每帧成本O(all visible) —— 即使 90% 不可见也会跑 widget 逻辑O(changed) —— 只在 model change 时重算位置
优势无需预先规划、无状态同步问题、无 invalidation bug可以做跨帧缓存、动画运行时、render bridge 批处理
劣势必须靠外部手段（视口裁剪、虚拟化、文本池、脏检测）把成本降到 O(visible)状态一致性维护成本高，retained 树本身也是每帧 CPU 成本
重要澄清（2026-06-14 代码核对修正）：QmUI（CUiRuntimeV2）不是 retained-mode。代码证据：UiButtons.cpp 注释直接写 Wraps CMenus::DoButton_Menu，内部全部调 Ctx.m_pUi->DoLabel() / Ctx.m_pMenus->DoButton_Menu() / Ctx.m_pUi->DoButtonLogic()（CUI 底层 API）；CUiV2RenderBridge（QmRender.cpp）只做 BeginFrame/RecordDrawCall/RecordClipPush/LastFrameStats——只计数，不绘制；m_Tree 每帧 BeginFrame/EndFrame（immediate）。QmUI 实际是：CUI 底层 immediate-mode 封装层 + 动画运行时（CUiV2AnimationRuntime，唯一跨帧状态，缓存动画值）+ token 设计系统（ui_token::color/radius/font）+ 帧级 tree（统计节点数）+ render bridge（计数）。它和 CUI 同构，多了动画 resolve / token 查找 / 卡片 overdraw，不是性能优势，也不需要作为 retained 着重优化。关键后果：QmUI widget 的 DoLabel 不走 m_MenuTextPool（hitrate 低根因之一），需要让 widget 支持 streamed 文本路径（见 ⑥ Phase 3）。
外部依据：Wikipedia「Immediate mode (computer graphics)」——immediate-mode 中“屏幕整体每次都从头渲染”；Hacker News 讨论——游戏偏好 immediate-mode 是因为“无需预先规划”；ImGui ListClipper issue #2404 / #7798——处理 586k 项虚拟列表的标准实践是只处理可见行 + 小 overscan，这正是本项目 Tee 皮肤列表、demo browser、settings 重列表的目标形态。

对 QmClient 的含义：设置页跑在 CUI（immediate）和 QmUI（CUI 封装 + 动画运行时）两套调用风格上，但底层都走 CUI 的 DoLabel/DoButtonLogic，不存在 retained 树维护成本。perf/ui_runtime 能拆出 tree_begin/end、anim_advance、render_bridge、ui_runtime_total 四段，可观测 QmUI 的动画与 render bridge 额外开销。归因时按“纯 CUI 路径”和“QmUI 封装路径”分流即可。

2.3 DDNet/QmClient 的架构约束

DDNet 是 2D 俯视角游戏，决定了哪些“通用优化”不适用：

  • 所有渲染通过 quad + sprite + texture 完成，没有后处理链（bloom / motion blur / SSAO）。
  • UI 和游戏渲染共享同一个 GL/Vulkan context，共享帧预算。
  • 菜单渲染不是独立线程，发生在 CMenus::OnRender() 中。
  • FBO / recorded render target 在设置页侧已清理完毕，本轮不再回到纹理录制式页面缓存（2D UI 的 FBO 创建+录制+blit 成本常高于实时渲染）。

2.5 优化决策树

面对任何 UI 性能问题，按投入产出比顺序判断：

1. 能不做吗？   → 裁剪、虚拟化、跳过不可见区域（收益最大，维度 1）
2. 能少做吗？   → 脏检测、缓存、只更新变化部分（维度 4）
3. 能做更快吗？ → 批处理、减少状态切换（维度 2）
4. 能异步做吗？ → 后台线程/Jobs 池、延迟提交（维度 5）
5. 能不分配吗？ → 对象池、预分配、零分配热路径（维度 6）

③ 统一架构渲染工作流

这条链路是当前架构的主流程。所有页面级优化都必须能落到这条链路的某一层，而不是单独写一个局部补丁。

loading/prewarm (budget-bounded, recoverable) -> plan collection cursor (collect descriptor only: scope/page/tab/subtab/key/style) -> prebuild cursor (build real CUIElement by token, skip m_Built) -> visible guard (reuse only; record miss/stale, no first-build) -> visible-ready presentation (assets: ready-then-show or stable skeleton) -> background jobs (demo meta / skin / decode / upload / preload: leftover tokens only) -> telemetry emit (text_prebuild / text_usage / adaptive_budget / visible_preflight) -> report + quality gate (targetSettings verdict, not mixed verdict) -> acceptance decision

⑤ 量化模型

5.1 分层帧时间目标

DDNet 是快节奏平台游戏，流畅性要求高于一般应用。p99 比平均值重要得多：一次 50ms 的卡顿远比 10 次 5ms 的微波动更影响体验。优化应优先消灭“尖峰帧”。

指标目标值理由
UI 帧时间均值≤ 4ms为游戏渲染留足 12ms+ 预算（60fps）
交互帧（切 tab / 滚动）≤ 8ms不超过 120Hz 刷新周期
最差帧 p99≤ 16ms不超过 60Hz 周期；超出即用户可感知卡顿
首帧（冷启动进入设置页）≤ 33ms允许一次较长帧，但不能连续两帧超标

5.2 尾部指标论证

量化系统必须同时描述平均吞吐和尾部体验。对滚动列表和首屏切 tab 场景，尾部比均值更重要。

指标用途状态 / 解释
fps_avg整体吞吐已采集 只能看大致是否偏慢
fps_min / frame_ms_max绝对最差点已采集 帮助发现首帧或极端阻塞，但会被单个离群值放大
frame_ms_p95 / p99尾部分布已采集 当前 report 主线
1% low尾部体验未落地 以最慢 1% 帧的平均值反推，直接反映滚动/翻页/打开面板的“掉帧感”。皮肤列表滚动必须纳入
scroll recovery交互恢复未落地 滚动停止后系统恢复稳定帧的速度，适合资源页和皮肤列表
外部依据：ASUS ROG「What are 1% Lows?」——1% 和 0.1% low 量化卡顿，比 avg FPS 更重要；Android Game developer docs 把 P99 FPS（1% percentile）定义为 stutter indicator；SuperTuxKart 开发博客「Why average FPS and 1% low FPS are misleading」专门论证 avg FPS 是 deeply flawed metric——constant smooth 120 avg FPS 优于波动的 60 avg。本项目应把 1% low 提升为一等指标。

落地口径：fps_summary 继续保留 avg/min/max/p95/p99，同时在 report 与 summary 中增加 1% low；若目标窗口缺少 tail 数据或无法计算 1% low，quality 不能判定为充分。

5.3 当前 baseline（2026-06-10，post-FBO-cleanup，1ms 采样阈值）

verdict: FAIL
p50: 1.326ms  p90: 2.014ms  p95: 2.420ms  p99: 12.906ms
max: 342.777ms  spike: 464 个  avg: 2.050ms

⑥ 后续可行道路

路线图按统一工作流的层组织，而不是按旧的 P0/P1/P2 单点策略。每一项都明确它落在哪一层、解决哪个 gap、用什么 telemetry 验收。

6.1 按 工作流层组织的路线图

阶段工作流层目标验收信号
P0 Visible guard + Prebuild 把 stable text coverage 从“部分完成”推到 settings 全 scope：TClient/QmClient 重 tab 的 slider label、checkbox label、按钮标题、tab/section/module 标题、列表静态标题、固定说明文案全部入池；非稳定候选（[new] 文案、彩虹/动画颜色标题）显式进 allowlist settings_subtab_switch / ingame_esc_open 里的 text_new → 0，所有 miss 都带可定位 key；stableTextCoverage.acceptanceBlocked=false
P0 Visible guard 候选扫描覆盖原始 UI API + settings wrapper + QmClient helper/变量路径三层；QmNewFeatureLabel、RainbowColor、DoModuleHeadline 必须先入 candidate 再以 stateful-new-label/animated-style 显式 allowlist，不被扫描器静默忽略 候选审计报告：candidate 总数 / 已入池 / allowlist 显式排除，三者可对账
P0 Report / quality 把 1% low 与 scroll_recovery 从“建议口径”落地为真实字段：C++ 侧 fps_summary 增 frame_ms_1pct_low、scroll window 增 scroll_recovery_ms；TS report 一等指标 皮肤列表滚动窗口能输出 1% low 与 scroll recovery，缺 tail 数据时 quality 判“不足以判断”
P1 Loading prewarm（分离） 把 PrewarmVisibleSettingsResources 拆成两条链路：资源预热走 VISIBLE/PREFETCH/BACKGROUND + GPU upload；UI cache 预热只走 plan collection + prebuild 游标，禁止写交互/布局状态。每条都带独立 telemetry + 同路径 A/B fps_summary prewarm_cost_ms + first_use_hit/first_use_saved_ms；无收益的预热项被削减或改 demand-driven
P1 Background jobs adaptive budget 已统一六类 token，继续收敛 IDLE_DRAIN backlog 硬上限与“健康进展”条件；demo metadata / header-date 扫描、Tee preview key 全量化为可见区 + dirty 缓存 work_drain 极端归因值收敛；目标窗口 frame_ms 不再因后台积压恶化
P1 Visible-ready（assets） 资源页/demo/Tee 在 visible-first 基础上补 visible-ready：先 ready 再 show，或用不缩放稳定 skeleton；卡片尺寸不在首屏缩放重排 geometry_stable=1、thumb_starts_during_draw=0、visible_ready=1
P2 QmUI runtime telemetry 修 perf/qmclient frame 对齐；补 subtab/module/widget_scope、layout_ms、draw_calls、clip_pushes、flush_count；让 CUI/QmUI 混合页能回答“谁主导这帧” 同一长帧能按 runtime + stage + widget_scope 对齐到 frame
P3 条件性 render backend 只有当 render_bridge、draw_calls、flush 或 pipeline 切换明确成为长帧主因时才进入 Vulkan/OpenGL 提交路径优化 telemetry 证明 render backend 是主因

6.2 明确不做

  • ❌ FBO / recorded render target / 纹理录制式页面缓存：设置页侧已清理，2D UI 不走此路。
  • ❌ 引入 retained-mode 全局 UI 框架：与 DDNet CUI 架构冲突；QmUI 本身是 CUI 封装 + 动画运行时（非 retained，见 2.2 澄清），不外扩成独立框架。
  • ❌ 全局 Draw List 批处理：与 CUI 架构冲突，改动量巨大；section 内批处理已够用。
  • ❌ Server Browser / Demo Browser 作为 settings-only 主证据：不同根因（同步遍历 vs 设置页进入/切换），不混入 settings verdict。
  • ❌ 全局 scheduler 大重构：不改 DDNet upstream 架构。

⑦ 验收口径与门禁

  1. settings:tclient、settings:qmclient、ingame_esc_open 继续作为 stable text 主验收窗口。
  2. settings:assets 进入时必须先满足 visible-ready，再允许展示真实卡片；不能靠 visible-first request 假装无感。
  3. 皮肤列表滚动必须把 1% low 纳入验收（此项依赖 P0 telemetry 落地）；当前在它落地前，验收仍以 frame_ms_p95/p99 + spike 为主，但 report 必须显式标注 1% low missing。
  4. 任何 target window 缺少 targetSettings、fps_summary、settings_text_usage、settings_adaptive_budget 或 visible-ready 证据时，都不能标记为通过。
  5. settings_text_miss、settings_text_stale 或目标窗口前 plan collection / prebuild 仍有 remaining 时，report 必须把 targetSettings 标为“不足以验收”，不能只显示正文 warning。
  6. 判断顺序固定：先看 settings / ingame Esc 目标窗口 → 再看 Tee / work_drain 背景热点 → 最后才考虑 backend 提交路径。
  7. Gate 命令：纯文档改动至少 python qmclient_scripts/gate/check_docs.py；常规代码改动至少 python qmclient_scripts/gate/check_gate.py --mode quick。同一 build 目录中 game-client / testrunner / run_cxx_tests / run_rust_tests / package_default 必须串行。
一句话总结：当前性能优化的目标不是“把一个页面做快”，而是把一条多阶段调度链路做成可证实、可退火、可验收的系统。
