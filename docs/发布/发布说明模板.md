# QmClient 发布说明（Release Note）写作规范

> **与生成脚本的关系**：`qmclient_scripts/generate_release_notes.py` 输出**面向玩家的自动说明**（确定性润色，**不调用外部 AI**）。脚本已实现：✅ 正式版 / 预发布通道头、✅ 功能领域分组、✅ 中文优先、✅ Conventional type→中文玩家前缀（`feat`→新增 等）、✅ 同领域性质单一时省略前缀、✅ 同领域相同/近相同条目去重、✅ 「其他」≤4 条并附未列出提示、✅ 轻量文案清理（空白折叠、去句末标点）、✅ 默认排除 `refactor`/工程类。仍属可选人工判断的部分：更深的玩家视角改写、跨条合并、拆分新领域。
>
> **工作流**：
> - **Nightly 预发布**：CI 跑脚本 → 输出即为**终稿**（自动汇总并润色，**无需人工润色**）；可被下次 Nightly 覆盖。
> - **正式版 Stable**：CI 同样跑脚本；输出已应可读，维护者**可选手动**再润色后编辑 GitHub Release。

---

## 0. 发布通道（正式版 vs 预发布）

面向中文 GitHub 协作团队，发布说明必须先标明**通道**，避免玩家把 Nightly 当成稳定版。

| 通道 | GitHub Release | Tag 约定 | 读者预期 | 说明文案要点 |
|------|----------------|----------|----------|--------------|
| **正式版 Stable** | 普通 Release（`prerelease: false`，可标 Latest） | `vX.Y.Z`（如 `v2.74.9`） | 日常使用 | 标题带「正式版」；脚本已生成玩家可读条目；可选手动润色合并 |
| **预发布 Pre-release** | Pre-release（`prerelease: true`，`latest=false`） | 当前为 **`nightly`**（可 force 覆盖）；以及 `*-rc*` / `*-beta*` 等 | 内测 / 尝鲜 | 标题带「预发布」；**必须**写不稳定、会被覆盖；说明=脚本自动终稿；相对最近正式版的变更范围 |

规则：

1. **正式版 = Stable**：只有打 `vX.Y.Z` 并走正式发版流水线时使用；不要用正式版文案包装 Nightly。
2. **Nightly = Pre-release**：对应仓库里的 `nightly` tag + GitHub Pre-release；每次构建可覆盖同名 Release。
3. 脚本 `--channel auto`：`vX.Y.Z` → stable；`nightly` / 含 rc|beta|alpha|pre → pre-release。
4. 预发布相对范围默认对比**最近正式版 tag**（不是上一次 nightly），方便回答「比 stable 多了什么」。
5. 写发版说明前：先定通道。Nightly 以脚本输出为准；正式版可在脚本输出上可选润色。禁止把工程类 commit 堆进玩家说明。

## 1. 这个文档解决什么

本规范用于撰写**单次版本的发布说明**（Release Note）——也就是每次发版时贴在 GitHub Release、QQ 群、官网更新公告里的那份"本次更新内容"。

它和 [`CHANGELOG_QmClient.md`](./CHANGELOG_QmClient.md) 是**两份不同定位的文档**，不要互相替换：

| | CHANGELOG_QmClient.md | Release Note（本规范） |
|---|---|---|
| **定位** | 长期演进日志 | 单次版本发布说明 |
| **组织方式** | 时间区间 × 变更类型（新增/变更/修复/…） | 功能领域 × 性质前缀 |
| **读者** | 排查问题、回溯历史、评估升级风险的人 | 看更新公告的玩家和普通用户 |
| **完整性** | 尽量全，宁可细 | 只挑用户能感知的，越短越好 |
| **生命周期** | 永久累积 | 随版本一次性发布 |

> 一句话：CHANGELOG 回答"历史上发生了什么"，Release Note 回答"**这次我能体验到什么**"。

---

## 2. 整体结构

一份 Release Note 由四部分组成：

```
版本标题（版本号 + 日期 + 一句话亮点）
└── 亮点摘要（可选，2-3 句话点出本次重点）
    └── 主题分组（按功能领域，正文核心）
        └── 收尾信息（关联 PR / 完整日志链接 / 下载链接，可选）
```

---

## 3. 核心模型：领域 × 前缀（正交，不要混）

这是本规范最关键的一条，专门解决"主题和前缀信息重复"的问题。

- **主题（二级标题）= 改了哪个功能领域**（图片、Linux、输入…）
- **前缀（每条开头）= 这次改动的性质**（feat 新增 / fix 修复 / improve 优化…）

两者**正交、互补**：主题告诉你"碰了什么"，前缀告诉你"怎么碰的"。

| ✅ 正确 | ❌ 错误 |
|---|---|
| 主题叫"图片"，组内既有 `feat` 也有 `fix` | 主题叫"新增功能"，组内全是 `feat`（标题和前缀说同一件事，冗余） |
| 主题叫"输入与操作"，组内 feat/fix/improve 混合 | 主题叫"问题修复"，组内全是 `fix`（那直接用前缀分组即可，何必起主题） |

**判断准则**：如果你起的主题名本身就是一种"变更性质"（新增/修复/优化/重构），那就和前缀重叠了——**主题应该换成功能领域名**。

---

## 4. 主题命名

### 4.1 命名原则

1. **主题名是"功能领域/模块"，不是"变更性质"。**
2. **单个主题至少 2 条才单独立组**；只有 1 条的零散改动，并入最相近的领域，不要为它单独开组。
3. **主题名随版本实际变更密度灵活调整**——这次图片改得多就立"图片"组，下次没有就不出现。不要为了凑齐一套固定主题而硬塞。
4. **领域聚集时可临时提升**：某领域本次改动密集（≥3 条）就单独成组；零散则归入相近主题。

### 4.2 常用功能领域（参考，非强制）

从 QmClient 历史变更中提炼的高频领域，起名时优先复用，保持跨版本一致：

| 领域 | 覆盖范围 |
|---|---|
| 视觉与皮肤 | 图片、皮肤、材质、特效、菜单外观 |
| HUD 与界面 | 计分板、灵动岛、通知栏、进度条、按键显示 |
| 聊天与社交 | 聊天气泡、好友、屏蔽词、关键词回复 |
| 翻译 | 入站/出站翻译、LLM 后端、语言切换 |
| 语音 | RiVoice、语音聊天、降噪 |
| 输入与操作 | 快捷键、手写笔、Fast Input、操作手感 |
| 编辑器 | 地图编辑、绘图工具 |
| 设置页 | 设置项、配置域、Tags 筛选 |
| 媒体 | 系统媒体控制、歌词、视频背景 |
| 性能与稳定性 | 帧率、内存、加载速度、崩溃 |
| 平台适配 | Linux / macOS / Windows / Android（可合并为"平台适配"，或某平台改动多时单独成组，如"Linux"） |

> 主题标题可酌情加 emoji 增强可读性（如 `## 🖼️ 图片`），但**全篇必须一致**——要么都加，要么都不加。

## 5. 前缀规范

### 5.1 前缀对照表

面向玩家的 Release Note 只用以下几个前缀（Conventional Commits 的精简子集）：

| 前缀（脚本中文） | Conventional | 含义 | 玩家视角的说法 |
|---|---|---|---|
| `新增：` | `feat` | 新功能 / 新增能力 | 新增了… |
| `改进：` | `improve` | 已有功能的体验改进（非 bug） | 优化了… / 改进了… |
| `修复：` | `fix` | 修复 bug | 修复了… |
| `优化：` | `perf` | 性能提升 | 性能优化… |
| `回退：` | `revert` | 回退变更 | 回退了… |
| （默认不写） | `refactor` | 内部重构，行为不变 | **原则上不写进 Release Note**（玩家无感知） |

### 5.2 前缀使用规则

1. **前缀只在"主题内"起区分作用**。一个主题内如果全是同一种性质（如全是 `feat`/新增），**省略前缀**，只保留主题即可——避免冗余（见第 3 节）。脚本对同领域同 type 会自动省略。
2. **玩家无感知的改动不进 Release Note**：`refactor` / `docs` / `test` / `chore` / `ci` / `build` 这类原则上不写。如确需记录（如向贡献者说明构建变化），统一收进末尾的"开发者与构建"小节并精简，不要混在主条目里。
3. **一条只用一个前缀**，按最主要的效果归类，不要堆叠。

## 6. 每一条的写法

### 6.1 玩家视角，隐藏实现细节

写"用户能感知到什么"，**不写"代码怎么实现的"**。实现细节属于 CHANGELOG，不属于 Release Note。

| ❌ 暴露实现 | ✅ 玩家视角 |
|---|---|
| `fix: 修复给 Tauri 命令传入过大的 Uint8Array 会报错` | `fix: 修复 Linux 下保存大体积资源时崩溃` |
| `feat: add support for binary data transfer via Latin-1 encoding in IPC` | `fix: 修复 Linux 下传输大文件时偶发报错` |
| `fix: 修复 CSectionLoader Process() 视口优先级失效` | `fix: 修复设置页偶发卡顿` |

### 6.2 动宾结构，突出效果

- 一条一个改动，**动宾结构开头**，先说"做了什么"再说"带来什么"。
- 关键词可加粗，方便扫读：`- feat: 新增**图片压缩**设置项，控制图片节点体积`。
- 太长的说明可在主条目下**缩进一行补充**，但 Release Note 尽量精简，细节留给 CHANGELOG。

### 6.3 语言策略

- **全中文**正文。
- **保留英文**的仅限：配置项/命令（`` `qm_spec_teleport` ``）、专有名词（DDNet / TClient / Linux / Vulkan / FFmpeg）、文件名。
- 代码和配置项用反引号包裹。
- **禁止中英文整句混杂**——不要前面 16 条中文、最后 1 条突然变英文。要么全中文，要么整篇统一另一种语言。

---

## 7. "其他"组的纪律

"其他"是最容易失控的兜底组，必须约束：

1. **上限 4 条**。脚本对「其他」自动截断到 4 条，并追加「…另有 N 条未列出，见完整变更」。人工润色正式版时也可回头拆分：能否归入已有主题？能否把聚集的几条提升为新主题？
2. **必须有前缀**（除非该组性质单一被省略），且优先尝试归入具体领域，实在无法归类才落这里。
3. **不要把用户可感知的功能和零碎修复混在一起**——可感知的功能应该有它自己的主题。

---

## 8. 收尾信息（可选）

正文之后可附：

- **关联 PR**：`关联 PR: #138, #139`
- **完整更新日志**：指向 `docs/CHANGELOG_QmClient.md` 对应版本段落
- **下载链接**：GitHub Release 页面会自动附带构建产物，通常无需手写

## 9. 空白模板（复制即用）

```markdown
# vX.Y.Z（YYYY-MM-DD）

<一句话点出本次最大亮点>。本次更新带来 <领域A>、<领域B> 和一批 <领域C> 优化。

## <领域 1>
- feat: <新增了什么>
- improve: <优化了什么>
- fix: <修复了什么>

## <领域 2>
- feat: <新增了什么>

## 性能与稳定性
- perf: <提升了什么>
- fix: <修复了什么>

## 其他
- <无法归类的零散项，≤4 条>

---

**关联 PR**: #xxx
**完整更新日志**: 见 `docs/CHANGELOG_QmClient.md` 的 vX.Y.Z 段落
```

## 10. 正反示例对比

### 反面（你最初给的那版，标注问题）

```markdown
## 图片优化
- feat: 增加图片压缩的设置项
- feat: 优化设置项默认参数          ← 这是 improve，不是 feat
- feat: 增加图片节点生成时，黑白压缩的功能

## Linux优化
- feat: 添加Linux运行时设置页面
- fix: 修复Linux环境下给Tauri命令传入过大的Uint8Array会报错   ← 暴露实现细节（Tauri/Uint8Array）
- feat: add support for binary data transfer via Latin-1 encoding in IPC   ← 英文 + 暴露实现

## 其他优化
- feat: 给Tab组件添加动画
- feat: 增加qf快捷键……
- fix: 当按键序列中出现后缀相同前缀不同的两个快捷键时……
- refactor: 优化右键菜单编辑页面   ← refactor 不该进面向玩家的 note
- （…共 8 条，"其他"严重过载）
```

问题清单：
1. "图片优化""Linux优化"组下几乎全是 `feat`，前缀冗余。
2. 多处暴露实现细节（Tauri / Uint8Array / Latin-1 / IPC）。
3. 最后一条突然变英文。
4. "其他优化"塞了 8 条，混了功能和修复。
5. `refactor` 不该出现在面向玩家的发布说明里。

### 正面（按本规范修正后）

```markdown
# v2.60.0（2026-06-26）

本次更新带来图片压缩、Linux 全面适配，以及一批操作与输入体验优化。

## 图片
- 新增**图片压缩**设置项，可控制图片节点体积
- 优化图片压缩默认参数，开箱即用
- 新增图片节点生成时的**黑白压缩**，进一步减小体积

## Linux 适配
- 新增 Linux 运行时设置页面
- Linux 下支持调整 UI 缩放
- 修复 Linux 下保存大体积资源时崩溃
- 修复 Linux 下传输大文件时偶发报错

## 输入与操作
- 新增 `qf` 快捷键，摄像机定位到选中物体但不改变缩放
- Tab 切换新增过渡动画
- 完善**手写笔**支持
- 修复按键序列前缀重叠时优先触发更长的快捷键
- 修复出现完全相同快捷键时不再二选一，改为同时执行
- `Ctrl+F` 搜索框支持 Esc 关闭、Enter 下一个、Shift+Enter 上一个

## 性能与稳定性
- 视野缩放过小时 URL 节点不渲染文字，提升性能
- 优化"整数化渲染文字大小"开启时的体验

---

**关联 PR**: #xxx
**完整更新日志**: 见 `docs/CHANGELOG_QmClient.md` 的 v2.60.0 段落
```

注意修正点：
- "图片"组三条全是新增性质，**直接省略前缀**，避免冗余。
- 实现细节全部翻译成玩家视角（Uint8Array/Latin-1 → "保存大体积资源时崩溃/传输大文件报错"）。
- 统一全中文。
- `refactor: 右键菜单重构` 玩家无感知，**直接移除**（如需保留，归到末尾"开发者与构建"小节）。
- 拆分了过载的"其他"：输入相关提升为"输入与操作"主题，性能相关归"性能与稳定性"。

## 11. 发布前自查清单

- [ ] 每个主题是不是"功能领域"而非"变更性质"？（避免和前缀重叠）
- [ ] 主题内是否性质单一到可以省略前缀？能省则省。
- [ ] 有没有暴露实现细节（框架名、数据结构、内部模块名）？全部改成玩家视角。
- [ ] 语言是否全篇统一（全中文，技术术语保留英文）？
- [ ] "其他"组是否 ≤4 条？超了就拆。
- [ ] `refactor`/`ci`/`chore` 等玩家无感知的是否已移出正文？
- [ ] 版本号、日期、关联 PR 是否齐全？
