# 卡片规格

> 状态：**草案**（2026-09-19）
> 本文是**全局卡片**的规格。首版聚焦**高度自适应**，因为它是卡片作为公共基础设施的第一位约束。
> 相关：[界面规格.md](界面规格.md)、[在研任务.md](../计划/在研任务.md)

---

## 一、定位

卡片是公共基础设施，不是某个页面的私有实现。因此对卡片的要求是**框架级**的：

- 页面只声明"有哪些卡片"，不关心卡片内部如何布局；
- 卡片自己负责**在任意内容与任意配置组合下给出正确高度**；
- 新卡片接入既有调度能力（帧预算、令牌、测量），而不是自建一套。

**高度自适应是这个契约的核心**：卡片高度错了，不是"某个页面显示不好看"，而是**框架失败**。

**前置条件：代码模块化**。"页面只声明卡片、功能代码不耦合页面"要成立，前提是功能代码本身有清晰边界。当前 `menus_qmclient.cpp`（7000 行）与 `menus_tclient.cpp`（6981 行）是主要障碍——拆分方案见 [大文件拆分方案.md](../计划/大文件拆分方案.md)。

**卡片即文件单位**：一张卡片 = 一个自包含文件，其中同时包含**渲染、测量、依赖声明**三部分，注册是唯一的对外接口。分类归属由注册声明表达，**不由目录表达**——否则"拖拽卡片"会退化成"移动文件"。这使"高度单一真相源"从规约变成物理事实（详见拆分方案 5.1–5.4）。

## 二、现状机制（代码事实）

### 2.1 高度的来源

卡片高度由**测量回调**给出，缓存于 deck：

- `SSettingsCardDefinition::m_Measure`（`SettingsCardDeck.h`）——返回内容高度；
- 缓存字段 `m_vContentHeights`、`m_vContentWidths`、`m_vMeasureRevisions`（`SettingsCardDeck.h:153`）；
- 高度动画：`m_TargetContentHeight`、`m_AnimatedContentHeight`、`m_LastContentHeightTarget`、`m_ContentHeightInitialized`（`SettingsCardDeck.h:95-111`）。

### 2.2 缓存失效只有三个条件

`SettingsCardDeck.cpp:264-281`：

```cpp
// 1. 宽度变化 → 失效
if(std::abs(CachedContentWidth - ContentWidth) > 0.01f) { CachedContentHeight = -1.0f; }

// 2. revision 变化 → 失效
if(CachedMeasureRevision != pDefinition->m_MeasureRevision) { CachedContentHeight = -1.0f; }

// 3. 每帧测量 → 失效
if(SettingsCardDeckNeedsContentMeasure(Collapsed, pDefinition->m_MeasureEachFrame, CachedContentHeight))
    CachedContentHeight = pDefinition->m_Measure ? pDefinition->m_Measure(ContentWidth) : 0.0f;
```

**关键推论**：卡片的**内容随配置变化**时，若宽度没变、revision 没变、又不是每帧测量，**高度就不会重新计算**。

### 2.3 revision 靠手工编码

`m_MeasureRevision` 需要调用方**手工把"影响高度的配置"编码成一个整数**，例如：

```cpp
// menus_qmclient.cpp:5251
case EQmModuleId::PlayerStats: return (g_Config.m_QmPlayerStatsMapProgress ? 1u : 0u) | (g_Config.m_QmPlayerStatsMapProgressStyle ? 2u : 0u);

// menus_qmclient.cpp:5263
case EQmModuleId::Lyrics: return (g_Config.m_QmSpotifyEnable ? 1u : 0u) | (g_Config.m_QmKugouHookEnable ? 2u : 0u) | (g_Config.m_QmQQMusicHookEnable ? 4u : 0u); // 来源附加行影响布局高度
```

全项目此类赋值点 **15 处以上**，且以位运算拼接。

### 2.4 `m_MeasureEachFrame` 被刻意限制

只有一处设置为非默认值（`menus_settings_controls.cpp:310`），且有**合同测试禁止**在主要设置页使用：

```cpp
// settings_warmup_layout_contract_test.cpp:99,132
EXPECT_EQ(Controls.find("Definition.m_MeasureEachFrame = true;"), std::string::npos);
EXPECT_EQ(Settings.find("Definition.m_MeasureEachFrame = true;"), std::string::npos);
```

即：团队已经认定"每帧重测"太贵，必须走 revision 路线。

## 三、核心问题：高度是"双重实现"的产物

这是本规格要解决的根本问题。

高度由**两条独立代码路径**决定，二者必须手工保持一致：

| | 渲染侧 | 测量侧 |
| --- | --- | --- |
| **做什么** | 用 `HSplitTop` **顺序消耗**矩形，消耗多少就是多少高 | 用**加法公式**估算总高 |
| **Translate 卡片实例** | `RenderQmFunctionTranslateContent`（`menus_qmclient.cpp:2702+`） | `MeasureContentHeight` 的 `case Translate`（`menus_qmclient.cpp:5650-5669`） |
| **规模** | **约 299 行，35 次 `HSplitTop`** | **约 20 行常量累加** |

测量侧的 Translate 公式：

```cpp
float Height = Rows(9.0f) + LineHeight * 1.6f + LineSpacing * 1.35f;
if(IsFtapiBackend)          Height += Row() + LineHeight * 0.8f + LineSpacing;
if(IsTencentCloudBackend)   Height += Row() * 4.0f;
else if(IsLibreTranslateBackend) Height += Row() * 2.0f;
if(IsLlmBackend) {
    Height += Row() * 7.0f + LineHeight + LineSpacing * 0.5f;
    if(g_Config.m_QmTranslateLlmEnableThinking && (...)) Height += Metrics.m_SmallSize + Metrics.m_LineSpacing;
}
return Height;
```

**它必须与那 299 行、35 次消耗逐行对应。**

作者对此有明确认知，`menus_qmclient.cpp:1916` 留有注释：

> `// 面板高度与 m_Measure 的算法逐字对应，不能再出现内容比测量值高一行的情况。`

"**不能再出现**"四个字表明:**这个错误历史上已经发生过**。

### 3.1 由此产生的四类缺陷

| 缺陷 | 触发条件 | 用户可见后果 |
| --- | --- | --- |
| **高度不足** | 渲染加了行，公式没同步 | 内容被裁剪、开关显示不全（"开关多了高度没跟上"） |
| **高度过剩** | 公式多算了，渲染没消耗 | 卡片底部空白（"平白无故多出一块高度"） |
| **条件组合遗漏** | 新增条件开关未编码进 revision | 切换开关后高度不更新，停留在旧值 |
| **魔数失配** | `Rows(9.0f)` 等常量与渲染实际行数脱钩 | 同上，且难以定位 |

### 3.2 为什么测试挡不住

现有测试是**静态合同测试**（源码字符串检查）：

```cpp
// qmclient_monitoring_test.cpp:7940
EXPECT_EQ(HudDeck.find("m_MeasureRevision = static_cast<uint64_t>(maximum(0.0f, EstimateContentHeight"), std::string::npos);
```

它只能证明"没有写某种可疑模式"，**不能证明测量值等于实际渲染高度**。这与项目 `AGENTS.md` 中"禁止用源码字符串证明运行时行为"的规范方向相反。

## 四、优化建议

按"消除根因 → 降低出错概率 → 兜住漏网"三层组织。

### 建议 1（根因）：让渲染本身产出高度，消灭双重实现

**核心思路**：同一段代码既用于渲染也用于测量，测量即"在探针矩形上跑一遍渲染"。

现成的切入点：渲染函数**已经有 `PrewarmOnly` 参数**（`menus_qmclient.cpp:2702`），它目前只用于抑制输入处理（`!PrewarmOnly && Input()->KeyPress(...)`，见 2817-2818）。扩展为"只消耗不绘制"即可：

```cpp
// 测量：走同一渲染路径，传入无限高探针，返回实际消耗
Definition.m_Measure = [this, ...](float ContentWidth) {
    CUIRect Probe{0.0f, 0.0f, ContentWidth, 1e7f};
    const float Before = Probe.h;
    RenderQmFunctionTranslateContent(Probe, ..., /*PrewarmOnly=*/true);
    return Before - Probe.h;
};
```

**收益**：测量与渲染**共用一条代码路径，结构上不可能不一致**。新增/删除行会自动反映到高度。

**代价与对策**：
- 测量成本 = 渲染成本。但项目已有 `IFrameScheduler` 帧预算体系，测量可挂在 `SettingsText` 等消费者下按预算限流；
- 需要渲染代码在 `PrewarmOnly` 下**严格不产生副作用**（不写配置、不触发网络、不改状态）。这是可审查的约束，且比"逐字对应"容易保证。

### 建议 2：把 revision 从"手工编码"改为"声明依赖"

现状要求开发者手工枚举：

```cpp
case EQmModuleId::Translate:
    if(...ftapi) return 1u;
    if(...tencentcloud) return 2u;
    ...
```

**漏一个分支就出错**，且无法验证完整性。

改为**声明式**：卡片声明"我的高度依赖这些配置"：

```cpp
Definition.m_DependsOn = {
    &g_Config.m_QmTranslateBackend,
    &g_Config.m_QmTranslateLlmProvider,
    &g_Config.m_QmTranslateLlmEnableThinking,
    &g_Config.m_QmTranslateFtapiAutoEnable,
};
```

框架自动比较这些值生成 revision。**新增依赖必须显式声明**，比位运算更容易审查，也不会因为忘记更新 `switch` 分支而静默失效。

> 若短期不便改框架，可先做**低成本的近似**：在 `m_Measure` 里读取配置时顺带累加一个哈希，把哈希一并作为 revision 来源。

### 建议 3：加"测量-渲染一致性"的运行时自检

漏网之鱼的兜底。在开发构建下**周期性强制重测**并与缓存值比较，不一致就报警：

```cpp
#ifdef CONF_DEBUG
if(帧计数 % N == 0) {
    const float ReMeasured = pDefinition->m_Measure(ContentWidth);
    if(std::abs(ReMeasured - CachedContentHeight) > 0.5f)
        dbg_msg("qmcard", "height drift: %s cached=%.1f actual=%.1f",
                pDefinition->m_Spec.m_pStableId, CachedContentHeight, ReMeasured);
}
#endif
```

**价值**：把"用户看到 UI 错位才发现"提前到"开发期日志/断言"。代价可控（只在 debug 且低频）。

### 建议 4：把高度一致性变成行为测试

现状是字符串检查；应改为**行为断言**：

- 对每个卡片，构造若干**配置组合**；
- 断言 `m_Measure(width) == 渲染实际消耗高度`（用探针矩形跑一遍渲染得到）；
- 覆盖**展开型开关**：开关关闭 / 开启两种状态下各测一次。

这与项目测试规范中"优先验证真实行为和可观察结果"一致，也能真正防住回归。

### 建议 5：给"展开型开关"一等支持

你提到的场景——**开关打开后出现子配置，必须重算高度**——目前完全依赖开发者记得更新 revision。

建议在卡片规格层提供显式声明：

```cpp
Card.ConditionalBlock(&g_Config.m_QmTranslateFtapiAutoEnable, [&]{ /* 子配置行 */ });
```

框架据此自动把该开关纳入 revision，并提供"展开/收起"的高度动画衔接。这样**条件内容"是卡片声明的一部分，而不是散落在渲染函数里靠人记**。

## 五、判定标准

卡片高度自适应算不算合格，用四个问题检验：

1. **新增一行内容，忘记改任何测量代码，高度是否自动正确？**（建议 1 达标即"是"）
2. **新增一个影响高度的开关，忘记改 revision，高度是否仍会自动更新？**（建议 2 或 5 达标即"是"）
3. **是否存在自动化手段，能在开发期发现"测量 ≠ 渲染"？**（建议 3 达标即"是"）
4. **测试失败时，是指出"哪个卡片的哪种配置组合高度不符"，还是仅仅"某字符串不存在"？**（建议 4 达标即"是"）

## 七、待确认事项

- 现有 15+ 处 `m_MeasureRevision` 手工赋值中，**有多少卡片的高度依赖未被完整编码**？需要逐卡片核对（本文未做全量核对）。
- Translate 卡片"多出一块高度"的**具体分支**未在本文确认——静态阅读只能证明该机制脆弱，**不能确定是哪一行常量与渲染不符**。需实测对比 `m_Measure` 返回值与实际消耗。
- `PrewarmOnly` 改为"测量模式"后，是否有渲染函数存在副作用（写配置、触网络）需要逐一排查。
